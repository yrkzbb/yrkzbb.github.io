    锁

    锁基础

    1. MySQL 有哪些锁？应该如何理解？

    MySQL 的锁可以从三个维度理解：锁多大范围、允许什么操作，以及具体锁住索引的哪一部分。

    1. 按锁定范围：包括全局锁、表级锁和行级锁。全局锁影响整个实例；表级锁包括显式表锁、协调 DDL 与 DML 的元数据锁（MDL），以及 InnoDB 的意向锁；行级锁粒度最小，适合高并发访问。
    2. 按兼容模式：分为共享锁（S 锁）和排他锁（X 锁）。S 锁之间兼容，S 锁与 X 锁、两个 X 锁通常冲突。SELECT ... FOR SHARE 使用共享锁定读，UPDATE、DELETE 和 SELECT ... FOR UPDATE 通常需要排他锁。
    3. 按 InnoDB 行锁范围：包括只锁索引记录的 Record Lock、只锁索引间隙的 Gap Lock，以及两者组合的 Next-Key Lock。后两者主要用于阻止范围内插入新记录。

    2. 数据库的表锁和行锁有什么作用？

    表锁和行锁都用于协调并发访问、避免冲突操作破坏数据一致性，主要区别是锁定粒度和并发成本。

    1. 表锁：一次锁住整张表，实现和管理相对简单，获取锁的开销较小，适合全表操作或并发要求不高的场景。但锁粒度大，即使两个事务访问不同记录，也可能互相阻塞，并发能力较低。
    2. 行锁：只锁住相关的索引记录或范围，不同事务修改不同记录时通常可以并发执行，适合高并发 OLTP 场景。但行锁的管理成本更高，事务锁定大量记录时会占用更多锁资源，也更容易形成复杂的锁等待和死锁。

    InnoDB 的“行锁”本质上是索引记录锁，不是直接按数据页中的物理行号加锁。

    2. 如果两个更新范围的条件不是主键或索引，还会阻塞吗？

    有可能，而且阻塞范围往往会比预期更大。InnoDB 的行锁是加在扫描到的索引记录上的；如果过滤条件没有可用索引，执行计划通常需要扫描聚簇索引的大量记录甚至全表。

    3. 两条 UPDATE 处理同一张表中不同的主键范围，一个 id < 10，另一个 id > 15，会不会阻塞？底层为什么？

    在题设只有这两个简单主键条件的情况下，通常不会互相阻塞。因为一条语句处理 id < 10，另一条处理 id > 15，目标记录和需要保护的逻辑范围互不重叠。

    底层原因是 InnoDB 的行锁建立在索引上。两条语句都可以使用主键索引直接做范围扫描，对各自命中的主键记录加排他锁；在 REPEATABLE READ 下，还会根据实际索引记录对相应边界使用 Gap Lock 或 Next-Key Lock。两边不会锁住同一条目标记录；即使稀疏数据使边界落在同一个物理索引间隙，纯间隙锁之间也是兼容的，它们的作用是阻止插入，不是互相排斥。两个事务在表级持有的意向排他锁（IX）之间也兼容，所以不会仅因操作同一张表而阻塞。

    这个结论有明确前提：执行计划确实使用主键范围，并且 SQL 没有通过其他条件、触发器或外键操作访问共同资源。如果实际扫描了相同记录，或者事务此前已经持有其他冲突锁，仍可能等待甚至死锁。

    在题设条件下通常不阻塞，最终锁范围要结合执行计划和事务上下文确认。
