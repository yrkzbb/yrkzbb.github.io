    事务

    事务基础

    1. ACID 靠什么保证？

    事务有原子性、一致性、隔离性和持久性，简称 ACID。在 InnoDB 中，它们不是由四种完全独立的技术一一实现的，而是由 undo log、redo log、MVCC、锁、数据库约束以及应用逻辑共同保证。

    1. 原子性（Atomicity）：事务中的操作要么全部成功，要么全部失败，不会只保留部分结果。InnoDB 修改数据时会生成 undo log，事务执行失败或显式执行 ROLLBACK 时，可以利用它撤销已完成的修改。
    2. 一致性（Consistency）：事务执行前后，数据都要满足完整性约束和业务规则。例如 A 向 B 转账 200 元，不考虑手续费时，两个账户的总额应保持不变。一致性是最终目标，它依赖其他三个特性、主键和外键等数据库约束，也依赖正确的应用逻辑，不是由某一种日志单独保证的。
    3. 隔离性（Isolation）：并发事务按照隔离级别的要求隔离，一个事务不应看到其他事务不该暴露的中间状态。InnoDB 主要通过 MVCC 和锁实现：普通 SELECT 通常采用 MVCC 快照读，当前读和写操作则会使用记录锁、间隙锁或 Next-Key Lock 等机制处理并发冲突。
    4. 持久性（Durability）：事务提交后，其结果在数据库崩溃后仍然可以恢复。InnoDB 采用 WAL（Write-Ahead Logging），先将相关 redo log 按配置写入并刷到持久化存储，数据页可以稍后刷盘；崩溃后通过 redo log 重做已提交修改。

    2. 一条 UPDATE 语句是原子性的吗？为什么？

    对于 InnoDB 等支持事务的存储引擎，单条 UPDATE 语句具有语句级原子性：它对目标行的修改要么全部成功，要么语句失败并撤销该语句已完成的修改，不会只更新其中一部分行后就正常结束。即使开启了自动提交，单条 UPDATE 也会作为一个事务执行；InnoDB 利用 undo log 支持语句回滚。

    这里要区分两种机制的职责：undo log 和事务回滚机制主要保证原子性；行锁主要处理并发写冲突、保证隔离性。不能把“加了行锁”直接等同于“实现了原子性”。

    但单条 SQL 的原子性不等于整段业务逻辑的原子性。如果业务是先 SELECT 读取库存，再在应用中计算，最后执行 UPDATE product SET stock = 新值，这是多个操作，并发时仍可能丢失更新。多条 SQL 要作为一个整体成功或失败，必须放在同一个显式事务中。如果表使用 MyISAM 等非事务存储引擎，也不能按 InnoDB 的事务回滚能力理解。

    3. 事务的基本特性是什么？

    事务的基本特性是 ACID：原子性表示操作要么全部成功、要么全部回滚；一致性表示事务前后数据满足约束和业务规则；隔离性表示并发事务之间按规则隔离；持久性表示提交结果在崩溃后仍能恢复。

    事务并发问题

    1. MySQL 可能出现哪些和并发相关的问题？

    MySQL 同时执行多个事务时，典型的并发读异常有脏读、不可重复读和幻读；更广义的并发问题还包括丢失更新、锁等待和死锁。

    1. 脏读（Dirty Read）：一个事务读到了另一个事务尚未提交的数据。如果后者回滚，前者读到的就是从未真正生效的数据。
    2. 不可重复读（Non-repeatable Read）：同一事务中两次读取同一行，期间另一事务修改或删除该行并提交，导致两次读取结果不同。
    3. 幻读（Phantom Read）：同一事务两次按相同条件查询一个范围，期间另一事务插入或删除了符合条件的记录并提交，导致前后读到的记录集不同。它和不可重复读的核心区别是：前者关注符合条件的记录集发生变化，后者关注同一行的值发生变化。
    4. 丢失更新（Lost Update）：两个事务都基于旧值计算新值，后提交的结果覆盖先提交的结果，使其中一次更新丢失。可以根据场景使用原子 UPDATE、SELECT ... FOR UPDATE 悲观锁，或带版本号条件的乐观锁避免。
    5. 锁等待和死锁：并发事务修改相同资源时可能互相阻塞；若多个事务循环等待对方持有的锁，就会死锁。InnoDB 检测到死锁后会选择一个事务回滚，应用程序需要捕获错误并在合理范围内重试。

    隔离级别越高，能避免的读异常通常越多，但并发性和锁成本也可能增加。InnoDB 在 REPEATABLE READ 下，普通快照读通过 MVCC 使用一致性视图，当前读则会结合 Next-Key Lock 等锁机制防止范围内被并发插入。不过，调高隔离级别不能代替正确的更新语句、锁顺序和重试机制。

    2. 哪些场景不适合脏读，举个例子？

    凡是业务判断必须基于已确认数据的场景，都不能接受脏读，例如资金结算、订单支付、库存扣减、权限校验、计费和审计。因为未提交数据随时可能回滚，如果用它继续做业务决策，就可能产生无法自动撤销的外部后果。

    例如，事务 A 将订单状态从“未支付”改成“已支付”，但还没有提交；事务 B 如果脏读到“已支付”，就可能触发发货：

    在 InnoDB 中，脏读只可能出现在 READ UNCOMMITTED 隔离级别；READ COMMITTED、REPEATABLE READ 和 SERIALIZABLE 都不允许脏读。即使是报表或监控等容许近似结果的场景，通常也更适合读取已提交的数据，而不是依赖脏读换取性能。

    3. MySQL 是怎么解决并发问题的？

    以常用的 InnoDB 为例，MySQL 主要通过事务隔离级别、MVCC 和锁机制控制并发，再配合死锁检测和应用层重试保证正确性。

    1. 事务隔离级别：MySQL 支持 READ UNCOMMITTED、READ COMMITTED、REPEATABLE READ 和 SERIALIZABLE。隔离级别规定了一个事务能看到其他事务的哪些修改，用于限制脏读、不可重复读和幻读等异常。隔离级别越高，通常限制越强，但也可能增加锁竞争和等待。
    2. MVCC：对普通 SELECT 的快照读，InnoDB 通过事务 ID、undo log 中的历史版本和 Read View 判断哪些记录版本可见。这样读操作通常无需加行锁，可以减少读写互相阻塞。
    3. 锁机制：UPDATE、DELETE 以及 SELECT ... FOR UPDATE 等当前读需要读取最新数据并加锁。InnoDB 会根据查询条件和索引使用记录锁、间隙锁或 Next-Key Lock，防止相同记录被冲突修改，并在需要时防止范围内出现新记录。
    4. 死锁检测和超时：并发事务如果循环等待锁，InnoDB 通常会检测死锁并回滚其中一个事务；普通锁等待超过配置时间后也会报错。应用程序要能够捕获这些错误并重试完整事务。

    所以，MySQL 解决并发问题的核心思路是：快照读尽量通过 MVCC 提高读写并发性，对必须串行化的冲突操作加锁，再由应用层处理业务条件、死锁重试和乐观冲突。

    4. 事务的隔离级别有哪些？

    SQL 标准定义了四种事务隔离级别，MySQL InnoDB 也支持这四种。从低到高分别是 READ UNCOMMITTED、READ COMMITTED、REPEATABLE READ 和 SERIALIZABLE。

    1. READ UNCOMMITTED（读未提交）：一个事务可以读到其他事务未提交的修改，因此可能出现脏读、不可重复读和幻读，隔离性最弱。
    2. READ COMMITTED（读已提交）：只能读到已提交的数据，所以不会脏读。InnoDB 在该级别下，每次快照读通常都会生成新的 Read View，因此同一事务的两次查询可能看到不同的已提交结果，仍可能出现不可重复读和幻读。
    3. REPEATABLE READ（可重复读）：保证同一事务中多次快照读看到一致的数据视图，可以避免脏读和不可重复读。按 SQL 标准，该级别仍允许幻读；但 InnoDB 的快照读通过 MVCC 的一致性视图避免常见幻读，当前读则通过 Next-Key Lock 等机制防止锁定范围内的并发插入。这是 InnoDB 的默认隔离级别。
    4. SERIALIZABLE（串行化）：隔离性最强，使并发事务的效果接近串行执行，可以避免脏读、不可重复读和幻读。但是它会增加锁等待和冲突，并发性通常最低。
    隔离级别 脏读 不可重复读 幻读
    READ UNCOMMITTED 可能 可能 可能
    READ COMMITTED 不会 可能 可能
    REPEATABLE READ 不会 不会 可能
    SERIALIZABLE 不会 不会 不会

    隔离级别不是越高越好，需要在一致性和并发性之间权衡。而且，调高隔离级别不一定能自动解决所有业务并发问题，例如库存超卖和丢失更新仍需要正确的原子更新、悲观锁或乐观锁。

    5. 可重复读隔离级别下，A 事务提交的数据，在 B 事务中能看见吗？

    不一定，需要看 B 事务的 Read View 何时建立，以及 B 执行的是快照读还是当前读。

    1. B 的 Read View 在 A 提交前已经建立：B 后续执行普通 SELECT 快照读时，仍使用同一个 Read View，因此看不到 A 后来提交的修改。这正是“可重复读”的含义。
    2. A 提交后，B 才建立第一个 Read View：B 的普通 SELECT 可以看到 A 已提交的数据。在 InnoDB 的 REPEATABLE READ 下，仅执行 START TRANSACTION 通常不会立即建立 Read View，它一般在第一次快照读时建立；使用 START TRANSACTION WITH CONSISTENT SNAPSHOT 则会在启动事务时建立一致性快照。
    3. B 执行当前读：SELECT ... FOR UPDATE、SELECT ... FOR SHARE、UPDATE 和 DELETE 需要读取最新的已提交版本，不使用旧的快照结果。因此 A 提交后，B 的当前读通常能看到 A 的修改；如果 A 尚未提交且持有冲突锁，B 可能需要等待。

    7. MySQL 默认的事务隔离级别是什么？

    MySQL InnoDB 的默认事务隔离级别是 REPEATABLE READ，也就是可重复读。在该级别下，普通快照读通过 MVCC 和 Read View 保证同一事务内多次读取的数据视图一致；当前读则会结合记录锁、间隙锁或 Next-Key Lock 处理并发冲突。

    8. MySQL 设置了可重复读隔离级别后，怎么保证不发生幻读？

    InnoDB 在 REPEATABLE READ 下不是只用一种机制防止幻读，而是分快照读和当前读处理：快照读依靠 MVCC 的一致性视图，当前读依靠 Next-Key Lock 等锁机制。如果业务要求“查询某个范围后继续修改，并保证期间不能插入新记录”，应从第一次查询开始使用 SELECT ... FOR UPDATE 等锁定读，而不是先做普通 SELECT。

    1. 快照读：普通 SELECT 首次建立 Read View 后，后续快照读通常复用同一个视图。其他事务后来插入并提交的记录对该视图不可见，因此前后两次相同范围的快照读不会凭空多出“幻行”。
    2. 当前读：SELECT ... FOR UPDATE、UPDATE 和 DELETE 等需要读取最新数据。对范围查询，InnoDB 会根据扫描的索引范围使用 Next-Key Lock，它相当于记录锁加间隙锁，既锁住已有索引记录，也阻止其他事务向相关索引间隙插入新记录。

    9. SERIALIZABLE 串行化隔离级别是通过什么实现的？

    InnoDB 的 SERIALIZABLE 主要通过更严格的加锁读和锁冲突规则，使并发事务的最终效果等价于某种串行执行顺序。它不是把整个 MySQL 变成单线程，没有冲突的事务仍然可以并发执行。

    在显式事务中，InnoDB 会将普通 SELECT 按加共享锁的读来处理，效果类似 SELECT ... FOR SHARE；UPDATE、DELETE 等写操作需要排他锁。对范围访问，还会结合间隙锁或 Next-Key Lock 阻止其他事务插入会改变查询结果的记录。

    有一个容易忽略的例外：当 autocommit=1 时，每条普通 SELECT 本身就是独立事务，InnoDB 可以采用一致性非锁定读。要让多条语句共同获得串行化隔离，应把它们放入同一个显式事务。

    共享锁之间可以兼容，但共享锁与排他锁、排他锁与排他锁之间会发生冲突。冲突事务需要等待对方提交或回滚，如果形成循环等待，InnoDB 会通过死锁检测回滚其中一个事务。因此 SERIALIZABLE 能提供最强的隔离性，但容易带来更多锁等待、死锁和更低的并发能力。

    MVCC

    1. 什么是 MVCC？它是如何实现的？

    MVCC 是多版本并发控制。它的核心思路是为同一行数据保留可追溯的历史版本，并根据当前事务的 Read View 决定哪个版本可见。这使普通查询可以读取合适的数据版本，而不必和写事务相互阻塞。

    InnoDB 的实现主要包括以下几部分：

    1. 隐藏列：InnoDB 记录中包含创建或最后修改该版本的事务 ID，以及指向对应 undo 记录的回滚指针。如果表没有合适的主键或唯一非空索引，InnoDB 还会生成隐藏行 ID 用作聚簇索引键。
    2. undo log 版本链：更新记录前，InnoDB 会在 undo log 中保留能够构造旧版本的信息。新版本通过回滚指针连向更旧版本，形成版本链。
    3. Read View：Read View 会记录创建快照时活跃的读写事务集合和相关事务 ID 边界。查询某行时，InnoDB 将该行版本的事务 ID 与 Read View 比较：如果版本对当前事务可见，就直接返回；否则沿 undo log 版本链向前查找，直到找到可见版本或确认该行不可见。

    READ COMMITTED 和 REPEATABLE READ 的重要区别就在 Read View 的创建时机：READ COMMITTED 下每次快照读通常创建新的 Read View，所以可以看到其他事务刚提交的数据；REPEATABLE READ 下一个事务的多次快照读通常复用首次建立的 Read View，所以能保持可重复读。

    MVCC 主要服务于普通 SELECT 快照读。UPDATE、DELETE 和 SELECT ... FOR UPDATE 等当前读需要获取最新已提交版本并加锁，不能只靠 MVCC 解决写冲突。

    事务实践与优化

    1. 滥用事务，或者一个事务里有特别多 SQL，有什么弊端？

    事务不是越大越安全。一个事务包含过多 SQL 或长时间不提交，会扩大锁、日志、版本保留和失败回滚的成本，典型问题有：

    1. 锁持有时间变长：事务持有的行锁、间隙锁和元数据锁通常要到提交或回滚后才释放。长事务会导致其他请求长时间等待，增加超时和死锁概率，也可能阻塞 ALTER TABLE 等 DDL。
    2. 阻碍 undo 清理：长时间存活的 Read View 可能使旧版本暂时不能被 purge，导致 undo log 和历史版本堆积，增加存储与 MVCC 查找成本。
    3. 日志和资源压力增大：大量修改会产生更多 undo log、redo log 和 binlog，占用 Buffer Pool、磁盘和 I/O 带宽，也会让单个大事务在复制端的应用时间变长，可能增加复制延迟。
    4. 失败和回滚成本高：事务越大，在末尾遇到错误、死锁或连接中断时，需要撤销的工作越多，回滚可能花费很长时间，重试代价也更高。
    5. 事务占用连接更久：如果在事务中执行远程调用、文件 I/O、人工交互或长时间计算，会同时占用数据库连接和锁，降低连接池吞吐量。
