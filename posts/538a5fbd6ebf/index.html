    网络场景

    浏览器访问流程

    1. 描述一下打开百度首页后发生的网络过程？

    核心过程可以概括为：解析 URL、获得目标地址、建立安全连接、发送 HTTP 请求、接收响应并渲染页面。具体协议会受浏览器缓存、代理和服务端是否支持 HTTP/2、HTTP/3 等因素影响。

    1. 处理 URL：浏览器解析协议、域名、端口和路径。若输入的是域名或 HTTP 地址，还可能经过地址栏搜索判断、HSTS 或服务端重定向，最终访问 HTTPS 地址。
    2. 检查本地缓存：浏览器会检查强缓存、Service Worker 等；如果资源可直接使用，部分网络请求可能省略。
    3. DNS 解析：依次查询浏览器、操作系统等缓存；未命中时向递归 DNS 服务器查询，最终得到百度接入节点或 CDN 节点的 IPv4/IPv6 地址。
    4. 寻找网络路径：主机根据路由表选择出口。目标不在本地网络时，会通过 ARP 或 IPv6 邻居发现获得网关的链路层地址，数据经过路由器、NAT 和运营商网络到达目标。
    5. 建立连接：HTTP/1.1 或 HTTP/2 通常先进行 TCP 三次握手；使用 HTTPS 时再进行 TLS 握手，验证证书并协商会话密钥与应用层协议。若使用 HTTP/3，则通过 UDP 上的 QUIC 完成连接和 TLS 协商，不单独建立 TCP 连接。
    6. 发送 HTTP 请求：浏览器发送请求行或相应协议帧、请求头和 Cookie 等信息。请求可能先到 CDN、负载均衡或反向代理，再由其访问后端服务和缓存。
    7. 接收 HTTP 响应：服务端返回状态码、响应头和 HTML。内容可能经过压缩，并通过 TCP 或 QUIC 分段传输；传输层负责相应的可靠性、流量和拥塞控制。
    8. 解析和渲染：浏览器解析 HTML 构建 DOM，解析 CSS 构建 CSSOM，执行 JavaScript，生成渲染树并完成布局、绘制和合成。解析期间还会并发请求 CSS、JavaScript、图片和字体等子资源。

    实际抓包时不一定能完整看到上述每一步，例如 DNS 和 TLS 可能命中缓存、连接可能被复用，页面也可能主要由 Service Worker 返回。

    网络故障排查

    1. 网页一直很慢、处于转圈状态，应从哪些角度定位问题？

    我会先确定“慢在哪个阶段”，再沿请求链路逐层缩小范围，而不是先猜服务器性能问题。浏览器开发者工具的 Network 瀑布图通常是第一手证据，可以区分排队、DNS、建连、TLS、等待首字节和内容下载时间。

    1. 先明确范围：是单个用户、单个地区还是所有用户；只影响某个页面、某个接口还是整个站点；问题是持续发生还是偶发。还要确认客户端网络、浏览器和设备是否有共同特征。
    2. 客户端与前端：检查浏览器控制台错误、主线程长任务、JavaScript 死循环、资源体积、请求并发、缓存命中和第三方脚本。如果网络请求已经完成但页面仍转圈，重点看前端状态和渲染逻辑。
    3. DNS 与连接：查看 DNS 是否解析缓慢或错误，TCP/QUIC 建连和 TLS 握手是否耗时，是否存在丢包、重传、代理或 IPv4/IPv6 路径差异。可用 curl 的分阶段耗时、dig、mtr 以及必要时的抓包辅助判断。
    4. HTTP 传输：检查状态码、重定向次数、TTFB、响应体大小、压缩、协议版本和连接复用。如果 TTFB 很快但下载慢，更像带宽、丢包或响应过大；如果 TTFB 很慢，更应检查服务端处理链路。
    5. 网关和服务端：结合负载均衡、Nginx 和应用访问日志定位排队时间与处理时间，检查 CPU、内存、GC、线程池、连接池、磁盘 I/O 和限流情况。
    6. 下游依赖：通过链路追踪和指标检查数据库慢查询、缓存穿透、RPC 超时、第三方接口等，确认是哪一段拉长了总耗时。

    最后应使用同一请求的时间戳、请求 ID 或 Trace ID 关联浏览器、网关、应用和下游日志。只有拿到各阶段耗时，才能判断是网络、前端还是后端问题。

    2. Server A 和 Server B 之间如何判断连接正常？出错后怎么办？

    判断两个服务器通信是否正常，要验证到业务协议这一层，ping 成功只能说明部分 ICMP 网络可达，不能证明目标端口和服务可用。

    我通常按以下层次检查：

    1. 地址与路由：确认 A 解析出的 B 地址正确，并检查路由是否可达；ping 或 traceroute 只能作为辅助，因为 ICMP 可能被禁用。
    2. 传输层：在 A 上对 B 的目标 IP 和端口执行 TCP 连接测试，例如使用 nc，并在 B 上确认进程确实监听了正确地址和端口。
    3. TLS 和应用层：通过 curl、RPC 健康检查或真实的轻量请求验证 TLS 证书、协议响应和业务状态，不能只看 TCP 三次握手成功。
    4. 持续连接：对于长连接，可结合应用心跳、读写超时和 TCP Keepalive 发现失效连接。TCP Keepalive 只能检查连接路径是否仍可用，不能代替业务健康检查。

    发生错误后，应设置明确的连接、读取和总超时，记录目标地址、错误码、耗时及 Trace ID，并根据错误类型处理。瞬时网络故障可以使用带指数退避和随机抖动的有限重试，但写操作必须考虑幂等；持续故障应通过熔断、降级、切换健康实例和告警避免请求堆积。最终结合两端日志、连接状态、负载均衡健康检查和抓包定位根因。

    3. 服务端正常启动，但客户端请求不到，可能有哪些原因？如何排查？

    “进程已经启动”只说明程序在运行，不代表它监听正确端口、网络路径可达或应用接口正常。我会按由近到远、由底层到应用层的顺序排查。

    常见原因包括：

    • 服务只绑定了 127.0.0.1，监听端口错误，或启动后实际没有成功监听。
    • 客户端使用了错误的域名、IP、端口或协议，DNS 缓存和解析记录不一致。
    • 主机防火墙、云安全组、ACL、容器端口映射、Kubernetes Service/Ingress 或 NAT 配置阻断流量。
    • 路由不通、回程路由异常、代理配置错误，或者 IPv4 与 IPv6 路径不一致。
    • Nginx、负载均衡没有正确转发，健康检查失败，服务实例未加入可用节点。
    • TLS 证书、SNI、协议版本不匹配，导致连接建立后在 TLS 阶段失败。
    • 服务线程池或连接池耗尽、依赖阻塞、过载限流，端口虽然可连但请求超时或返回错误。
    • 鉴权、Host、路径或请求方法不符合接口要求，表现为 401、403、404、405 等应用层错误。

    排查时先在服务端检查监听地址和端口，再从服务端本机访问回环地址和实际网卡地址。随后从客户端核对 DNS，用端口连接工具判断 TCP 是否可达，再用 curl -v 等工具观察 TLS、请求头、状态码和各阶段耗时。并同步检查防火墙、网关、应用日志和指标；如果仍不能定位，可在客户端、中间节点或服务端抓包，判断请求到达了哪里以及响应是否沿原路径返回。

    4. 服务器 ping 不通但 HTTP 能请求成功，会出现这种情况吗？原因是什么？

    会，而且比较常见。ping 使用 ICMP Echo，HTTP 通常使用 TCP，HTTP/3 则使用 UDP 上的 QUIC；它们不是同一种协议。只要 HTTP 实际使用的目标地址和端口可达，ICMP 不通并不妨碍 HTTP 成功。

    可能原因包括：

    • 服务器、防火墙、安全组或运营商禁止或限速 ICMP Echo，但允许 TCP 80、443 或相应 UDP 流量。
    • 服务器在高负载时降低 ICMP 响应优先级，业务端口仍能正常处理请求。
    • HTTP 请求经过代理、VPN、CDN 或负载均衡，ping 的却是域名解析出的另一地址或另一条网络路径。
    • ping 和 HTTP 分别使用了 IPv4、IPv6，或者 DNS 在不同时间、不同网络环境返回了不同节点。
    • 中间设备只过滤 ICMP，或不返回 TTL 超时等 ICMP 报文。

    因此不能用 ping 作为 HTTP 服务是否可用的唯一依据。应核对两次测试的实际目标 IP 和协议，并直接测试目标端口、执行 HTTP 请求及检查 TLS/状态码。反过来，ping 成功也只能说明 ICMP 路径可用，不能证明 HTTP 服务已经监听并能正确处理请求。
