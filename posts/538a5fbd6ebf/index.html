网络场景

浏览器访问流程

1. 描述一下打开百度首页后发生的网络过程？

浏览器打开百度首页，首先解析 URL，然后通过 DNS 查询获得服务器 IP。接着根据路由找到网关：如果目标不在本地网络，会通过 ARP 获取网关的 MAC 地址。之后与服务器建立 TCP 连接；如果使用 HTTPS，还要进行 TLS 握手，验证证书并协商加密密钥。
连接建立后，浏览器发送 HTTP 请求，服务器返回 HTML。浏览器解析 HTML，再请求 CSS、JavaScript、图片等资源，构建页面并渲染。传输过程中，数据会经过路由器、运营商网络、负载均衡或 CDN，最后到达服务器。连接使用完后会被复用，或者通过 TCP 挥手关闭。

URL 解析 → DNS 得到 IP → 路由和 ARP → TCP/QUIC 建连 → TLS 握手 → HTTP 请求响应 → 浏览器解析渲染 → 连接复用或关闭。

网络故障排查

1. 网页一直很慢、处于转圈状态，应从哪些角度定位问题？

我会先用浏览器开发者工具的 Network 面板，确定是哪个请求慢，以及时间花在 DNS、TCP/TLS 建连、等待服务器响应还是资源下载。
如果 DNS 或建连慢，就检查解析、延迟、丢包、代理和网络链路；如果等待首字节时间长，就重点查看服务端日志、CPU、线程池、数据库、缓存和下游服务；如果下载慢，就检查带宽和资源大小；如果请求都完成了页面还在转圈，就检查前端 JavaScript、主线程阻塞和渲染问题。
总体思路是先定位慢在哪个阶段，再沿链路逐层排查。

先用 Network 面板划分问题阶段，再判断是客户端、网络、服务端还是前端渲染问题。

2. Server A 和 Server B 之间如何判断连接正常？出错后怎么办？

判断两个服务器通信是否正常，要验证到业务协议这一层，ping 成功只能说明部分 ICMP 网络可达，不能证明目标端口和服务可用。

我通常按以下层次检查：

  1. 地址与路由：确认 A 解析出的 B 地址正确，并检查路由是否可达；ping 或 traceroute 只能作为辅助，因为 ICMP 可能被禁用。
  2. 传输层：在 A 上对 B 的目标 IP 和端口执行 TCP 连接测试，例如使用 nc，并在 B 上确认进程确实监听了正确地址和端口。
  3. TLS 和应用层：通过 curl、RPC 健康检查或真实的轻量请求验证 TLS 证书、协议响应和业务状态，不能只看 TCP 三次握手成功。
  4. 持续连接：对于长连接，可结合应用心跳、读写超时和 TCP Keepalive 发现失效连接。TCP Keepalive 只能检查连接路径是否仍可用，不能代替业务健康检查。

发生错误后，应设置明确的连接、读取和总超时，记录目标地址、错误码、耗时及 Trace ID，并根据错误类型处理。瞬时网络故障可以使用带指数退避和随机抖动的有限重试，但写操作必须考虑幂等；持续故障应通过熔断、降级、切换健康实例和告警避免请求堆积。最终结合两端日志、连接状态、负载均衡健康检查和抓包定位根因。

3. 服务端正常启动，但客户端请求不到，可能有哪些原因？如何排查？

我会按照从服务端到客户端的链路逐层排查。首先看进程和日志，确认服务确实正常运行；再用 ss 查看端口是否监听，以及是否只绑定了 127.0.0.1。然后在服务端本机用 curl 测试：如果本机也访问不了，重点排查应用和监听配置；如果本机能访问、远程不能，就检查防火墙、安全组、路由、容器端口映射以及网关或负载均衡。
如果端口能连通但请求仍失败，再检查 IP、端口、协议、域名、TLS、请求路径和应用日志。

先查进程和监听，再用本机访问划分应用问题与网络问题，最后沿防火墙、容器、网关到客户端逐层排查。

4. 服务器 ping 不通但 HTTP 能请求成功，会出现这种情况吗？原因是什么？

ping 使用的是 ICMP 协议，而 HTTP 使用 TCP 协议，两者走的协议和安全策略可能不同。服务器、防火墙或云安全组可能禁止或丢弃 ICMP 回显报文，但允许 TCP 的 80 或 443 端口，所以会出现 ping 不通、HTTP 却能正常访问的情况。
另外，HTTP 请求可能实际访问的是 CDN、反向代理或负载均衡，而不是后端服务器本身。

ping 不通只能说明 ICMP 没有得到响应，不能直接说明服务器不可达；判断 Web 服务是否正常，应测试实际的 HTTP 端口和请求。
