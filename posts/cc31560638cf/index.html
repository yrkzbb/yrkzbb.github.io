    主从复制

    1. MySQL 主从同步的原理是什么？

    MySQL 主从复制的核心是：主库把已提交的数据变更记录到 binlog，从库拉取这些事件并重放，使数据逐步与主库一致。默认复制通常是异步的，所以主库提交成功时，从库可能还没有应用完成。

    主要流程有三步：

    1. 主库提交事务并写入 binlog。
    2. 从库的接收线程连接主库，获取 binlog 事件并写入本地 relay log。
    3. 从库的协调线程和应用线程读取 relay log，并行或串行重放事务。

    复制可以用于读扩展、备份和故障切换，但它不自动等于高可用。还需要处理复制延迟、故障检测、主库切换、数据一致性和脑裂等问题。对刚写完就必须读到最新值的请求，不能无条件路由到异步从库。

    2. 主从复制延迟有哪些处理方法？

    我会先判断延迟发生在“日志传输”还是“从库应用”阶段，再决定优化方式，而不是直接把所有查询切回主库。

    常见处理方法有：

    1. 监控复制位点、GTID 和应用线程状态，结合网络、磁盘、CPU、锁等待定位瓶颈。
    2. 避免超大事务、长事务、一次更新过多行以及耗时 DDL，减少从库单次重放压力。
    3. 配置并行复制并合理增加应用线程；同时保证从库硬件、参数和索引能够支撑重放与查询负载。
    4. 降低从库上的重查询干扰，必要时拆分只读副本与容灾副本。
    5. 对强一致读，短期路由到主库，或等待指定 GTID 已在从库执行后再读取；普通读仍可根据容忍度访问从库。

    半同步复制主要降低主库故障时事务完全未传到任何从库的风险，并不保证从库已经应用完成，所以不能单独解决查询延迟问题。

    数据拆分

    1. 分表和分库是什么？有什么区别？

    分表是把一张逻辑大表拆成多张物理表，重点解决单表数据量、索引体积和查询维护压力；分库是把数据拆到多个数据库或实例，重点分散连接、CPU、内存、I/O 和存储压力，实现更强的水平扩展。

    两者都可以按不同方向拆分：

    • 水平拆分：结构不变，按用户 ID、时间或哈希等规则拆分数据行。
    • 垂直拆分：按业务模块拆库，或把大表中访问频率、长度差异明显的字段拆到不同表。

    分表后通常仍可在同一数据库内查询，跨表操作复杂一些；分库后还需要路由到正确实例，跨库事务、关联查询、全局唯一 ID、扩容迁移和运维成本都会明显增加。因此不应只因为数据量达到某个固定值就分库分表，而要先确认单表索引和 SQL 已合理，且单机资源或吞吐确实成为瓶颈。

    2. 如何实现分库分表？

    实现分库分表的核心是确定拆分规则，并让应用能够把请求路由到正确的库和表。我通常会按下面几步实施：

    1. 确认拆分目标：先判断瓶颈来自单表数据量还是单实例资源。单表过大可以先分表，实例的连接、CPU、I/O 或存储达到瓶颈时再考虑分库。
    2. 选择分片键和规则：选择查询中经常携带、分布较均匀且不易修改的字段，例如 user_id。可以按范围拆分，也可以通过 user_id % 分片数 或一致性哈希拆分。范围分片便于扩容和范围查询，但容易产生热点；哈希分片较均匀，但范围查询和扩容更复杂。
    3. 实现数据路由：可以在应用层自行路由，也可以使用 ShardingSphere 等中间件。路由规则必须统一，避免同一条数据被写入不同分片。
    4. 处理分布式问题：使用雪花算法等生成全局唯一 ID；尽量避免跨分片 JOIN、分页和事务，把关联数据放在同一分片。确实需要强一致时，再考虑分布式事务或通过业务补偿保证最终一致性。
    5. 平滑迁移和验证：先创建分片并同步历史数据，再通过双写或增量日志同步新数据，校验一致后逐步切换读写流量，并保留回滚方案。

    设计时还要提前考虑扩容。直接取模会导致增加分片时大量数据重新映射，可以预先规划更多逻辑分片，再把逻辑分片映射到物理库，扩容时只迁移部分逻辑分片。

    3. 存储拆分后如何解决唯一主键问题？

    分库分表后不能继续依赖各分片独立的自增主键，否则不同分片可能生成相同 ID。通常要使用全局唯一 ID，常见方案有：

    1. 数据库号段：由一个服务批量申请一段 ID，各节点在内存中递增使用。性能较好且 ID 趋势递增，但要保证号段服务高可用。
    2. 雪花算法：ID 由时间戳、节点编号和序列号组成，各节点可以独立生成。性能高、趋势递增，但要正确分配节点编号并处理时钟回拨。
    3. UUID：生成简单且不依赖中心节点，但随机 UUID 较长、无序，不适合直接作为 InnoDB 聚簇索引。必须使用时可选择 UUIDv7，并用 BINARY(16) 存储。
