消息队列

消息队列场景

1. 什么是消息队列？

消息队列是一种异步通信中间件：生产者把消息发送给消息代理服务（Broker），Broker 暂存消息并按规则投递给消费者，消费者再按自己的处理能力进行消费。

Broker 可以理解为生产者和消费者之间的“中转站”，通常由一台或多台服务器组成。Kafka、RocketMQ 和 RabbitMQ 中负责接收、存储、路由或投递消息的服务端节点，都可以称为 Broker。

它把消息的生产和处理解耦，双方不必同时在线，也不需要直接依赖彼此地址。常见模型有点对点和发布订阅，具体产品通常还提供持久化、确认、重试、顺序消费和消息回溯等能力。

2. 为什么需要消息队列？

主要是为了解耦、异步和削峰填谷。

  • 解耦：订单系统只发布“订单已创建”事件，不需要逐一调用库存、积分和通知系统。
  • 异步：把非核心链路放到后台处理，缩短主请求响应时间。
  • 削峰：Broker 暂存突发流量，消费者按稳定速率处理，保护数据库等下游系统。

3. 消息队列有什么缺点？#

第一，会增加系统复杂度。引入消息队列后，需要额外处理消息丢失、重复消费、顺序错乱和消息积压等问题。

第二，会增加数据一致性处理难度。消息通常是异步消费的，一般只能保证最终一致性，所以还要设计幂等、重试和补偿机制。

第三，会增加运维成本和故障点。如果 Broker 出现故障，消息的生产和消费都可能受影响，因此需要部署高可用集群，并做好监控和告警。

4. 消息队列怎么选型？

消息队列选型不能只比较谁的吞吐量高，我一般会先看业务场景，再从吞吐量和延迟、可靠性、消息顺序、事务与延迟消息、路由能力、消息回溯以及团队运维成本几个维度综合判断。

如果是日志采集、埋点、CDC 或实时流处理，需要高吞吐、消息长期保留和按 offset 回放，我会倾向选择 Kafka。如果是订单、支付等业务消息，需要事务消息、延迟消息、顺序消息和失败重试，我会倾向选择 RocketMQ。如果业务规模中小，但需要灵活的交换机路由、较低延迟和 AMQP 生态，我会考虑 RabbitMQ。ActiveMQ 目前更多见于已有的 JMS 项目，新项目通常会优先评估前面三种。

例如秒杀场景更关注峰值吞吐和削峰能力，可以重点评估 Kafka 或 RocketMQ；金融或交易场景除了性能，还要重点验证持久化、副本、确认、幂等和容灾能力。

最后我会使用真实消息大小、峰值流量、分区或队列数量以及实际可靠性配置进行压测。因为固定的“每秒多少条”“能建多少 Topic”并不是产品的绝对指标，会受到硬件、版本、消息大小和部署配置影响，所以不存在适合所有场景的消息队列。

5. 消息队列使用场景有哪些？

常见场景包括：

  • 用户注册后异步发送邮件、短信和初始化数据。
  • 秒杀、支付回调等峰值流量缓冲。
  • 订单事件驱动库存、物流、积分等系统。
  • 订单超时关闭、定时提醒等延迟任务。
  • 数据库变更、日志和埋点进入数据平台。
  • 跨系统最终一致性和失败重试。

6. 消息重复消费怎么解决？

消息重复消费一般通过消费端幂等解决。

因为消息队列通常采用至少一次投递，如果生产者发送超时后重试，或者消费者处理成功但 ACK 丢失，消息都可能被再次投递。

具体实现时，我会给消息设置业务唯一标识，比如订单 ID，并通过数据库唯一索引、去重表或者状态条件更新，判断该业务是否已经处理过。

7. 消息丢失怎么解决的？

要分生产、Broker 和消费三个阶段治理：

  • 生产端：等待 Broker 确认，失败时有限重试；对关键消息可配合本地消息表或事务消息。
  • Broker：开启持久化和多副本，选择满足可靠性要求的同步策略，并监控副本状态和磁盘。
  • 消费端：业务处理成功后再确认；失败则重试，超过阈值进入死信队列或人工补偿。

同时要有消息轨迹、对账和补偿任务。

8. 使用消息队列还应该注意哪些问题？

除了重复、丢失和顺序，我还会关注：

  • 消息体只放必要数据，控制大小，并设计可兼容的消息版本。
  • 设置重试上限、退避和死信处理，避免毒消息无限重试。
  • 做生产与消费限流，防止积压恢复时冲垮下游。
  • 规划 Topic、分区或队列数量，避免热点键。
  • 做好权限、传输加密和敏感数据治理。

9. 消息队列的可靠性、顺序性怎么保证？

可靠性依赖端到端协作：生产端确认和重试、Broker 持久化及多副本、消费成功后确认，再配合幂等、死信和对账补偿。

顺序性通常只能在一个分区或队列内保证。生产者应按 orderId 等业务键路由到同一分区，消费者对该分区串行处理，并避免异步线程导致完成顺序变化。

10. 如何保证幂等写？

幂等性是指同一操作的多次执行对系统状态的影响与一次执行结果一致。例如，支付接口若因网络重试被多次调用，最终应确保仅扣款一次。实现幂等写的核心方案：

  • 唯一标识（幂等键）：客户端为每个请求生成全局唯一 ID（如 UUID、业务主键），服务端校验该 ID 是否已处理，适用场景：接口调用、消息消费等。
  • 数据库事务 + 乐观锁：通过版本号或状态字段控制并发更新，确保多次更新等同于单次操作，适用场景：数据库记录更新（如余额扣减、订单状态变更）。
  • 数据库唯一约束：利用数据库唯一索引防止重复数据写入，适用场景：数据插入（如订单创建）。
  • 分布式锁：通过锁机制保证同一时刻仅有一个请求执行关键操作，适用场景：高并发下的资源抢夺（如秒杀）。
  • 消息去重：消息队列生产者为每条消息生成唯一的消息 ID，消费者处理消息前先检查该消息 ID 是否已经处理过，如果已经处理过则丢弃该消息。

11. 如何处理消息队列的消息积压问题？

消息积压本质上是生产速度大于消费速度。我会先查看消费延迟、失败率和各分区积压情况，判断是消费者异常、处理逻辑慢、下游故障，还是分区并行度不足。

修复问题后，优先优化批量消费、慢 SQL 和耗时调用；在分区数和下游容量允许的情况下，再增加消费者实例或消费线程。

如果已经积压了几百万条消息，可以临时创建分区更多的新 Topic，把积压消息快速转发过去，再增加消费者并行处理。积压处理完成后恢复原来的架构。

12. 如何保证数据一致性，事务消息如何实现？

消息队列场景一般保证的是最终一致性，常见方案有事务消息和本地消息表。

以 RocketMQ 事务消息为例：生产者先发送一条消费者不可见的半消息，Broker 保存成功后，生产者执行本地事务，再根据事务结果提交或回滚消息。如果 Broker 没收到结果，会回查生产者的本地事务状态。提交后消息才会投递，回滚则不会投递。

事务消息主要保证本地事务和消息发送的一致性，不能保证下游业务一定成功。所以消费者还需要通过幂等、失败重试、死信队列和补偿机制，最终达到数据一致

13. 消息队列是参考哪种设计模式？

核心思想主要对应生产者—消费者模式和发布—订阅模式。

生产者—消费者模式通过缓冲队列协调两端速度；发布—订阅模式让一条事件被多个相互独立的订阅者接收。它还体现了观察者模式的思想，但消息中间件通常通过 Broker 异步传递并持久化消息，生产者和消费者不直接持有彼此引用，因此不能简单等同于进程内观察者模式。

14. 让你写一个消息队列，该如何进行架构设计？

如果让我从零设计一个消息队列，我会先确定吞吐量、延迟、消息大小、保留时间、顺序范围和投递语义，再围绕下面八个部分展开。

设计一个消息队列的架构思维导图

图中的设计思路可以整理为以下八点：

  1. 消息队列的整体流程：Producer 发送消息给 Broker，Broker 存储消息后再发送给 Consumer 消费，Consumer 完成处理后回复消费确认。
  2. RPC 如何设计：Producer 向 Broker 发送消息、Broker 向 Consumer 投递消息，至少涉及两次 RPC。设计时可以参考 Dubbo 等开源 RPC 框架，重点考虑服务发现、序列化协议、连接管理、超时与重试。
  3. Broker 如何持久化：需要决定消息存放在文件系统还是数据库，并提前设计消息堆积后的存储、清理、限流和扩容策略。
  4. 消费关系如何保存：需要明确采用点对点还是广播方式；广播订阅关系及消费进度等元数据，可以由 ZooKeeper、Config Server 或自研高可用控制面维护。
  5. 消息可靠性如何保证：发送、存储和消费确认都要有可靠性机制；消息重复时，通过业务唯一键、唯一索引、去重表或状态机实现幂等。
  6. 消息队列如何保证高可用：可以参考 Kafka 的多副本机制，Partition 由 Leader 对外服务、Follower 同步数据；Broker 宕机后重新选举 Leader 并恢复服务。
  7. 消息事务特性：消息发送要与本地业务处于同一事务语义中。可以先将消息写入本地消息表，再投递给服务端，成功后删除或标记完成；定时任务扫描本地消息表并补偿发送失败的记录。
  8. MQ 的伸缩性和可扩展性：可以参考 Kafka 的 Broker → Topic → Partition 模型，每个 Partition 保存一部分数据。资源不足时增加 Partition 和 Broker，完成数据迁移与重新均衡，以存放更多数据并提高吞吐量。

消息队列架构设计文字笔记

15. 如何设计任务取消、超时、重试和死信队列？

我会把它设计成一套持久化的任务状态机，而不是只依赖消息队列里的消息状态。任务表至少保存 task_id、业务幂等键、状态、重试次数、最大重试次数、截止时间和取消标记，状态可以定义为 PENDING、RUNNING、SUCCEEDED、FAILED、CANCELLED、TIMED_OUT 和 DEAD。Worker 对状态的修改要使用条件更新，避免取消、完成和超时并发覆盖。

任务取消通常采用协作式取消。客户端提交取消请求后，服务端原子地设置取消标记；尚未执行的任务可以从逻辑上直接取消，正在执行的 Worker 则在调用模型前后、工具调用之间等安全点检查标记，主动停止并释放资源。已经产生不可逆副作用的步骤不能靠取消恢复，需要幂等或补偿操作。强制终止进程只能作为兜底，因为它可能留下未提交事务、子进程或外部请求。

超时需要分层设置：队列等待超时限制任务排队时间，任务总超时限制整个执行时长，模型、数据库和 HTTP 调用还应分别设置连接与读取超时。软超时用于通知任务主动清理，硬超时用于隔离失控任务。需要注意，调用方收到超时只代表它不再等待，不代表下游执行已经停止，因此还要传播截止时间或取消信号，并防止超时任务稍后写入过期结果。

重试只针对网络抖动、限流和临时依赖故障等可恢复错误；参数错误、权限错误和确定性的业务失败应直接失败。重试要设置最大次数，使用指数退避并加入随机抖动，例如 1s、2s、4s，同时设置总重试时间预算。每次执行都携带相同的业务幂等键，通过唯一索引、状态条件更新或结果表避免重复扣费、重复发消息等副作用。

任务超过最大重试次数，或被识别为无法自动处理的“毒任务”后，进入死信队列。死信消息应保留原始载荷引用、异常类型、错误摘要、重试历史和 Trace ID，并配置积压量与增长速率告警。死信不能无限自动回灌；应先修复代码、数据或依赖问题，再由人工或受控工具重放，重放过程仍然要幂等。

在 Python Agent 场景中，API 可以先返回 task_id，Worker 从 Celery、RabbitMQ 或其他队列取任务，状态保存在数据库等可靠存储中。消息 ACK 应在任务状态安全落库后完成；Worker 宕机导致消息重投时，由幂等键和状态机保证不会重复产生业务结果。这样即使发生重复投递、取消与完成竞争、超时后继续执行等情况，最终状态也有明确的判断依据。
