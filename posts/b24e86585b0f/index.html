锁

线程同步与锁

1. 为什么并发执行线程要加锁？

核心原因是：多个线程并发访问共享可变数据时，一组逻辑操作往往不是原子的。如果不进行同步，线程执行步骤可能交错，产生竞态条件，导致数据丢失、状态不一致，或者一个线程看不到另一个线程的最新修改。

例如，count++ 通常包含读取、加一和写回多个步骤。两个线程同时执行时，都可能读取到相同的旧值，最终只增加一次。对这段操作加互斥锁，可以让同一时刻只有一个线程进入临界区，同时建立必要的内存可见性保证。

但并发执行不代表一定要加锁。如果线程不共享可变状态，或者使用不可变对象、线程局部数据、消息传递、原子变量及正确设计的无锁结构，就可以不使用传统互斥锁。锁的粒度也要合理：范围太大会降低并发度，范围太小则可能无法保护完整的不变量。

2. 自旋锁是什么？应用在哪些场景？

自旋锁是一种获取失败后不立即阻塞或睡眠，而是在 CPU 上循环检查锁状态的锁。它避免了线程睡眠、唤醒和调度切换的开销，但等待期间会持续消耗 CPU。

它适合以下场景：

  • 临界区很短，锁预计很快就会释放；
  • 锁竞争较少；
  • 多核环境下，持锁线程可以在另一个 CPU 核心上继续运行并及时释放锁；
  • 内核、中断上下文等不适合睡眠的代码区域；
  • 用户态同步库中的短时间自适应等待，即先自旋几次，失败后再阻塞。

如果临界区较长、竞争激烈，或者运行环境只有一个可用 CPU 核心，长时间自旋会浪费 CPU，阻塞式互斥锁通常更合适。持有自旋锁时一般也不应该执行可能阻塞或耗时较长的操作。

3. 乐观锁和悲观锁有什么区别？

核心区别是对冲突概率的假设不同：悲观锁假设冲突容易发生，访问共享数据前先加锁；乐观锁假设冲突较少，先执行操作，提交更新时再检测冲突。

  • 悲观锁通常使用互斥锁、读写锁或数据库行锁实现。它能直接阻止其他执行者修改数据，适合冲突频繁、临界区较长，或者冲突后回滚代价较高的场景；代价是可能发生阻塞、上下文切换和死锁。
  • 乐观锁通常使用版本号、时间戳或 CAS 实现。更新时比较数据是否仍是读取时的版本，成功则提交，失败则重试或返回冲突。它适合读多写少、冲突概率低的场景；竞争激烈时频繁重试可能浪费 CPU，并可能出现饥饿问题。

乐观锁不等于完全“无锁”，具体实现仍可能在底层使用锁；CAS 方案还要考虑 ABA 问题。选择哪一种不能只看名称，应结合冲突率、重试成本、临界区长度和延迟要求判断。

死锁

1. 死锁发生的条件是什么？

死锁是多个线程或进程互相等待对方持有的资源，导致所有参与者都无法继续执行。经典的 Coffman 四个必要条件是：

  1. 互斥条件：资源同一时刻只能被一个执行者占用；
  2. 请求并保持条件：已经持有资源的执行者继续请求其他资源，并且等待时不释放现有资源；
  3. 不可剥夺条件：资源不能被系统强制收回，只能由持有者主动释放；
  4. 循环等待条件：存在一个执行者等待环，每个执行者都在等待下一个执行者持有的资源。

四个条件同时成立才可能发生死锁，破坏其中任意一个条件都可以从机制上防止死锁。

2. 如何避免死锁？

实践中最常用的方法是规定全局一致的加锁顺序，破坏循环等待条件。例如所有线程都必须先获取锁 A，再获取锁 B，不能反向获取。

还可以采用以下措施：

  • 尽量一次申请所需资源，避免持有部分资源时继续等待其他资源；
  • 缩小临界区，不在持锁期间执行网络 I/O、磁盘 I/O 等不可控的阻塞操作；
  • 使用 tryLock 或带超时的加锁，获取失败时释放已经持有的锁，经过退避后重试；
  • 减少嵌套锁，优先使用更高层的并发容器或消息传递；
  • 在资源需求可预知时，使用银行家算法等方法，只批准不会让系统进入不安全状态的申请；
  • 对无法完全预防的系统建立死锁检测与恢复机制，例如检测等待图中的环并终止或回滚部分任务。

需要区分的是：超时和检测并没有从根本上阻止死锁产生，而是让系统能够退出等待或在发生后恢复。

3. 讲一下银行家算法。

银行家算法是一种死锁避免算法。它不会简单地满足所有资源请求，而是在分配前进行安全性检查：只有分配后系统仍存在一个能让所有进程依次完成的安全序列，才批准这次请求，否则让申请者继续等待。

算法通常维护以下数据：

  • Available：当前各类资源的可用数量；
  • Max：每个进程对各类资源的最大需求；
  • Allocation：已经分配给每个进程的资源；
  • Need：每个进程仍需要的资源，满足 Need = Max - Allocation。

收到进程的 Request 后，先检查 Request <= Need 且 Request <= Available。然后假设完成这次分配，再执行安全性检查：从剩余资源中寻找一个满足 Need <= Work 的未完成进程，假设它执行完成并释放其 Allocation，不断重复。如果最终所有进程都能完成，说明存在安全序列，系统处于安全状态，可以正式分配；否则撤销试分配并让进程等待。

安全状态表示当前存在避免死锁的执行顺序；不安全状态不等于已经发生死锁，只表示继续运行存在死锁风险。银行家算法要求事先知道最大资源需求，还要反复进行安全性检查，因此更适合资源种类和数量相对固定、最大需求可预测的场景，在通用操作系统中并不常直接用于普通进程调度。
