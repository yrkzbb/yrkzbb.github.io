    应用层

    HTTP、HTTPS 与网络通信

    1. HTTP 和 HTTPS 的区别？

    核心区别是：HTTPS 不是一种完全独立的新协议，而是运行在 TLS 之上的 HTTP。HTTP 数据通常以明文传输；HTTPS 通过 TLS 提供加密、完整性校验和身份认证。

    • 安全性：HTTP 报文可能被窃听或篡改；HTTPS 可以降低窃听、篡改和冒充服务器的风险。
    • 默认端口：HTTP 通常使用 80，HTTPS 通常使用 443。
    • 连接过程：HTTP 建立 TCP 连接后即可传输 HTTP 报文；传统 HTTPS 在 TCP 连接之上还要进行 TLS 握手。
    • 证书：HTTPS 协议需要向 CA 申请数字证书，来保证服务器的身份是可信的。

    2. HTTPS 的握手过程？

    HTTPS 一般先建立底层连接，再进行 TLS 握手，握手成功后才传输加密的 HTTP 数据。以目前常见的 TLS 1.3 完整握手为例：

    1. 客户端发送 ClientHello，其中包含支持的 TLS 版本、密码套件、随机数等等。
    2. 服务端回复 ServerHello，选择 TLS 版本和密码套件，并返回自己的密钥交换参数。双方据此计算共享密钥。
    3. 服务端发送证书、证书验证签名以及握手完成消息，证明自己持有证书对应的私钥。
    4. 客户端校验证书链、有效期、域名、吊销状态等，并验证服务端签名。
    5. 客户端发送握手完成消息。双方确认此前的握手消息未被篡改，并派生出会话密钥。
    6. 后续 HTTP 报文使用对称加密传输，同时进行完整性保护。

    TLS 1.2 的消息顺序和密钥交换方式有所不同，完整握手通常需要更多往返；TLS 1.3 简化了握手，并移除了静态 RSA 密钥交换等旧方案。若命中会话恢复，握手还可以进一步缩短。

    3. HTTPS 是如何防范中间人攻击的？

    HTTPS 主要通过“证书身份认证、密钥协商和完整性校验”防范中间人攻击，而不仅仅是对数据加密。

    客户端会验证服务端证书是否由受信任的 CA 签发、证书中的域名是否与访问目标一致、证书是否有效。攻击者即使截获并转发握手消息，通常也没有合法证书对应的私钥，无法完成有效签名，也就不能冒充真实服务器。

    握手完成后，双方使用协商出的会话密钥加密数据，并用认证加密算法校验完整性。攻击者既难以读取明文，也无法在不被发现的情况下修改报文。

    不过 HTTPS 并非在任何条件下都能阻止中间人攻击。例如用户主动忽略证书警告、客户端信任了攻击者安装的根证书、CA 或服务端私钥失陷，身份认证就可能失效。因此客户端必须正确校验证书，敏感场景还可以使用证书固定等额外措施。

    4. HTTP/1.1 和 HTTP/2 的区别是什么？

    HTTP/2 的主要改进是采用二进制分帧，并在一条连接上多路复用多个请求和响应，从而减少 HTTP/1.1 并发传输时对多条 TCP 连接的依赖。两者的请求方法、状态码、URI 等核心语义基本一致。

    • 报文格式：HTTP/1.1 使用文本格式；HTTP/2 将消息拆成二进制帧。
    • 并发方式：HTTP/1.1 的同一连接通常按顺序处理响应。虽然有管线化机制，但兼容性和队头阻塞问题使其很少使用，浏览器一般通过多条连接并发。HTTP/2 可在一条连接中交错传输多个流。
    • 首部压缩：HTTP/1.1 的请求会重复携带许多首部；HTTP/2 使用 HPACK 压缩首部。
    • 请求优先级：HTTP/2 提供流优先级相关机制，但实际支持和效果取决于客户端、服务端的实现。
    • 服务器推送：HTTP/2 定义了 Server Push，不过实践收益有限，部分浏览器已不再支持。

    HTTP/2 仍基于 TCP，因此丢包时可能造成连接级的队头阻塞：一个 TCP 包丢失会影响同一连接上的所有 HTTP/2 流。HTTP/3 基于 QUIC，主要用于进一步解决这个问题。

    5. HTTP 建立 TCP 连接后，在什么情况下会中断？

    TCP 连接可能正常关闭，也可能异常中断，不能只由 HTTP 协议单方面决定。

    • HTTP/1.0 默认通常是短连接，请求响应结束后关闭；HTTP/1.1 默认使用持久连接，但任一方可以发送 Connection: close，在本次响应完成后关闭连接。
    • 客户端、服务端或代理设置了空闲超时、请求超时、最大连接时长或单连接最大请求数，达到条件后会关闭连接。
    • 应用进程退出、服务器重启、客户端关闭页面或取消请求时，连接可能被关闭。
    • 网络断开、NAT 映射失效、防火墙清理连接，或者发生 TCP 重传超时，也可能使连接失效。
    • 收到 TCP RST、协议解析失败、TLS 错误或资源不足时，连接可能被异常终止。

    正常关闭一般通过 TCP 的 FIN/ACK 完成；异常终止常表现为 RST 或超时。HTTP/2 中还可以用 GOAWAY 表示不再接受新的流，但已有流是否完成要结合错误码和双方行为判断。

    6. HTTP、Socket 和 TCP 的区别？

    三者不在同一个抽象层次：HTTP 是应用层协议，TCP 是传输层协议，Socket 是操作系统提供给应用程序使用网络通信能力的编程接口或通信端点。

    • HTTP 规定请求、响应、方法、状态码和首部等应用数据的语义。
    • TCP 提供面向连接、可靠、有序的字节流传输，但不理解 HTTP 报文含义。
    • Socket 不是一种与 HTTP、TCP 并列的网络协议。程序可以通过 Socket API 创建 TCP 或 UDP 通信端点，执行连接、监听、收发数据等操作。

    例如传统 HTTP/1.1 通信中，应用通过 TCP Socket 建立连接，再在这条 TCP 字节流上传输 HTTP 报文。但 Socket 也可以承载自定义协议，HTTP/3 则基于 UDP 上的 QUIC，因此“HTTP 一定基于 TCP”并不严谨。

    7. HTTP 到底是不是无状态的？

    HTTP 协议本身是无状态的：每个请求原则上都应包含完成处理所需的信息，协议不会自动记住前一次请求对应的是谁、做过什么。

    但这不代表使用 HTTP 的应用不能保存状态。应用可以借助 Cookie、服务端 Session、Token、URL 参数或数据库，把多个独立请求关联到同一用户或会话。因此，“HTTP 无状态”描述的是协议默认的请求处理模型，不是说整个 Web 应用没有状态。

    另外，持久连接只是在多个请求之间复用底层连接，它与业务会话状态是两个概念。即使多个请求使用同一条 TCP 连接，HTTP 语义仍然可以是无状态的。

    8. 携带 Cookie 的 HTTP 请求是有状态还是无状态的？Cookie 是 HTTP 协议簇的一部分，为什么还说 HTTP 是无状态的？

    携带 Cookie 不会改变 HTTP 协议本身无状态的性质，但它可以让上层应用表现为“有会话状态”。关键在于区分协议是否自动保存上下文，以及应用是否显式携带状态标识。

    服务端通过响应头 Set-Cookie 让浏览器保存数据；之后浏览器按域名、路径、过期时间和安全属性等规则，在请求头 Cookie 中把相应数据重新发送给服务端。每次请求仍然是独立、完整的，服务端之所以能识别同一会话，是因为请求显式携带了 Cookie，而不是 HTTP 自动记住了之前的请求。

    Cookie 可以直接保存少量状态，也可以只保存一个会话标识，真正的会话数据存放在服务端。因此更准确的说法是：HTTP 是无状态协议，Cookie 是在 HTTP 首部之上建立和维持应用状态的一种机制。

    会话管理与身份认证

    1. Cookie 和 Session 有什么区别？

    核心区别是：Cookie 主要保存在客户端，Session 通常保存在服务端。两者经常配合使用，但不是同一个层次的概念。

    • 存储位置：Cookie 由浏览器保存；Session 数据一般保存在服务端内存、数据库或 Redis 中。
    • 传输方式：符合域名、路径等条件的 Cookie 会随 HTTP 请求自动发送。Session 本身不会发送给客户端，客户端通常只携带一个 session_id，服务端据此查找会话数据。
    • 容量和开销：Cookie 容量较小，且随请求传输会增加网络开销；Session 可存更多数据，但会占用服务端存储，并涉及过期清理和集群共享。
    • 安全性：Session 数据不直接暴露给客户端，但 session_id 一旦被盗仍可能造成会话劫持。Cookie 应根据场景设置 HttpOnly、Secure、SameSite 等属性，并全程使用 HTTPS。
    • 生命周期：Cookie 可设置过期时间；Session 的有效期由服务端控制，通常在超时、退出登录或服务端删除后失效。

    因此，敏感业务数据一般不直接放在 Cookie 中，常见做法是 Cookie 只保存随机且不可预测的会话标识，实际状态留在服务端。

    2. Token、Session 和 Cookie 有什么区别？

    Cookie 是客户端存储和自动传输数据的机制，Session 是服务端保存会话状态的方案，Token 则是客户端请求时携带的访问凭证。三者可以组合使用，并不是互斥关系。

    • Session 认证：登录后服务端创建 Session，客户端保存 session_id。后续请求携带该标识，服务端查询 Session 并确认用户身份。
    • Token 认证：服务端签发 Token，客户端后续提交 Token。Token 可以是无结构的随机字符串，也可以是 JWT；前者通常仍要到服务端存储中查询，JWT 则可以在验证签名后读取声明。
    • Cookie：既可以保存 session_id，也可以保存 Token。它解决的是浏览器如何存储和发送凭证，不直接决定服务端采用 Session 还是 Token 认证。

    例如“Cookie 与 Token 对比”并不完全严谨，因为 Token 也可以放进 Cookie。真正需要比较的通常是“服务端有状态的 Session 认证”和“自包含 Token 认证”。

    3. 如果客户端禁用了 Cookie，Session 还能用吗？

    能，但前提是通过其他方式把 Session 标识传给服务端。Session 数据在服务端，Cookie 只是浏览器传递 session_id 最常见的载体，所以禁用 Cookie 不等于服务端不能创建 Session。

    替代方式包括把会话标识放在自定义请求头、表单字段或 URL 中。不过 URL 重写容易让会话标识进入浏览器历史、日志和 Referer，还可能被复制分享，泄露风险较高；自定义请求头更适合可控的客户端，但普通页面跳转不便自动携带。

    如果系统完全依赖 Cookie 传递 session_id，而且没有实现替代机制，那么客户端禁用 Cookie 后就无法维持该 Session 会话。

    4. 把数据存到 localStorage，和 Cookie 有什么区别？

    最关键的区别是：Cookie 可以由浏览器按规则自动附加到 HTTP 请求中，localStorage 不会自动发送，JavaScript 需要主动读取并使用。

    • 容量：单个 Cookie 通常只有约 4 KB；localStorage 一般有数 MB，但具体配额取决于浏览器和站点策略。
    • 生命周期：Cookie 可以设置会话期或明确的过期时间；localStorage 默认长期保留，直到代码或用户主动清除。
    • 访问方式：Cookie 可以设置 HttpOnly，让 JavaScript 无法读取；localStorage 始终可被同源页面的 JavaScript 访问。
    • 请求开销：匹配作用域的 Cookie 会随请求发送；localStorage 不会增加每次请求的 Cookie 首部大小。
    • 作用域：Cookie 可设置 Domain、Path、SameSite 等规则；localStorage 主要按源，也就是协议、主机和端口隔离。
    • API 特性：localStorage 是同步 API，只存字符串；大量读写可能阻塞主线程，也不适合作为大型数据库使用。

    二者都不能抵御已经成功执行的 XSS，但 HttpOnly Cookie 可以阻止恶意脚本直接读取凭证；Cookie 自动发送又会带来 CSRF 风险，因此需要结合 SameSite、CSRF Token 等措施。

    5. 什么数据应该存在 Cookie，什么数据存放到 localStorage？

    需要由服务端随请求自动接收、容量很小的数据适合 Cookie；只供前端使用、体积相对较大且不敏感的数据更适合 localStorage。

    • Cookie：常用于 session_id、刷新令牌以及少量需要服务端感知的偏好。认证凭证通常优先放在设置了 HttpOnly、Secure 和合适 SameSite 属性的 Cookie 中。
    • localStorage：适合主题、语言、非敏感的页面配置、草稿或前端缓存。只有当前端代码确实需要读取时才放这里。
    • 都不适合：密码、银行卡号、私钥等高敏感数据不应长期保存在二者中；超大或结构复杂的数据更适合 IndexedDB 等方案。

    最终要结合 XSS、CSRF、跨子域需求、数据生命周期和是否需要服务端自动接收来判断，不能只按容量选择。

    6. JWT 令牌和传统 Session 方式有什么区别？

    与传统 Session 认证相比，JWT 常见用法的核心区别是把一部分身份和授权声明放进签名令牌，由服务端验证签名，而不是每次拿 session_id 查询服务端会话。

    • 状态位置：Session 的会话状态主要在服务端；自包含 JWT 的声明主要由客户端携带。
    • 校验方式：Session 通常要查询内存、数据库或 Redis；JWT 通常本地验证签名、签发方、受众和有效期。
    • 扩展性：JWT 便于多个服务使用同一验证规则，减少共享 Session 查询；Session 则需要粘性会话或共享会话存储。
    • 撤销能力：Session 可以在服务端立即删除；JWT 在到期前通常仍有效，若要求立即撤销，需要黑名单、版本号或其他服务端状态。
    • 数据大小：Session ID 通常很短；JWT 包含头部、声明和签名，请求体积更大。

    JWT 不是天然更安全，也不一定更快。如果系统必须频繁查询权限或维护撤销状态，JWT 的“无状态”优势会减弱。选择时要结合系统架构、失效要求和请求规模。

    7. JWT 令牌都有哪些字段？

    常见的已签名 JWT 由三部分组成，中间用 . 分隔：Header.Payload.Signature。

    1. Header：描述令牌类型和签名算法，常见字段有 typ 和 alg，还可能包含密钥标识 kid。
    2. Payload：存放 Claims，也就是声明。标准注册声明包括签发方 iss、主题 sub、受众 aud、过期时间 exp、生效时间 nbf、签发时间 iat 和唯一标识 jti，还可以放业务自定义声明。
    3. Signature：对编码后的 Header 和 Payload 进行签名或 MAC 计算，用来验证内容是否被篡改以及签发者是否可信。

    需要注意，普通 JWS 形式的 JWT 只是 Base64URL 编码并签名，Payload 可以被读取，并没有加密。因此不能把密码等敏感信息放进去。JWT 标准也没有要求所有注册声明都必须出现，具体必填字段由应用协议决定。

    8. JWT 为什么便于集群部署？什么是集群部署？

    集群部署是把同一个服务运行在多台机器或多个实例上，再通过负载均衡分发请求，用于提高吞吐量、可用性和横向扩展能力。

    传统本地 Session 会带来一个问题：用户第一次登录落到实例 A，下一次请求若落到实例 B，B 的本地内存中可能没有该 Session。通常要使用粘性会话，或者把 Session 放到 Redis 等共享存储中。

    自包含 JWT 将身份声明交给客户端携带。只要集群中的实例拥有正确的验签密钥并执行相同的校验规则，任意实例都可以验证令牌，不必读取某台机器上的本地 Session，所以更适合无状态横向扩容。

    不过 JWT 不是“解决集群部署”的唯一方式，也不代表系统完全没有共享状态。用户、权限、密钥轮换、令牌撤销等数据仍可能需要数据库或缓存支持。

    9. JWT 的缺点是什么？

    JWT 的主要缺点是签发后难以立即撤销，而且令牌体积、信息暴露和密钥管理都需要额外关注。

    • 撤销困难：自包含 JWT 在 exp 到期前通常一直有效。若维护黑名单，又会引入服务端状态和查询开销。
    • 令牌较大：JWT 比随机 Session ID 长，每次请求携带都会增加网络开销，不适合放入过多声明。
    • Payload 默认不保密：签名保证完整性和来源，不等于加密，客户端可以解码看到内容。
    • 权限可能过期：用户权限已被修改，但旧 JWT 中的声明可能在令牌过期前仍然有效。
    • 密钥管理复杂：算法选择、密钥保管和轮换不当会直接影响安全；服务端还必须严格校验 alg、iss、aud、exp 等字段。

    因此 JWT 更适合短期访问凭证和跨服务验证，不应把“完全无状态”当成必须追求的目标。

    10. JWT 泄露后怎么办？JWT 自身是怎么处理的？

    JWT 一旦泄露，攻击者通常可以在它失效前冒用。JWT 的签名只能防止篡改，不能阻止别人使用已经拿到的合法令牌，也不会自动发现泄露。

    常见应对措施是：

    1. 使用较短有效期的 Access Token，缩短泄露后的可利用窗口。
    2. 使用生命周期更长但受严格保护的 Refresh Token，并采用轮换和重复使用检测；发现异常后撤销令牌族。
    3. 服务端按 jti、用户版本号或会话版本维护撤销记录，在改密、退出登录或发现风险时使旧令牌失效。
    4. 轮换或吊销签名密钥可以让一批令牌失效，但影响范围大，通常用于密钥泄露等事件。
    5. 全程使用 HTTPS，避免在 URL 和日志中传递令牌，并做好 XSS、CSRF 防护和异常登录监测。

    如果业务要求“立即踢下线”，就必须引入撤销列表、Token Introspection 或服务端会话等状态，不能只依赖 JWT 的 exp。

    11. 前端如何存储 JWT？

    没有适用于所有系统的唯一答案。浏览器应用中，更稳妥的常见方案是把 Refresh Token 放在 HttpOnly、Secure、适当设置 SameSite 的 Cookie 中，把短期 Access Token 仅保存在内存中。

    • 放在 localStorage 或 sessionStorage 中实现简单，也方便设置 Authorization: Bearer，但发生 XSS 时恶意脚本可以直接读取令牌；其中 sessionStorage 只是在标签页生命周期和共享范围上不同，不能解决 XSS。
    • 放在 HttpOnly Cookie 中可以避免 JavaScript 直接读取，但浏览器会自动携带 Cookie，需要根据跨站场景配置 SameSite，并在必要时增加 CSRF Token、校验 Origin 等防护。
    • 只放内存可以减少持久泄露风险，但刷新页面后会丢失，通常要配合受保护的 Refresh Token 换取新的 Access Token。

    无论放在哪里，都应避免写入 URL、前端日志或错误上报，并设置较短有效期。原生移动端则应优先使用系统提供的安全存储，而不是套用浏览器方案。

    HTTP、RPC 与实时通信

    1. 为什么有 HTTP 协议了，还要用 RPC？

    HTTP 主要定义通用的应用层通信语义，而 RPC 解决的是如何像调用本地函数一样调用远程服务，包括接口定义、参数序列化、代码生成、服务发现、超时、重试和错误模型等问题。二者不是替代关系，RPC 完全可以基于 HTTP 实现，例如 gRPC 通常基于 HTTP/2。

    面向浏览器、开放平台和跨语言兼容时，HTTP/JSON 接口通用、易调试、生态成熟，通常更合适。内部微服务调用如果接口数量多、性能和类型约束要求高，RPC 配合 Protobuf 等二进制序列化，可以提供明确的接口契约、自动生成客户端代码和较小的报文。

    但 RPC 也会增加框架依赖、治理成本和调试门槛。因此不是“有了 RPC 就不用 HTTP”，而是根据调用方、性能、兼容性和工程复杂度选择通信抽象。

    2. HTTP 长连接与 WebSocket 有什么区别？

    HTTP 长连接主要是复用底层连接，WebSocket 则是在一条长连接上提供全双工、双向主动通信。保持连接不断开不等于通信模型相同。

    • 通信模式：传统 HTTP 仍以请求—响应为核心，通常由客户端发起请求；WebSocket 建立后，客户端和服务端都能随时主动发送消息。
    • 协议格式：HTTP/1.1 长连接会重复传输 HTTP 首部；WebSocket 建立后使用较轻量的帧格式传输文本或二进制消息。
    • 建立过程：经典 WebSocket 先通过 HTTP/1.1 Upgrade 握手切换协议；建立后传输的已不再是普通 HTTP 请求和响应。新版协议栈也支持通过 HTTP/2 或 HTTP/3 建立 WebSocket，但语义仍是双向消息通道。
    • 适用场景：HTTP 长连接适合复用请求、减少握手；WebSocket 适合聊天、实时协作、行情推送和在线游戏等高频双向通信。

    如果只需要服务端单向推送，也可以考虑 SSE；请求频率很低时，普通 HTTP 轮询可能更简单。选择应结合通信方向、实时性、连接规模及代理支持情况。

    Nginx

    1. Nginx 有哪些负载均衡算法？

    Nginx 常见的负载均衡方法包括轮询、加权轮询、最少连接、IP 哈希和通用哈希；具体可用能力还要看使用的是开源版、商业订阅以及是否安装第三方模块。

    • 轮询：默认方法，请求依次分配到各上游服务器。
    • 加权轮询：通过 weight 让性能更强的节点接收更高比例的请求；权重也是其他部分算法可使用的服务器参数，不是完全独立的调度器。
    • 最少连接：使用 least_conn，优先选择当前活动连接较少的节点，适合请求耗时差异较大的场景。
    • IP 哈希：使用 ip_hash，根据客户端 IP 选择节点，可实现一定程度的会话粘滞，但代理、NAT 和节点变化会影响分布效果。
    • 通用哈希：使用 hash key [consistent]，可以按 URI、用户 ID 等键分配；consistent 可减少节点变化时的重映射。
    • 随机选择：支持 random，还可结合“两次随机选择”后按最少连接等条件择优。
    • 最短响应时间：least_time 会综合响应时间和活动连接数选择节点，但其可用范围取决于 Nginx 产品和版本，不能默认视为所有开源环境都支持。

    算法选择要结合请求耗时、节点性能、长连接比例、会话状态和流量分布。生产环境还需要配合健康检查、失败重试和容量保护，不能只看算法名称。

    2. Nginx 位于七层网络结构中的哪一层？

    要看 Nginx 使用的模块和代理对象，不能一概而论。作为 HTTP/HTTPS 反向代理时，Nginx 能解析域名、URI、请求头等 HTTP 语义，因此通常称为七层负载均衡，也就是 OSI 的应用层。

    使用 stream 模块转发 TCP 或 UDP 流量时，Nginx 主要根据地址、端口和连接等传输层信息工作，通常称为四层负载均衡。即使七层代理底层也依赖 TCP、TLS 等协议，“位于第几层”描述的是它做转发决策时理解到的最高协议层，而不是说它只参与某一层。

    DNS

    1. DNS 的全称是什么？

    DNS 的全称是 Domain Name System，中文通常称为“域名系统”。它是一个分布式、分层的命名系统，主要负责把域名解析为 IP 地址，也可以查询邮件服务器、权威 DNS 等其他资源记录。

    2. DNS 域名解析的工作流程？

    以查询 www.example.com 的 IP 地址为例，通常流程如下：

    1. 应用先检查自身缓存，操作系统再检查本地 DNS 缓存和 hosts 文件。
    2. 如果没有命中，主机把查询发送给配置的递归 DNS 解析器，例如运营商、企业或公共 DNS 服务提供的解析器。
    3. 递归解析器先检查自己的缓存。未命中时，它通常从根 DNS 服务器开始迭代查询。
    4. 根服务器返回 .com 顶级域权威服务器的信息。
    5. .com 顶级域服务器返回 example.com 权威 DNS 服务器的信息。
    6. 递归解析器向该权威 DNS 服务器查询 www.example.com，获得 A、AAAA 或经 CNAME 继续解析后的结果。
    7. 递归解析器把结果返回客户端，并按照记录的 TTL 缓存；客户端和操作系统也可能缓存结果。

    根服务器和顶级域服务器通常返回的是下一层服务器的转介信息，而不是目标域名的最终 IP。若查询命中任一级缓存，则不需要走完整流程。

    3. DNS 的端口是多少？

    传统 DNS 服务使用 53 端口，UDP 和 TCP 都可以使用该端口。普通查询通常优先使用 UDP；区域传送和某些需要可靠传输的场景使用 TCP。

    加密 DNS 使用的端口可能不同，例如 DNS over TLS 通常使用 TCP 853，DNS over HTTPS 通常使用 HTTPS 的 443。因此回答端口时需要说明指的是哪种 DNS 传输方式。

    5. DNS 底层使用 TCP 还是 UDP？

    传统 DNS 两者都使用。普通查询通常优先使用 UDP，因为无需建立连接、开销较小；但不能简单概括成“DNS 只用 UDP，超过固定字节数就一定改用 TCP”。

    当 UDP 响应被截断时，响应会设置 TC 标志，客户端通常再使用 TCP 重试。借助 EDNS(0)，UDP DNS 报文也可以超过早期的 512 字节限制，但实际大小还要考虑网络 MTU 和分片风险。区域传送 AXFR、IXFR 使用 TCP；现代实现也可能为了可靠性、连接复用或隐私直接选择 TCP、DoT、DoH 或 DoQ。
