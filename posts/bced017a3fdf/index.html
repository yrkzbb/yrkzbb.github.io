场景

Redis 应用场景

1. 为什么使用 Redis，它除了缓存还有哪些应用场景？

使用 Redis 的核心原因是：它能用很低的访问延迟承担高频读写，并通过丰富的数据结构和原子操作简化常见业务实现。但是否应该使用，还要看业务对数据量、一致性、持久性和成本的要求，不是所有数据都适合放在 Redis 中。

主要优势有：

  • 访问速度快：数据主要在内存中操作，再加上高效的数据结构和事件处理模型，适合对延迟敏感的高并发访问。
  • 数据结构丰富：除了 String，还提供 Hash、List、Set、Sorted Set、Stream 等结构，可以直接实现计数、排行榜、去重、队列等需求。
  • 支持过期时间：可以为 Key 设置 TTL，很适合缓存、会话、验证码等有明确生命周期的数据。
  • 单条命令具有原子性：像 INCR、SET key value NX EX、Set 和 Sorted Set 的操作可以减少应用层的并发竞争；需要组合多步逻辑时还可以评估 Lua 脚本或事务。
  • 具备持久化和高可用能力：可以使用 RDB、AOF、主从复制、Sentinel 和 Redis Cluster，在性能、数据安全、容量和可用性之间做选择。

典型场景包括：

  • 缓存数据库查询结果或热点对象，降低数据库压力。
  • 保存分布式会话、验证码和短期状态。
  • 实现计数器、限流、排行榜、去重集合和地理位置查询。
  • 利用 SET ... NX EX、Lua 脚本等机制实现有条件的分布式锁和协调功能。
  • 用 List、Stream 或 Pub/Sub 实现特定场景下的异步通信，但是否能替代专用消息队列，需要结合消息可靠性、堆积量和消费模型判断。

需要注意的是，Redis 主要依赖内存，单位容量成本通常高于磁盘数据库；默认的异步主从复制也不保证强一致。因此，对严格不能丢失的核心业务数据，我通常会以数据库作为可靠数据源，再让 Redis 承担缓存或加速层，而不是不加区分地用 Redis 替代数据库。

2. 为什么 Redis 通常比 MySQL 快？

在简单 Key-Value 读写场景中，Redis 通常比 MySQL 快，核心原因是数据访问路径更短，需要完成的工作更少。但这不是一个对所有查询都成立的绝对结论，两者定位不同，需要在相同数据量、请求模型和持久化要求下比较。

主要原因有：

  • 以内存访问为主：Redis 的数据主要存放在内存中，常见操作不需要等待随机磁盘 I/O。MySQL 虽然也有 Buffer Pool，热数据同样可能命中内存，但数据页、日志和持久化等机制更复杂。
  • 命令执行路径简单：Redis 常见命令可以直接对字典、跳表等数据结构操作；MySQL 通常还要经历 SQL 解析、优化、执行计划、索引或数据页访问等流程。
  • 并发控制成本较低：Redis 的命令执行主路径主要是单线程串行，减少了共享数据的锁竞争和线程切换。MySQL 要支持多会话并发、事务隔离和 MVCC，管理成本更高。
  • 一致性和持久性责任不同：MySQL 需要维护 redo log、undo log、事务提交和崩溃恢复等机制。Redis 可以根据需要配置 RDB 或 AOF，但它默认并不提供与关系数据库相同的事务和持久性语义。

所以更准确地说，Redis 的优势是处理简单、高频、延迟敏感的数据访问；MySQL 的优势是复杂查询、事务、约束和可靠持久化。两者通常是配合使用，而不是直接互相替代。

3. 本地缓存和 Redis 缓存有什么区别？

核心区别是：本地缓存在应用进程内，访问更快，但多实例之间不共享；Redis 是独立的远程缓存，需要网络访问，但可以被多个应用实例共享。

对比项 本地缓存 Redis 缓存
存储位置 应用进程内存 独立 Redis 进程的内存
访问延迟 无网络开销，通常更低 有网络、协议和序列化开销
数据共享 每个应用实例各有一份 多个应用实例共享一份数据
一致性 多份副本容易不一致，失效通知更复杂 数据较集中，但仍需处理与数据库的一致性
容量 受单个应用进程内存限制 可以独立配置容量并通过 Cluster 扩展
生命周期 应用重启后通常丢失 与应用进程解耦，可选持久化和高可用
运维成本 不需要独立服务，但会占用应用内存 需要部署、监控、容量管理和故障处理

本地缓存适合数量小、访问频率高、允许短暂不一致的数据，例如配置、字典或极热数据；Redis 适合需要跨实例共享、集中设置 TTL 或容量较大的缓存。对延迟和吞吐要求很高的系统，也可以使用“本地缓存 + Redis”的两级缓存，但要额外处理更新通知、过期时间和多级数据一致性。

4. 高并发场景下，Redis 单节点加 MySQL 单节点能承受多大并发量？

没有一个固定数字。并发连接数、QPS 和延迟是不同指标，系统的上限取决于硬件、命令或 SQL 复杂度、数据量和分布、缓存命中率、网络、连接池以及延迟目标。没有这些条件时，直接说能承受几万或几十万并发并不严谨。

如果只用于方案初估，在常见服务器、小 Key 和简单 GET/SET 下，Redis 单节点通常可以达到数万至十万级 ops/s；MySQL 单节点的简单主键点查询可能达到万级 QPS，事务写入往往更低。这些只是很粗的量级，Big Key、复杂 SQL、低效索引、锁竞争、AOF 刷盘策略和 MySQL 持久化配置都可能让结果相差数倍甚至数量级。

5. Redis 支持并发操作吗？

支持，但要区分并发接收请求和命令并行执行。Redis 可以同时维护大量客户端连接，通过 I/O 多路复用处理并发网络事件；但单个 Redis 节点上，普通命令的核心执行路径主要仍由主线程串行完成。

这意味着单条 Redis 命令在服务端不会被另一条命令执行到一半时插入，所以 INCR、HSET 等单条命令具有原子性。但“先 GET，再根据结果 SET”是多条命令，中间可能穿插其他客户端的操作，需要根据场景使用 WATCH/MULTI/EXEC、Lua 脚本或直接使用带条件的原子命令。

Redis 6 开始可以启用 I/O 线程辅助网络数据读写，但这不等于任意命令都会多线程并行修改数据。因此，对 Big Key 的复杂操作、大型 Lua 脚本或阻塞性命令，仍可能占用主线程并影响其他请求。

7. Redis 的 Big Key 问题是什么？

Big Key 指的是占用内存过大，或者集合成员数过多的 Key。它不只指 Key 名很长，重点是 Value 及其底层结构的体积或操作成本很大。

例如，一个 String 保存了数 MB 数据，或一个 Hash、List、Set、Sorted Set 中有几十万个成员，都可能成为 Big Key。多大算“大”没有通用固定阈值，要根据延迟目标、网络带宽、实例容量和命令类型判断。同样大小的 String 和拥有大量成员的集合，操作风险也可能不同。

8. Big Key 有哪些危害？

Big Key 的主要问题不只是占用内存，还可能影响整个实例的延迟和可用性：

  • 阻塞主线程：一次读取、遍历或删除大对象可能长时间占用命令执行线程，拉高其他请求的 P99 延迟。
  • 消耗网络带宽：一次传输过大的 Value 会占用带宽和客户端缓冲区，也可能导致超时。
  • 引起内存和分片倾斜：少数 Big Key 可能让某个 Cluster 节点的内存、CPU 或流量明显高于其他节点。
  • 放大持久化和复制压力：Big Key 的写入、迁移和同步会产生更大的 AOF、复制流和网络开销。
  • 删除延迟和内存抖动：同步 DEL 一个含大量成员的集合可能造成明显阻塞，大对象频繁创建和释放还可能加剧内存碎片和抖动。

9. Redis Big Key 如何治理？

处理 Big Key 的思路是：先识别和量化，再从数据模型上拆分，同时避免一次全量读写或同步删除。

  • 发现：可以结合 redis-cli --bigkeys、MEMORY USAGE、慢查询、延迟监控以及对 SCAN 结果的抽样统计进行排查。--bigkeys 主要找各类型中相对较大的 Key，不能完全替代精确内存分析。
  • 拆分数据：将大 String 拆成多个小块，或者按用户、日期、业务分区将大集合拆成多个 Key。在 Cluster 中要谨慎使用 Hash Tag，避免拆分后仍全部集中到同一 Slot。
  • 减少存储体积：只保存必要字段，选择更合适的数据结构和编码；是否压缩要权衡 CPU 开销和网络收益。
  • 分批处理：集合数据使用 HSCAN、SSCAN、ZSCAN 等渐进式遍历，避免一次返回全部成员。
  • 安全删除：大对象可以使用 UNLINK 先从键空间解除，再由后台线程释放内存；执行前仍应评估后台释放速度和瞬时内存压力。
  • 在入口限制：对 Value 字节数和集合成员数设置业务阈值，建立持续监控，防止 Big Key 再次生成。

10. 什么是 Hot Key？

Hot Key 指在某段时间内访问频率远高于其他 Key，导致请求集中在某个 Redis 节点或某个 Key 上。例如热门商品、热搜榜、爆款活动或全局配置的 Key。

Hot Key 和 Big Key 不是一回事：Big Key 关心的是体积或成员数，Hot Key 关心的是访问频率。一个很小的 Key 也可以因为请求过多成为 Hot Key，同一个 Key 也可能既大又热。Redis Cluster 按 Key 将数据映射到固定 Slot，不会自动把单个 Hot Key 的请求分散到多个主节点。

11. 如何解决 Hot Key 问题？

解决 Hot Key 要先区分是读热点还是写热点，再选择分散、合并或限制请求的方案：

  • 识别热点：结合 redis-cli --hotkeys、MONITOR 的短时诊断、客户端埋点、代理统计和节点 CPU/网络指标发现热点。MONITOR 开销较大，不应长时间在高负载生产环境运行。
  • 本地缓存：对读多写少、允许短暂不一致的热 Key，在应用实例内增加一级缓存，大量读请求不再访问 Redis。
  • 创建读副本：将同一份热数据写入多个带后缀的 Key，读请求按规则分散到不同 Key 和 Slot。该方案适合读多写少场景，代价是需要处理多副本更新和过期的一致性。
  • 拆分写热点：计数器等可合并业务可以拆成多个分片 Key，将写入分散后再定期汇总。如果业务要求对单一值做强实时更新，则不能直接使用这种方法。
  • 请求合并与限流：对同一 Key 的并发回源请求做 singleflight/互斥合并，对超过系统能力的流量限流、排队或降级，并在业务可接受时返回短期旧值。

仅增加 Redis Cluster 节点不一定能解决单个 Hot Key，因为该 Key 仍然属于一个 Slot。需要从 Key 设计和请求路径上将流量真正分散。

12. 如何保证 Redis 与 MySQL 的缓存一致性？

严格来说，在没有分布式事务或统一顺序控制的情况下，很难让 Redis 和 MySQL 在任意时刻都完全强一致。实际项目中常用 Cache Aside（旁路缓存）模式，将 MySQL 作为可靠数据源，通过更新数据库后删除缓存来获得最终一致。

读取流程是：

  1. 先读 Redis，命中就直接返回。
  2. 未命中时查询 MySQL。
  3. 将查询结果写入 Redis 并设置合理 TTL，然后返回数据。

更新流程通常是：

  1. 先在 MySQL 中提交数据修改。
  2. 数据库提交成功后删除 Redis 缓存，而不是直接更新缓存。后续读请求缓存未命中，再从 MySQL 加载新值。

“先更新 MySQL，再删缓存”通常比“先删缓存，再更新 MySQL”的不一致窗口更小，但仍需要处理删除失败以及并发读回写旧值的竞态。根据一致性要求，可以进一步采用：

  • 失败重试：将删除缓存的任务放入可靠消息队列或本地事件表，失败后重试并监控死信。
  • 订阅 binlog：通过 CDC 消费 MySQL binlog，按数据变更事件删除或更新缓存，并做好幂等、顺序和重试处理。
  • 延迟双删：在特定竞态模型下，第一次删除后延迟再删一次，降低旧值被并发请求重新写入的风险。延迟时间需要结合业务请求时长设置，它仍是最终一致方案，不能当作强一致保证。
  • 版本校验或串行化：在对顺序敏感的场景中为数据携带版本号，拒绝用旧版本覆盖新版本；对少量强一致路径可考虑加锁或串行化，但会牺牲可用性和吞吐量。

TTL 只是最后的兜底，决定了错误缓存最长可能存在多久，不应用它代替更新通知。最终方案要根据业务能容忍的不一致窗口、吞吐量和系统复杂度选择。

13. 缓存雪崩、缓存击穿和缓存穿透是什么，如何解决？

三者的区别在于缓存未命中的原因不同：雪崩是大量 Key 同时失效或 Redis 整体不可用，击穿是某个热 Key 失效，穿透是查询本来就不存在的数据。它们都可能让请求绕过缓存直接压到数据库，但治理方式不完全相同。

问题 表现 常见解决方案
缓存雪崩 大批 Key 在相近时间过期，或 Redis 故障，流量集中回源 TTL 加随机值打散过期时间；核心数据预热；Redis 高可用和容量预案；应用侧限流、熔断、降级及请求合并
缓存击穿 一个高频热 Key 到期，大量并发请求同时查询数据库 对回源加互斥锁或做 singleflight，只让一个请求重建缓存；采用逻辑过期并在后台刷新；必要时对热点预热
缓存穿透 请求的 Key 在 Redis 和数据库中都不存在，每次都回源 先做参数和权限校验；对不存在的结果做短 TTL 的空值缓存；在数据量较大时使用布隆过滤器拦截一定不存在的 Key；对恶意流量限流

这些手段需要组合使用。例如，缓存空值会占用内存，而布隆过滤器存在误判；逻辑过期可以避免热 Key 集中回源，但客户端可能在短时间内读到旧值。选型时要结合数据一致性和可用性要求。

14. 布隆过滤器的原理是什么？

布隆过滤器是一种用来判断元素是否可能存在的空间高效概率数据结构。它的结论是：判定不存在时一定不存在；判定存在时只是可能存在，因为它会有假阳性，但标准布隆过滤器在数据正确写入且位没有被删除的前提下不会有假阴性。

它由一个位数组和多个 Hash 函数组成：

  1. 写入元素：用 k 个 Hash 函数对元素计算，得到 k 个位置，把位数组中对应的位设为 1。
  2. 查询元素：用相同的 Hash 函数计算位置。只要有一位是 0，元素就一定不存在；如果所有位都是 1，可能是该元素设置的，也可能是其他元素碰撞的，所以只能说可能存在。

误判率取决于位数组大小、Hash 函数数量和实际写入的元素数。设计时应根据预期容量和可接受的误判率计算参数，实际数量大幅超过预期时，误判率会上升。标准布隆过滤器不能直接安全删除元素，因为同一个位可能被多个元素共用；如果需要删除，可以评估 Counting Bloom Filter 或定期重建。

在缓存穿透场景中，请求先查布隆过滤器；如果判定不存在就直接拒绝，如果判定可能存在，仍然需要继续查 Redis 或数据库确认。

15. 如何设计秒杀系统以处理高并发并避免超卖？

秒杀系统的核心思路是：在入口拦截无效流量，用 Redis 原子地预扣库存，通过消息队列削峰后异步落库，最后由数据库条件更新和唯一约束兜底。

一个常见的处理流程是：

  1. 事前预热：将活动页面静态化并放到 CDN，将商品信息和可售库存预热到 Redis，避免开始时大量请求直接读 MySQL。

  2. 入口限流：在 CDN、网关和应用层做限流、黑名单、验证码或动态秒杀路径校验，只让系统能承受的请求进入核心流程。

  3. 原子校验和预扣：用 Redis Lua 脚本在一次原子执行中完成活动状态、用户是否重复购买、库存是否大于 0 的检查，然后扣减库存并记录用户预订。不能把“查库存”和“减库存”拆成两次非原子请求。

  4. 消息队列削峰：预扣成功后发送下单消息，后台消费者按 MySQL 能力异步创建订单。消息要有唯一业务 ID，并做好持久化、重试、幂等消费和死信处理。

  5. 数据库兜底：扣减数据库库存时使用带条件的原子更新，例如：

    只有受影响行数为 1 才表示扣减成功；同时对“活动 ID + 用户 ID”等业务键建立唯一约束，防止重复消费创建多张订单。

  6. 结果查询与补偿：前端查询异步处理结果，而不是长时间阻塞等待。如果消息最终失败、订单超时未支付或数据库扣减失败，需要按幂等规则回补库存，并通过对账任务发现 Redis、订单和 MySQL 之间的差异。

防超卖的最后保证不应只放在 Redis。Redis 预扣用于快速过滤大部分请求，MySQL 的 stock > 0 条件更新负责防止库存减成负数，唯一约束和幂等逻辑防止重复下单，消息与补偿机制负责处理跨系统的最终一致。
