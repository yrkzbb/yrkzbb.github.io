数据结构

Redis 数据结构

1. 讲一下 Redis 底层的数据结构？

Redis 对外提供的是 String、List、Hash、Set、ZSet 等数据类型，但它们并不是固定对应一种底层结构。

常见的底层结构主要有：

  • SDS（简单动态字符串）：保存字符串和很多内部文本数据。它会记录长度和容量，因此获取长度是 O(1)，也能保存包含 \0 的二进制数据，并通过预分配等方式减少频繁扩容。
  • 哈希表（dict）：用于数据库的键空间，也用于元素较多时的 Hash、Set，以及普通编码下 ZSet 的成员到分值映射。它的增删改查平均是 O(1)，扩容时通常采用渐进式 rehash，避免一次迁移造成长时间阻塞。
  • listpack（紧凑列表）：把多个元素连续存放，适合元素较少、内容较小时使用。它比哈希表等结构节省内存，但查找通常需要顺序遍历，数据变大后 Redis 会转换为更适合的编码。
  • 整数集合（intset）：用于成员较少且全部为整数的 Set。元素有序、存储紧凑；加入非整数成员或超过配置阈值后，会转换成其他编码。
  • quicklist：主要用于 List，本质上是由双向链表组织多个 listpack 节点。它在两端插入、删除效率和内存连续性之间做了折中。
  • 跳表（skiplist）：用于数据量较大的 ZSet，按分值有序，平均查找、插入和删除复杂度是 O(log N)。Redis 同时配合哈希表保存“成员到分值”的映射，使按成员查询分值平均为 O(1)。

对应到五种常用类型，可以概括为：

Redis 类型 常见内部编码或结构
String 整数编码，或由 SDS 支撑的 embstr、raw 编码
List listpack 或 quicklist
Hash listpack 或哈希表
Set intset、listpack 或哈希表
ZSet listpack，或跳表加哈希表

2. Redis 的 ZSet 在项目里具体怎么用？

我在项目里主要用 ZSet 做积分排行榜。Key 按榜单周期拆分，例如 rank:daily:20260821；成员保存用户 ID，score 保存积分。用户信息仍放在数据库或单独的缓存中，不把昵称、头像等信息拼进成员，避免更新资料时还要修改排行榜。

实现时我会特别注意几个问题：同分成员会按成员字典序确定先后，如果业务要求“先达到该分数的人排名更高”，就需要单独设计排序分值或排名规则；分页不要一次返回大量成员；高并发活动还要评估热点 Key，必要时按业务维度拆分并在最终查询时合并。

ZSet 也能用来实现延迟任务，把执行时间戳作为 score，按时间范围取到期任务。不过仅靠查询后删除不能保证可靠性，还需要解决并发抢占、重复消费、确认和失败重试，因此复杂任务场景下我会优先评估专业消息队列。

3. Redis 中 Set 和 ZSet 的区别是什么？

核心区别是：Set 是无序去重集合，ZSet 是通过 score 排序的去重集合。如果只需要判断成员是否存在，或者做交集、并集、差集，我会优先使用 Set；如果还需要排名或按分数范围查询，就使用 ZSet。

对比项 Set ZSet
成员 成员唯一 成员唯一
顺序 逻辑上无序 按 score 从小到大排序
分值 没有 每个成员关联一个 score，不同成员的分值可以相同
常用操作 SADD、SISMEMBER、SINTER、SUNION ZADD、ZSCORE、ZRANGE、ZRANK
常见底层结构 intset、listpack 或哈希表 listpack，或跳表加哈希表
典型复杂度 哈希表编码下，添加和判断成员平均为 O(1) 普通编码下，添加、删除和排名查询通常为 O(log N)
适用场景 标签、抽奖池、共同好友、元素去重 排行榜、权重队列、按时间戳查询任务

例如，记录某篇文章被哪些用户点赞，只关心用户是否点过赞，可以用 Set；如果要按照用户积分生成排行榜，就用 ZSet。另外，ZSet 中分值相同的成员仍然可以同时存在，Redis 会再按成员的字典序确定它们之间的顺序。

4. ZSet 底层是怎么实现的？

ZSet 并不总是只用跳表实现。数据量较小时，Redis 通常使用 listpack；数据超过相应阈值后，会转换为跳表加哈希表的组合结构，以同时满足按分值排序和按成员快速查询的需求。

小数据量使用 listpack 时，成员和 score 紧凑地连续存储，并保持分值有序。它的内存开销较小，但查找和移动元素通常需要线性遍历，所以更适合成员少、单个元素也较小的场景。

数据量较大时，ZSet 内部主要包含两部分：

  • 跳表：节点按照 score 排序；分值相同时再按照成员的字典序排序。每个节点有随机生成的多层前进指针，还会记录跨度，因此查找、插入、删除和计算排名平均为 O(log N)，范围查询定位起点后可以顺序遍历。
  • 哈希表：保存成员到 score 的映射，因此使用 ZSCORE 等命令按成员查询分值时，平均复杂度为 O(1)。

这两种结构保存的是同一批成员，Redis 在执行 ZADD、ZREM 等写操作时会同时维护它们。这样会增加一定的内存开销，但兼顾了两类访问方式：跳表负责有序和范围操作，哈希表负责按成员快速定位。

5. 跳表是怎么实现的？

跳表可以理解为在有序链表上增加了多级索引。最底层保存全部节点，越高层保存的节点越少；查询时从最高层开始向右跳跃，不能继续前进时下降一层，直到最底层找到目标位置，因此平均查找复杂度可以从普通链表的 O(N) 降到 O(log N)。

Redis 跳表的主要结构包括：

  • 跳表本身：记录头节点、尾节点、当前最大层数和节点数量。
  • 跳表节点：保存成员、score、后退指针，以及多个层级。每一层包含一个前进指针和一个 span（跨度）。
  • 排序规则：先按 score 升序；score 相同时，再按成员的字典序排序。

查找时，从头节点的最高层开始：如果下一个节点仍小于目标，就继续向右；否则下降到下一层。不断重复，最终会在第 0 层确定目标节点或插入位置。

插入时，Redis 会先记录目标位置在每一层的前驱节点，然后为新节点随机生成层数，并修改相应层的前进指针。节点每增加一层的概率是 25%，所以高层节点会逐渐变少；Redis 的实现最多支持 32 层。随机层数使跳表不需要像平衡树那样通过旋转维持严格平衡，但查找、插入和删除的平均复杂度仍是 O(log N)，最坏情况下是 O(N)。

删除与查找过程类似：先找到各层的前驱节点，再断开目标节点并更新指针。Redis 还会同步维护各层的 span，它表示当前节点到下一节点之间跨越的第 0 层节点数，因此 ZRANK、ZREVRANK 等命令可以在查找过程中累加跨度得到排名，而不需要从头遍历整个集合。

6. 跳表是怎么设置层高的？

在每次插入节点时独立随机生成。新节点至少有 1 层，之后每增加一层的概率是 25%，最高不超过 32 层。

如果随机出的层高超过跳表当前最高层，Redis 会把新增层级的前驱节点设为头节点，并提高跳表记录的当前最大层数；否则最大层数保持不变。

7. Redis 为什么使用跳表而不是 B+ 树？

核心原因是 Redis 的 ZSet 主要在内存中完成排序、更新和范围查询，跳表已经能提供平均 O(log N) 的查找、插入和删除，而且实现和维护相对简单。B+ 树当然也能实现这些功能，但它最大的优势是减少磁盘 I/O，这在 Redis 的主要访问模型中并不突出。

具体来说：

  • 访问介质不同：B+ 树一个节点可以存放大量键，树高较低，能用一次页读取获得多个键，因此很适合数据库和文件系统的磁盘、页式存储。Redis 的 ZSet 主要驻留内存，不需要把减少磁盘随机 I/O 作为首要目标。
  • 更新方式更简单：跳表通过随机层高维持概率平衡，插入和删除主要修改前后指针。B+ 树需要处理节点分裂、合并和再平衡，工程实现更复杂。
  • 范围遍历方便：跳表定位范围起点后，可以沿第 0 层向前或向后遍历。B+ 树的叶子节点链表也能高效完成范围查询，所以这不是跳表独有的优势，只是跳表用更直接的结构就能满足 Redis 的需求。
  • 排名计算方便：Redis 在跳表每一层维护 span，查找过程中累加跨度就能计算成员排名，适合 ZRANK、ZREVRANK 等命令。
  • 与哈希表互补：ZSet 同时使用哈希表按成员查询 score，平均为 O(1)；跳表主要负责排序、排名和分数范围查询，两者分工清晰。

所以不能简单认为跳表一定比 B+ 树快或更省内存。B+ 树具有更高的扇出和更好的块内局部性，在磁盘索引、页式存储或某些缓存敏感场景中更合适；Redis 选择跳表，是因为它在纯内存、有序集合频繁更新和范围查询的场景下，以较低的实现复杂度满足了所需性能。

8. 压缩列表是怎么实现的？

压缩列表通常指旧版 Redis 的 ziplist。它不是普通链表，而是一块连续内存，将多个元素紧凑地顺序存放，通过变长编码减少指针和结构体的额外开销。它适合元素数量少、单个元素较小的场景；Redis 7.0 起，Hash、ZSet 等结构已主要使用 listpack 取代 ziplist。

ziplist 整体由以下部分组成：

  • zlbytes：占 4 字节。
  • zltail：占 4 字节。
  • zllen：占 2 字节。
  • entry：真正保存的元素。
  • zlend：占 1 字节，值为 0xFF，表示压缩列表结束。

由于头部大小固定，第一个节点可以通过头部后的地址直接定位，尾节点则通过 zltail 定位，这两种操作都是 O(1)；查找中间某个节点仍需要从头部或尾部逐个遍历，复杂度为 O(N)。zllen 只负责记录数量，并不负责定位首尾节点。

查询时根据每个节点编码出的长度顺序移动；在中间插入或删除元素时，因为底层是连续内存，需要扩容或收缩并移动后续数据，所以通常是 O(N)。此外，previous_entry_length 根据前一节点大小可能占 1 字节或 5 字节：如果某次更新使它发生扩展，后续节点也可能继续扩展，从而产生“连锁更新”。这也是旧 ziplist 的一个问题。

当前的 listpack 仍采用连续内存和紧凑的变长编码，但每个元素在尾部记录自身长度，不再让下一个元素保存前一个元素长度，因此避免了 ziplist 的连锁更新问题。它依然更适合小规模数据，因为中间插入、删除和按值查找仍可能需要移动或遍历数据。

9. 介绍一下 Redis 中的 listpack？

listpack 是 Redis 使用的一种紧凑顺序结构，本质上是一块连续内存。它通过变长编码保存字符串或整数，主要用于元素较少、单个元素较小时降低内存开销。Redis 7.0 起，小型 Hash、ZSet 等结构主要使用 listpack 取代旧的 ziplist。

它的整体布局和 entry 结构如下：

  • total-bytes：占 4 字节，记录整个 listpack 的总字节数。
  • num-elements：占 2 字节，记录元素数量；达到特殊上限值时，需要遍历才能获得准确数量。
  • entry：保存具体元素。
  • end：占 1 字节，值为 0xFF，表示结束。

图中的 len 对应 Redis 实现中的 backlen。每个 entry 主要包含：

  • encoding 同时描述数据类型和长度，Redis 会根据内容选择不同的字符串或整数编码。
  • data 保存实际内容；部分较小整数可以直接包含在编码中，不需要单独的数据区域。
  • backlen 使用变长编码记录当前 entry 自身的长度，Redis 可以从当前位置向前解析出上一个元素，从而支持反向遍历。

listpack 和 ziplist 的关键区别在于：ziplist 的节点记录前一个节点长度，当前节点变大时可能迫使后续节点的 prevlen 扩展，造成连锁更新；listpack 的节点记录自身长度，修改当前节点不会因为长度字段变化而连锁修改后续节点。

它的优势是内存连续、没有普通链表的节点指针开销，而且紧凑布局通常具有较好的缓存局部性。但它并不是所有场景都更高效：按值查找或按下标访问中间元素通常需要遍历，复杂度为 O(N)；在中间插入、删除还可能引起内存扩容和数据移动。因此 Redis 主要把它用于小规模数据，超过相应阈值后会转换为哈希表、跳表或 quicklist 等更合适的结构。

10. 哈希表是怎么扩容的？

Redis 哈希表扩容的核心是渐进式 rehash：它不会一次性搬迁所有数据，而是同时保留新旧两张哈希表，把迁移工作分摊到后续操作和周期任务中，避免数据量较大时长时间阻塞主线程。

正常情况下，当哈希表的负载因子达到扩容条件时，Redis 会为第二张哈希表分配更大的桶数组，容量通常扩展到足以容纳现有元素的下一个 2 的幂，因此常见结果是扩大约一倍。负载因子可以理解为：

扩容过程大致如下：

  1. 平时数据保存在第一张哈希表中，第二张表为空。
  2. 触发扩容后，为第二张表分配更大的桶数组，并设置 rehash 进度。
  3. Redis 每次只迁移旧表中的少量桶。迁移时需要根据新表容量重新计算元素所在位置，不能直接复制旧下标。
  4. 在迁移期间，查询、更新和删除需要同时检查两张表；新插入的元素通常直接写入新表，避免继续增加旧表的数据。
  5. 旧表全部迁移完成后，释放旧桶数组，让新表成为主表，并清空 rehash 状态。

迁移主要通过两种方式推进：一是在执行哈希表的增删改查时顺带迁移少量桶；二是 Redis 的周期任务在限定时间内主动推进迁移。这样单次操作的额外开销比较可控，但在 rehash 期间会同时持有两张表，因此会暂时占用更多内存。

Redis 是否立即扩容还会结合运行状态判断。例如执行生成 RDB 或重写 AOF 的后台任务时，通常会尽量避免普通扩容，以减少写时复制带来的额外内存；但如果负载因子已经过高，仍会强制扩容，防止哈希冲突链过长。具体阈值属于实现策略，理解重点是：负载因子决定是否需要扩容，双表配合渐进式迁移控制单次延迟。

11. 哈希表扩容的时候，有读请求怎么查？

扩容期间，Redis 会同时查询旧表和新表。它先根据旧表容量计算桶下标并查找旧表，如果没有找到且当前正在 rehash，再根据新表容量重新计算下标并查找新表；只要任意一张表找到目标 Key，就返回对应结果。

12. Redis 的 String 使用什么存储？为什么不用 C 语言字符串？

Redis 的 String 根据内容采用不同编码：能直接表示为整数时使用 int 编码；字符串较短时通常使用 embstr；字符串较长时使用 raw。其中 embstr 和 raw 的字符串内容都由 SDS（Simple Dynamic String，简单动态字符串）支撑。

  • int：值能够表示为整数时，直接在 Redis 对象中保存整数，减少额外内存分配。
  • embstr：Redis 对象头、SDS 头和字符数组通过一次连续内存分配完成，适合较短字符串，分配次数少、缓存局部性较好。
  • raw：Redis 对象和 SDS 分开分配，适合较长字符串，也便于后续修改和扩容。

Redis 不直接使用 C 字符串，主要有以下原因：

  1. 获取长度更高效：C 字符串需要从头扫描到 \0，strlen 是 O(N)；SDS 在头部记录 len，获取长度是 O(1)。
  2. 二进制安全：C 字符串把 \0 当作结束符，难以直接保存中间包含零字节的数据；SDS 根据 len 判断边界，可以保存图片、序列化数据等任意字节序列。
  3. 降低缓冲区溢出风险：SDS 同时记录已使用长度和可用容量，拼接前会检查空间并按需扩容，不会假设目标缓冲区一定足够。
  4. 减少频繁内存分配：SDS 扩容时可以保留额外空间，后续追加数据不一定每次都重新分配；缩短字符串时也不必立刻释放全部剩余空间。
  5. 兼容部分 C 字符串函数：SDS 的数据区末尾仍保留 \0，所以文本场景下仍可复用部分以 C 字符串为输入的函数；但 Redis 自身主要依靠长度字段处理数据。

所以，SDS 不是完全抛弃字符数组，而是在字符数组前增加长度、容量和类型等元数据，从而兼顾二进制安全、操作效率和内存管理。实际编码可以通过 OBJECT ENCODING key 查看。
