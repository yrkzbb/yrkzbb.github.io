网络IO

网络 I/O 模型

1. 你了解过哪些 I/O 模型？

以 Unix 网络 I/O 为例，常见模型有五种：

  • 阻塞 I/O：调用 read、recv 等操作后，线程会等待数据就绪并完成复制，期间通常不能继续处理其他工作；
  • 非阻塞 I/O：数据未就绪时调用立即返回，例如返回 EAGAIN，程序需要稍后重试；如果只是不断轮询，会浪费 CPU；
  • I/O 多路复用：使用 select、poll、epoll 等接口同时等待多个描述符，就绪后再执行实际读写；
  • 信号驱动 I/O：描述符就绪时由内核发送信号通知进程，应用收到通知后进行读写，使用相对较少；
  • 异步 I/O：应用提交操作后继续执行，由内核完成数据传输并通知结果，例如部分平台的 AIO、io_uring 或 IOCP 能力。

阻塞与非阻塞描述的是一次 I/O 调用是否等待；同步与异步更关注数据传输由谁完成以及完成结果如何通知。I/O 多路复用通常仍属于同步 I/O，因为就绪后应用还要主动调用 read 或 write 完成数据传输。

2. 服务器处理并发请求有哪几种方式？

常见并发服务器模型包括：

  • 迭代式处理：一个请求处理完再处理下一个，实现简单，只适合并发需求很低或单次处理极短的场景；
  • 每连接一个进程：隔离性较好，但创建和切换进程的成本较高；
  • 每连接一个线程：编程直观，但大量连接会带来线程栈、调度和上下文切换开销；
  • 进程池或线程池：复用固定数量的工作单元，限制资源消耗，适合任务数量较多但并发上限需要控制的场景；
  • 事件驱动模型：少量线程通过 I/O 多路复用管理大量连接，通常采用 Reactor 模式；
  • 异步完成模型：提交异步 I/O，完成后由系统通知，常对应 Proactor 思路；
  • 混合模型：事件循环负责网络 I/O，再把计算、阻塞操作或业务任务交给工作线程池。

选择时要结合连接数量、单个请求耗时、CPU 或 I/O 密集程度、隔离要求和开发复杂度。高并发网络服务通常使用事件驱动与线程池结合，而不是简单地为每个连接创建一个线程。

I/O 多路复用

1. 讲一下 I/O 多路复用。

I/O 多路复用是指：一个线程通过一个等待接口，同时关注多个文件描述符的就绪事件。没有事件时线程可以阻塞；当一个或多个描述符可读、可写或发生异常时，内核通知应用，应用再处理对应连接。

典型流程是：

  1. 将监听套接字和已连接套接字注册到多路复用接口；
  2. 调用 select、poll 或 epoll_wait 等接口等待事件；
  3. 接口返回后，找出就绪描述符；
  4. 对就绪连接执行 accept、read、write 等非阻塞操作；
  5. 更新关注事件并再次等待。

它的优势是少量线程就能管理大量连接，减少线程数量和上下文切换。但它并不会让单个 I/O 操作本身更快，也不能消除业务计算开销。如果事件处理函数执行时间过长，会阻塞整个事件循环，因此耗时计算和阻塞调用通常需要转移到工作线程池。

2. select、poll、epoll 的区别是什么？

三者都能等待多个文件描述符的就绪事件，但数据结构和就绪事件获取方式不同：

对比项 select poll epoll
描述符集合 位图 pollfd 数组 内核维护的兴趣集合与就绪队列
数量限制 受 FD_SETSIZE 限制 无固定的小型位图上限，但受系统资源限制 受系统资源限制
每次等待 需要传入并重建集合 需要传入整个数组 注册后只需等待就绪事件
查找就绪项 通常扫描整个集合 通常扫描整个数组 直接返回就绪项
触发模式 水平触发 水平触发 支持水平触发和边缘触发
平台 可移植性较好 多种 Unix-like 系统 Linux 专有

当描述符数量很多但同时活跃的连接较少时，epoll 通常更有优势，因为无需每次复制并线性扫描全部描述符。连接数量较少或大部分连接始终活跃时，三者的实际差距可能没有想象中大，还要结合事件处理逻辑、系统调用次数和数据分布通过压测判断。

3. epoll 的边缘触发和水平触发有什么区别？

核心区别是通知条件：

  • 水平触发（LT）：只要描述符仍处于就绪状态，epoll_wait 就会继续报告它。例如接收缓冲区还有数据未读完，下次等待仍会收到可读事件。LT 是默认模式，逻辑更简单，容错性较好。
  • 边缘触发（ET）：通常只在描述符状态从未就绪变为就绪时通知。应用收到事件后应持续读或写，直到非阻塞操作返回 EAGAIN，否则剩余数据可能不会立即再次触发通知。

ET 可以减少重复通知和部分系统调用，但编程要求更严格，通常必须配合非阻塞描述符和“处理到 EAGAIN”的循环。它不一定在所有场景都比 LT 快；如果连接规模不大或业务处理才是瓶颈，差异可能很小。

高性能网络框架

1. Redis、Nginx、Netty 依赖什么实现高性能？

它们都大量使用非阻塞 I/O、事件驱动和 I/O 多路复用，但高性能不只是依赖 epoll。

  • Redis：核心命令执行通常采用事件循环，利用 epoll、kqueue 等平台接口管理连接，避免为每个连接创建线程；内存数据结构、高效编码和较短的命令执行路径也很重要。较新的 Redis 还可以使用 I/O 线程处理部分网络读写，但命令执行模型不能简单概括为“完全多线程”。
  • Nginx：通常采用多个 worker 进程，每个 worker 使用事件循环和平台多路复用接口处理大量连接；同时利用非阻塞 I/O、连接复用、缓冲、sendfile 等机制。避免在 worker 中执行阻塞操作是保持响应能力的关键。
  • Netty：基于 Java NIO 的 Selector 和 EventLoop 模型，也可在支持的平台使用原生 epoll、kqueue 等传输；它还通过线程模型、内存池、ByteBuf、批量处理和部分零拷贝能力减少分配与数据复制开销。

因此，它们的共同点是用少量线程管理大量连接，并尽量减少阻塞、线程切换、内存分配和数据复制。实际性能仍受业务逻辑、连接活跃度、数据大小、系统配置和硬件条件影响。

零拷贝

1. 零拷贝是什么？

零拷贝是一类减少数据在用户空间与内核空间之间的 CPU 拷贝和上下文切换的技术。“零”通常不是指整个链路完全没有任何数据移动，而是尽量避免由 CPU 执行不必要的中间复制。

例如传统文件发送可能经历：磁盘数据进入内核页缓存，再复制到用户缓冲区，然后复制回套接字缓冲区，最后由 DMA 发送到网卡。使用 Linux 的 sendfile()，内核可以直接在文件和套接字之间传递数据，避免数据先进入用户空间；部分硬件和内核还可以通过描述符传递进一步减少实际数据复制。

常见相关机制包括 sendfile、splice、mmap、writev，以及应用层通过缓冲区切片或组合避免复制。它们减少的拷贝阶段并不完全相同，也有各自的文件类型、协议和平台限制。

零拷贝适合文件传输、代理转发等大数据搬运场景。如果应用必须在用户态解析、修改或加密数据，就不一定能绕过用户空间；小数据场景下，系统调用和管理成本也可能抵消收益，所以仍要结合实际链路和压测结果选择。
