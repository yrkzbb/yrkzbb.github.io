## HTTP 基础

### 1. HTTP 报文由哪些部分组成？

从语义上看，HTTP 报文由**起始信息、头字段和可选的消息体**组成。在 HTTP/1.x 的文本报文中，具体表现为起始行、请求头或响应头、空行和消息体四部分。

#### 请求报文

```http
POST /users HTTP/1.1
Host: example.com
Content-Type: application/json
Content-Length: 16

{"name":"Alice"}
```

- **请求行**：包含请求方法、请求目标和 HTTP 版本，例如 `POST /users HTTP/1.1`。
- **请求头**：描述主机、内容类型、认证、缓存等元数据，例如 `Host`、`Content-Type`、`Authorization`。
- **空行**：在 HTTP/1.x 中用来分隔头部和消息体。
- **请求体**：可选，承载 JSON、表单或文件等数据。`GET` 通常不使用请求体。

#### 响应报文

```http
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 11

{"ok":true}
```

- **状态行**：包含 HTTP 版本、状态码和原因短语，例如 `HTTP/1.1 200 OK`。
- **响应头**：描述响应内容、缓存、Cookie 等信息，例如 `Content-Type`、`Cache-Control`、`Set-Cookie`。
- **空行**：分隔头部和响应体。
- **响应体**：可选，承载 HTML、JSON、图片或文件等内容。例如 `204` 响应就不包含消息体。

### 2. HTTP 常用状态码有哪些？

HTTP 状态码的第一位表示大类：`1xx` 是信息响应，`2xx` 表示成功，`3xx` 表示重定向或缓存协商，`4xx` 表示客户端错误，`5xx` 表示服务端错误。

| 状态码                      | 含义                       | 常见场景                                    |
| --------------------------- | -------------------------- | ------------------------------------------- |
| `100 Continue`              | 可以继续发送请求体         | 客户端使用 `Expect: 100-continue`           |
| `200 OK`                    | 请求成功                   | 成功查询或处理请求                          |
| `201 Created`               | 成功创建资源               | `POST` 新建资源                             |
| `204 No Content`            | 请求成功，但无响应体       | 成功删除或无需返回数据的更新                |
| `**301** Moved Permanently` | 资源永久迁移               | 域名或 URL 永久更换                         |
| `**302** Found`             | 资源临时位于另一地址       | 临时跳转                                    |
| `304 Not Modified`          | 缓存协商命中，资源未变更   | 配合 `If-None-Match` 或 `If-Modified-Since` |
| `400 Bad Request`           | 请求语法或参数有误         | JSON 格式错误、缺少必需参数                 |
| `401 Unauthorized`          | 缺少有效身份认证           | 未登录、Token 无效或过期                    |
| `403 Forbidden`             | 服务器理解请求，但拒绝执行 | 身份已识别但没有资源权限                    |
| `404 Not Found`             | 找不到目标资源             | URL 或业务资源不存在                        |
| `405 Method Not Allowed`    | 资源不允许该请求方法       | 对只读接口发送 `POST`                       |
| `409 Conflict`              | 请求与资源当前状态冲突     | 重复创建、版本冲突                          |
| `429 Too Many Requests`     | 请求过多                   | 触发限流                                    |
| `500 Internal Server Error` | 服务器内部异常             | 未处理异常或程序错误                        |
| `**502** Bad Gateway`       | 网关从上游收到无效响应     | 上游服务异常或连接失败                      |
| `503 Service Unavailable`   | 服务当前不可用             | 过载、维护或临时降级                        |
| `**504** Gateway Timeout`   | 网关等待上游响应超时       | 上游服务处理过慢                            |

需要注意，`401` 的名称虽然是 Unauthorized，实际语义主要是“缺少有效认证凭据”；已经完成身份识别但没有权限时，通常使用 `403`。

### 3. HTTP `502` 和 `504` 有什么区别？

`502` 和 `504` 通常都是网关或反向代理返回的错误。核心区别是：**`502` 表示已经从上游收到了无效响应，或者无法正常建立上游连接；`504` 表示等待上游响应超时**。

- **`502 Bad Gateway`**：上游进程崩溃、端口未监听、连接被拒绝或重置，或上游返回了代理无法解析的响应，都可能导致 `502`。
- **`504 Gateway Timeout`**：网关通常已经尝试访问上游，但上游处理过慢、下游依赖阻塞或网络延迟过高，在规定时间内没有得到响应。

排查时，`502` 优先检查上游实例状态、端口、连接和协议是否正常；`504` 优先检查上游耗时、慢 SQL、连接池、下游依赖和代理超时配置。不过不同网关的错误映射可能有差异，最终要结合代理和上游日志判断。

### 4. HTTP 常用的请求方法有哪些？

HTTP 请求方法用来表达客户端希望对资源执行什么操作。常见方法有：

| 方法      | 常见语义                                     | 安全性与幂等性                    |
| --------- | -------------------------------------------- | --------------------------------- |
| `GET`     | 获取资源                                     | 安全、幂等                        |
| `HEAD`    | 只获取与 `GET` 相同的响应头，不返回响应体    | 安全、幂等                        |
| `POST`    | 提交数据进行处理，常用于新建子资源或执行动作 | 通常不幂等                        |
| `PUT`     | 用请求内容创建或整体替换目标资源             | 幂等                              |
| `PATCH`   | 部分更新资源                                 | 不默认保证幂等，取决于补丁语义    |
| `DELETE`  | 删除目标资源                                 | 幂等                              |
| `OPTIONS` | 查询服务器或资源支持的通信选项               | 安全、幂等，常见于 CORS 预检      |
| `CONNECT` | 让代理建立到目标的隧道                       | 常用于经 HTTP 代理建立 HTTPS 连接 |
| `TRACE`   | 请求服务器回显收到的请求，用于诊断           | 实际服务中常因安全考虑禁用        |

### 5. `GET` 和 `POST` 分别适合什么场景，有哪些区别？

核心区别是语义：**`GET` 用于获取资源，原则上不应产生业务副作用；`POST` 用于向服务器提交数据进行处理，常用于创建资源或执行动作**。

GET 主要用于查询资源，POST 主要用于提交数据或创建资源。

GET 通常是安全且幂等的，多次请求不会改变服务器状态；POST 通常会改变服务器状态，一般不保证幂等。GET 参数通常放在 URL 中，容易被缓存、收藏和记录，而且受 URL 长度限制；POST 数据通常放在请求体中，更适合表单提交、复杂数据和文件上传。

安全性方面，POST 并不天然比 GET 安全，真正的传输安全依赖 HTTPS，只是敏感数据不应该放在 URL 中。

简单来说，查询、搜索和分页用 GET，创建资源、表单提交和文件上传用 POST，核心还是根据 HTTP 语义选择。

### 6. HTTP 长连接是什么？

HTTP 长连接，也叫持久连接，是指**一次 HTTP 请求响应结束后不立即关闭底层连接，后续请求继续复用它**。这样可以避免每次请求都重新建立 TCP 连接，HTTPS 还能减少重复 TLS 握手，从而降低延迟和 CPU 开销。

HTTP/1.0 默认是短连接，需要设置 `Connection: keep-alive`；HTTP/1.1 默认开启长连接，通过 `Connection: close` 才会关闭。

需要注意，HTTP 长连接只是复用底层连接，并不等于 WebSocket。HTTP 通常仍然是客户端发起请求、服务端响应；WebSocket 才支持真正的全双工通信。

### 7. HTTP 的默认端口是什么？

**HTTP 的默认端口是 `80`，HTTPS 的默认端口是 `443`**。所谓默认端口，是指 URL 没有显式指定端口时，客户端根据 URI Scheme 选择的端口。

### 8. HTTP/1.1 如何判断请求边界？

HTTP/1.1 解析器需要**先以 `CRLF CRLF`，即 `\r\n\r\n`，找到请求头结束位置，再根据头字段确定消息体长度**。

> HTTP/1.1 是基于 TCP 字节流传输的，TCP 本身没有消息边界，所以 HTTP 必须通过协议字段判断一个请求在哪里结束。
>
> 首先，请求行和请求头按行解析，遇到空行，也就是 `\r\n\r\n`，表示请求头结束。
>
> 如果请求没有请求体，那么空行就是整个请求的结束；如果有请求体，通常通过两种方式确定边界：
>
> - 有 `Content-Length` 时，再读取指定长度的字节。
> - 有 `Transfer-Encoding: chunked` 时，按照分块格式读取，直到长度为 0 的分块结束。
>
> 如果两者同时出现，应优先按 `Transfer-Encoding` 处理或直接拒绝，因为不同组件解析规则不一致可能导致 HTTP 请求走私。
>
> 另外，某些请求可以根据方法和语义判断没有请求体；如果既不能确定长度，也不是分块传输，为避免把后续请求误当作请求体，服务器通常会拒绝请求或关闭连接。
>
> 一句话总结：**先用空行确定请求头边界，再通过 `Content-Length` 或 `chunked` 确定请求体边界。**

### 9. HTTP 断点续传是什么？

HTTP 断点续传就是文件下载中断后，从已经下载的位置继续传输，不需要重新下载整个文件。对下载来说，它主要基于 HTTP 的 **Range Request** 机制。

它主要通过范围请求实现。客户端记录已下载的字节数，重新请求时携带 `Range: bytes=1000-`；服务器如果支持，就返回 `206 Partial Content`，并通过 `Content-Range` 告诉客户端返回的数据范围和文件总大小。

例如，客户端已下载前 1000 字节，可以请求从第 1000 字节继续：

```http
GET /video.mp4 HTTP/1.1
Host: example.com
Range: bytes=1000-
```

服务器支持该范围时，返回 `206 Partial Content`：

```http
HTTP/1.1 206 Partial Content
Accept-Ranges: bytes
Content-Range: bytes 1000-9999/10000
Content-Length: 9000
```

`Content-Range` 表示本次返回的字节区间和完整资源大小。如果请求范围不可满足，服务器可以返回 `416 Range Not Satisfiable`。

为了防止中断期间文件已经变更，客户端可以保存 `ETag` 或 `Last-Modified`，续传时通过 `If-Range` 让服务器校验资源版本。版本不匹配时应重新下载完整文件，避免拼接出错误内容。

简单来说，就是通过 **`Range` 指定续传位置，`206` 返回部分数据，`ETag` 或 `Last-Modified` 校验文件版本**。

### 10. HTTP 为什么不安全？

这里通常说的是**明文 HTTP 不提供加密、完整性保护和服务器身份认证**，而不是说 HTTP 这个应用层语义本身必然导致安全漏洞。

- **不保密**：请求和响应以明文传输，路径上的网络节点可能窃听 Cookie、Token、请求参数和响应内容。
- **不保证完整性**：攻击者可能篡改传输内容，例如替换页面脚本、修改下载文件或注入广告，通信双方无法仅靠 HTTP 发现。
- **不验证通信对方身份**：客户端无法仅靠明文 HTTP 确认连接的是真实服务器，容易受到 DNS 欺骗、中间人攻击或恶意代理的影响。

HTTPS 在 HTTP 与传输层之间使用 TLS，通过加密、消息认证和数字证书解决传输途中的保密性、完整性和服务器身份认证问题。但 HTTPS 不会自动解决 SQL 注入、XSS、CSRF、越权和业务逻辑漏洞，这些仍需要应用层安全措施。

## HTTP、HTTPS 与网络通信

### 1. HTTP 和 HTTPS 的区别？

核心区别是：HTTPS 不是一种完全独立的新协议，而是运行在 TLS 之上的 HTTP。HTTP 数据通常以明文传输；HTTPS 通过 TLS 提供加密、完整性校验和身份认证。

- **安全性**：HTTP 报文可能被窃听或篡改；HTTPS 可以降低窃听、篡改和冒充服务器的风险。
- **默认端口**：HTTP 通常使用 `80`，HTTPS 通常使用 `443`。
- **连接过程**：HTTP 建立 TCP 连接后即可传输 HTTP 报文；传统 HTTPS 在 TCP 连接之上还要进行 TLS 握手。
- **证书**：HTTPS 协议需要向 CA 申请数字证书，来保证服务器的身份是可信的。

### 2. HTTPS 的握手过程？

HTTPS 一般先建立底层连接，再进行 TLS 握手，握手成功后才传输加密的 HTTP 数据。以目前常见的 TLS 1.3 完整握手为例：

1.  客户端发送 `ClientHello`，其中包含支持的 TLS 版本、密码套件、随机数等等。
2.  服务端回复 `ServerHello`，选择 TLS 版本和密码套件，并返回自己的密钥交换参数。双方据此计算共享密钥。
3.  服务端发送证书、证书验证签名以及握手完成消息，证明自己持有证书对应的私钥。
4.  客户端校验证书、有效期、域名、吊销状态等，并验证服务端签名。
5.  客户端发送握手完成消息。双方确认此前的握手消息未被篡改，并派生出会话密钥。
6.  后续 HTTP 报文使用对称加密传输，同时进行完整性保护。

### 3. HTTPS 是如何防范中间人攻击的？

HTTPS 主要通过“证书身份认证、密钥协商和完整性校验”防范中间人攻击，而不仅仅是对数据加密。

HTTPS 的核心是：**用 CA 证书确认对方身份，用密钥交换建立只有双方知道的会话密钥，再用加密和完整性校验防止数据被窃听或篡改。**

### 4. HTTP/1.1 和 HTTP/2 的区别是什么？

HTTP/2 的主要改进是采用二进制分帧，并在一条连接上多路复用多个请求和响应，从而减少 HTTP/1.1 并发传输时对多条 TCP 连接的依赖。两者的请求方法、状态码、URI 等核心语义基本一致。

- **报文格式**：HTTP/1.1 使用文本格式；HTTP/2 将消息拆成二进制帧。
- **并发方式**：HTTP/1.1 的同一连接通常按顺序处理响应。HTTP/2 可在一条连接中交错传输多个流。
- **首部压缩**：HTTP/1.1 的请求会重复携带许多首部；HTTP/2 使用 HPACK 压缩首部。

### 5. HTTP 建立 TCP 连接后，在什么情况下会中断？

TCP 连接可能正常关闭，也可能异常中断，不能只由 HTTP 协议单方面决定。

- HTTP/1.0 默认通常是短连接，请求响应结束后关闭；HTTP/1.1 默认使用持久连接，但任一方可以发送 `Connection: close`，在本次响应完成后关闭连接。
- 客户端、服务端或代理设置了空闲超时、请求超时、最大连接时长或单连接最大请求数，达到条件后会关闭连接。
- 应用进程退出、服务器重启、客户端关闭页面或取消请求时，连接可能被关闭。
- 网络断开、NAT 映射失效、防火墙清理连接，或者发生 TCP 重传超时，也可能使连接失效。
- 收到 TCP `RST`、协议解析失败、TLS 错误或资源不足时，连接可能被异常终止。

正常关闭一般通过 TCP 的 `FIN`/`ACK` 完成；异常终止常表现为 `RST` 或超时。

### 6. HTTP、Socket 和 TCP 的区别？

三者不在同一个抽象层次：HTTP（超文本传输协议）是应用层协议，TCP 是传输层协议，Socket 是操作系统提供给应用程序使用网络通信能力的通信接口。

- **HTTP** 是一种用于传输超文本数据的应用层协议，用于在客户端和服务器之间传输和显示 Web 页面。
- **TCP** 提供面向连接、可靠、有序的字节流传输，负责在通信的两端之间建立可靠的数据传输连接。
- **Socket** 是通信的一端，提供了网络通信的接口，可实现不同计算机之间的数据交换。

### 7. HTTP 到底是不是无状态的？

HTTP 协议本身是无状态的：每个请求原则上都应包含完成处理所需的信息，协议不会自动记住前一次请求对应的是谁、做过什么。但使用 HTTP 的应用可以借助 Cookie、服务端 Session、Token、URL 参数或数据库，把多个独立请求关联到同一用户或会话。因此，“HTTP 无状态”描述的是协议默认的请求处理模型，不是说整个 Web 应用没有状态。

### 8. 携带 Cookie 的 HTTP 请求是有状态还是无状态的？Cookie 是 HTTP 协议簇的一部分，为什么还说 HTTP 是无状态的？

携带 Cookie 不会改变 HTTP 协议本身无状态的性质，但它可以让上层应用表现为“有会话状态”。关键在于区分协议是否自动保存上下文，以及应用是否显式携带状态标识。

**提供传递状态标识的能力，不等于协议自身维护状态**。HTTP 是无状态的通信协议，Cookie 是在无状态协议之上携带上下文的机制；它能帮助应用实现状态，但不会把 HTTP 本身变成有状态协议。

## 会话管理与身份认证

### 1. Cookie 和 Session 有什么区别？

核心区别是：Cookie 主要保存在客户端，Session 通常保存在服务端。两者经常配合使用，但不是同一个层次的概念。

- **存储位置**：Cookie 由浏览器保存；Session 数据一般保存在服务端内存、数据库或 Redis 中。
- **传输方式**：符合域名、路径等条件的 Cookie 会随 HTTP 请求自动发送。Session 本身不会发送给客户端，客户端通常只携带一个 `session_id`，服务端据此查找会话数据。
- **容量和开销**：Cookie 容量较小，且随请求传输会增加网络开销；Session 可存更多数据，但会占用服务端存储，并涉及过期清理和集群共享。
- **安全性**：Session 数据不直接暴露给客户端，但 `session_id` 一旦被盗仍可能造成会话劫持。Cookie 应根据场景设置 `HttpOnly`、`Secure`、`SameSite` 等属性，并全程使用 HTTPS。
- **生命周期**：Cookie 可设置过期时间；Session 的有效期由服务端控制，通常在超时、退出登录或服务端删除后失效。

### 2. Token、Session 和 Cookie 有什么区别？

Cookie 是客户端存储和自动传输数据的机制，Session 是服务端保存会话状态的方案，Token 则是客户端请求时携带的访问凭证。

- **Session 认证**：登录后服务端创建 Session，客户端保存 `session_id`。后续请求携带该标识，服务端查询 Session 并确认用户身份。
- **Token 认证**：服务端签发 Token，客户端后续提交 Token。Token 可以是无结构的随机字符串，也可以是 JWT；前者通常仍要到服务端存储中查询，JWT 则可以在验证签名后读取声明。
- **Cookie**：既可以保存 `session_id`，也可以保存 Token。它解决的是浏览器如何存储和发送凭证，不直接决定服务端采用 Session 还是 Token 认证。

### 3. 如果客户端禁用了 Cookie，Session 还能用吗？

能，但前提是通过其他方式把 Session 标识传给服务端。Session 数据在服务端，Cookie 只是浏览器传递 `session_id` 最常见的载体，所以禁用 Cookie 不等于服务端不能创建 Session。

替代方式包括把会话标识放在自定义请求头、表单字段或 URL 中。不过 URL 重写容易让会话标识进入浏览器历史、日志和 `Referer`，还可能被复制分享，泄露风险较高。

如果系统完全依赖 Cookie 传递 `session_id`，而且没有实现替代机制，那么客户端禁用 Cookie 后就无法维持该 Session 会话。

### 4. 把数据存到 localStorage，和 Cookie 有什么区别？

最关键的区别是：Cookie 可以由浏览器按规则自动附加到 HTTP 请求中，`localStorage` 不会自动发送，JavaScript 需要主动读取并使用。

- **容量**：单个 Cookie 通常只有约 4 KB；`localStorage` 一般有数 MB，但具体配额取决于浏览器和站点策略。
- **生命周期**：Cookie 可以设置会话期或明确的过期时间；`localStorage` 默认长期保留，直到代码或用户主动清除。
- **访问方式**：Cookie 可以设置 `HttpOnly`，让 JavaScript 无法读取；`localStorage` 始终可被同源页面的 JavaScript 访问。
- **请求开销**：匹配作用域的 Cookie 会随请求发送；`localStorage` 不会增加每次请求的 Cookie 首部大小。
- **作用域**：Cookie 可设置 `Domain`、`Path`、`SameSite` 等规则；`localStorage` 主要按源，也就是协议、主机和端口隔离。

### 5. 什么数据应该存在 Cookie，什么数据存放到 localStorage？

需要由服务端随请求自动接收、容量很小的数据适合 Cookie；只供前端使用、体积相对较大且不敏感的数据更适合 `localStorage`。

- **Cookie**：常用于 `session_id`、刷新令牌以及少量需要服务端感知的偏好。认证凭证通常优先放在设置了 `HttpOnly`、`Secure` 和合适 `SameSite` 属性的 Cookie 中。
- **`localStorage`**：适合主题、语言、非敏感的页面配置、草稿或前端缓存。只有当前端代码确实需要读取时才放这里。
- **都不适合**：密码、银行卡号、私钥等高敏感数据不应长期保存在二者中；超大或结构复杂的数据更适合 IndexedDB 等方案。

### 6. JWT 令牌和传统 Session 方式有什么区别？

与传统 Session 认证相比，JWT 常见用法的核心区别是把一部分身份和授权声明放进签名令牌，由服务端验证签名，而不是每次拿 `session_id` 查询服务端会话。

- **状态位置**：Session 的会话状态主要在服务端；自包含 JWT 的声明主要由客户端携带。
- **校验方式**：Session 通常要查询内存、数据库或 Redis；JWT 通常本地验证签名、签发方、受众和有效期。
- **扩展性**：JWT 便于多个服务使用同一验证规则，减少共享 Session 查询；Session 则需要粘性会话或共享会话存储。
- **撤销能力**：Session 可以在服务端立即删除；JWT 在到期前通常仍有效，若要求立即撤销，需要黑名单、版本号或其他服务端状态。
- **数据大小**：Session ID 通常很短；JWT 包含头部、声明和签名，请求体积更大。

JWT 不是天然更安全，也不一定更快。如果系统必须频繁查询权限或维护撤销状态，JWT 的“无状态”优势会减弱。选择时要结合系统架构、失效要求和请求规模。

### 7. JWT 令牌都有哪些字段？

常见的已签名 JWT 由三部分组成，中间用 `.` 分隔：`Header.Payload.Signature`。

1.  **Header**：描述令牌类型和签名算法，常见字段有 `typ` 和 `alg`，还可能包含密钥标识 `kid`。
2.  **Payload**：存放 Claims，也就是声明。标准注册声明包括签发方 `iss`、主题 `sub`、受众 `aud`、过期时间 `exp`、生效时间 `nbf`、签发时间 `iat` 和唯一标识 `jti`，还可以放业务自定义声明。
3.  **Signature**：对编码后的 Header 和 Payload 进行签名或 MAC 计算，用来验证内容是否被篡改以及签发者是否可信。

### 8. JWT 为什么便于集群部署？什么是集群部署？

集群部署是把同一个服务运行在多台机器或多个实例上，再通过负载均衡分发请求，用于提高吞吐量、可用性和横向扩展能力。

传统本地 Session 会带来一个问题：用户第一次登录落到实例 A，下一次请求若落到实例 B，B 的本地内存中可能没有该 Session。通常要使用粘性会话，或者把 Session 放到 Redis 等共享存储中。

自包含 JWT 将身份声明交给客户端携带。只要集群中的实例拥有正确的验签密钥并执行相同的校验规则，任意实例都可以验证令牌，不必读取某台机器上的本地 Session，所以更适合无状态横向扩容。

### 9. JWT 的缺点是什么？

JWT 的主要缺点是签发后难以立即撤销，而且令牌体积、信息暴露和密钥管理都需要额外关注。

- **撤销困难**：自包含 JWT 在 `exp` 到期前通常一直有效。若维护黑名单，又会引入服务端状态和查询开销。
- **令牌较大**：JWT 比随机 Session ID 长，每次请求携带都会增加网络开销，不适合放入过多声明。
- **Payload 默认不保密**：签名保证完整性和来源，不等于加密，客户端可以解码看到内容。
- **权限可能过期**：用户权限已被修改，但旧 JWT 中的声明可能在令牌过期前仍然有效。
- **密钥管理复杂**：算法选择、密钥保管和轮换不当会直接影响安全；服务端还必须严格校验 `alg`、`iss`、`aud`、`exp` 等字段。

因此 JWT 更适合短期访问凭证和跨服务验证，不应把“完全无状态”当成必须追求的目标。

### 10. JWT 泄露后怎么办？JWT 自身是怎么处理的？

JWT 泄露后，攻击者在 Token 过期前都可以冒用。JWT 本身不会自动失效，也无法直接收回。  
处理上先撤销 Refresh Token；Access Token 可以通过 Redis 黑名单或用户的 tokenVersion 立即失效。如果是签名密钥泄露，还要立刻轮换密钥。  
设计上采用短有效期的 Access Token，加上可撤销、可轮换的 Refresh Token，来缩小风险窗口。

### 11. 前端如何存储 JWT？

常见方案是把 Refresh Token 放在 `HttpOnly`、`Secure`、适当设置 `SameSite` 的 Cookie 中，把短期 Access Token 仅保存在内存中。

- 放在 `localStorage` 或 `sessionStorage` 中实现简单，也方便设置 `Authorization: Bearer`，但发生 XSS 时恶意脚本可以直接读取令牌；其中 `sessionStorage` 只是在标签页生命周期和共享范围上不同，不能解决 XSS。
- 放在 `HttpOnly` Cookie 中可以避免 JavaScript 直接读取，但浏览器会自动携带 Cookie，需要根据跨站场景配置 `SameSite`，并在必要时增加 CSRF Token、校验 `Origin` 等防护。
- 只放内存可以减少持久泄露风险，但刷新页面后会丢失，通常要配合受保护的 Refresh Token 换取新的 Access Token。

## HTTP、RPC 与实时通信

### 1. 为什么有 HTTP 协议了，还要用 RPC？

HTTP 主要定义通用的应用层通信语义，而 RPC 解决的是如何像调用本地函数一样调用远程服务，包括接口定义、参数序列化、代码生成、服务发现、超时、重试和错误模型等问题。二者不是替代关系，RPC 完全可以基于 HTTP 实现，例如 gRPC 通常基于 HTTP/2。

面向浏览器、开放平台和跨语言兼容时，HTTP/JSON 接口通用、易调试、生态成熟，通常更合适。内部微服务调用如果接口数量多、性能和类型约束要求高，RPC 配合 Protobuf 等二进制序列化，可以提供明确的接口契约、自动生成客户端代码和较小的报文。

### 2. HTTP 长连接与 WebSocket 有什么区别？

HTTP 长连接主要是复用底层连接，WebSocket 则是在一条长连接上提供全双工、双向主动通信。保持连接不断开不等于通信模型相同。

- **通信模式**：传统 HTTP 仍以请求—响应为核心，通常由客户端发起请求；WebSocket 建立后，客户端和服务端都能随时主动发送消息。
- **协议格式**：HTTP/1.1 长连接会重复传输 HTTP 首部；WebSocket 建立后使用较轻量的帧格式传输文本或二进制消息。
- **建立过程**：经典 WebSocket 先通过 HTTP/1.1 `Upgrade` 握手切换协议；建立后传输的已不再是普通 HTTP 请求和响应。新版协议栈也支持通过 HTTP/2 或 HTTP/3 建立 WebSocket，但语义仍是双向消息通道。
- **适用场景**：HTTP 长连接适合复用请求、减少握手；WebSocket 适合聊天、实时协作、行情推送和在线游戏等高频双向通信。

如果只需要服务端单向推送，也可以考虑 SSE；请求频率很低时，普通 HTTP 轮询可能更简单。选择应结合通信方向、实时性、连接规模及代理支持情况。

## Nginx

### 1. Nginx 有哪些负载均衡算法？

Nginx 常见的负载均衡方法包括轮询、加权轮询、最少连接、IP 哈希和通用哈希；

- **轮询**：默认方法，请求依次分配到各上游服务器。
- **加权轮询**：通过 `weight` 让性能更强的节点接收更高比例的请求；权重也是其他部分算法可使用的服务器参数，不是完全独立的调度器。
- **最少连接**：使用 `least_conn`，优先选择当前活动连接较少的节点，适合请求耗时差异较大的场景。
- **IP 哈希**：使用 `ip_hash`，根据客户端 IP 选择节点，可实现一定程度的会话粘滞，但代理、NAT 和节点变化会影响分布效果。
- **通用哈希**：使用 `hash key [consistent]`，可以按 URI、用户 ID 等键分配；`consistent` 可减少节点变化时的重映射。
- **最短响应时间**：`least_time` 会综合响应时间和活动连接数选择节点，但其可用范围取决于 Nginx 产品和版本，不能默认视为所有开源环境都支持。

### 2. Nginx 位于七层网络结构中的哪一层？

作为 HTTP/HTTPS 反向代理时，Nginx 能解析域名、URI、请求头等 HTTP 语义，因此通常称为七层负载均衡，也就是 OSI 的应用层。

## DNS

### 1. DNS 的全称是什么？

DNS 的全称是 **Domain Name System**，称为“域名系统”。它是一个分布式、分层的命名系统，主要负责把域名解析为 IP 地址。

### 2. DNS 域名解析的工作流程？

以查询 `www.ccnu.edu.com` 的 IP 地址为例，通常流程如下：

（1）在浏览器地址栏输入地址 `www.ccnu.edu.cn`。

（2）先在本机域名解析的缓存中查找该域名，若找到则可以立即获取对应的 IP 地址。

（3）若不在本机缓存中，则向本地 DNS 服务器发送请求，请求解析域名。

（4）DNS 收到请求后查找自己的缓存表，若查到则发送；反之向上级 DNS 服务器提出请求，直到解析成功或返回错误信息。

### 3. DNS 的端口是多少？

默认使用 `53` 端口

### 4. 改过 hosts 文件吗？

改过。`hosts` 文件用于在本机静态配置“主机名到 IP 地址”的映射。

例如在 Linux 和 macOS 的 `/etc/hosts` 中加入：

```text
127.0.0.1 api.example.test
```

之后本机访问 `api.example.test` 时，通常会直接解析到 `127.0.0.1`，不再向 DNS 服务器查询。修改后要注意权限、本地 DNS 缓存和代理缓存；它只影响当前主机，也不支持像 DNS 那样配置 TTL 或通配域名。

### 5. DNS 底层使用 TCP 还是 UDP？

传统 DNS 两者都使用。普通查询通常优先使用 UDP，因为无需建立连接、开销较小。

当 UDP 响应被截断时，响应会设置 `TC` 标志，客户端通常再使用 TCP 重试。借助 EDNS(0)，UDP DNS 报文也可以超过早期的 512 字节限制，但实际大小还要考虑网络 MTU 和分片风险。区域传送 `AXFR`、`IXFR` 使用 TCP；现代实现也可能为了可靠性、连接复用或隐私直接选择 TCP、DoT（853端口）、DoH（443端口） 或 DoQ。
