## MySQL 执行流程

### 1. 执行一条 SQL 请求的过程是什么？

一条查询 SQL 的整体流程可以概括为：`连接器 → 查询缓存（MySQL 8.0 已移除）→ 解析器 → 预处理器 → 优化器 → 执行器 → 存储引擎`。

![MySQL 执行一条 SQL 查询语句的流程](../img/mysql-sql-execution-flow.png)

1. **连接器**：与客户端建立连接，完成身份认证，并获取该用户的权限信息。
2. **查询缓存**：如果完全相同的查询命中缓存，就直接返回结果；由于表更新会使相关缓存失效，MySQL 8.0 已经移除了该模块。
3. **解析器**：对 SQL 进行词法和语法分析，识别关键字、表名和字段，并构建语法树；语法错误会在这一阶段被发现。
4. **预处理阶段**：检查表和字段是否存在，将 `SELECT *` 展开为具体字段，并进行相关校验。
5. **优化阶段**：根据索引、统计信息和执行成本，选择成本较低的索引、表连接顺序及执行方式，生成执行计划。
6. **执行阶段**：执行器按照执行计划调用存储引擎接口读取或修改数据，并将结果返回给客户端。
7. **存储引擎**：真正负责数据的存取。以 InnoDB 为例，它会通过索引查找记录，并涉及缓冲池、事务、锁和日志等机制。

面试时我会概括为：客户端先通过连接器建立连接，然后 SQL 经过解析器生成语法树；执行 SQL 时再依次经过预处理、优化和执行三个阶段，最后由执行器调用存储引擎读取数据并返回结果。MySQL 8.0 已经移除了查询缓存。

## MySQL 存储引擎

### 1. 讲一讲 MySQL 的引擎吧，你有什么了解？

存储引擎是 MySQL 中真正负责数据存储和读取的组件，采用插件化设计，可以在建表时通过 `ENGINE` 指定。不同存储引擎在事务、锁粒度、索引和适用场景等方面有所区别。

- **InnoDB**：MySQL 默认的存储引擎，支持事务、行级锁、MVCC、外键和崩溃恢复，适合绝大多数高并发读写及要求数据一致性的业务场景。
- **MyISAM**：不支持事务和外键，只支持表级锁，读性能较好但并发写能力和崩溃恢复能力较弱，实际业务中已经较少使用。
- **Memory**：数据主要存放在内存中，访问速度快，但数据库重启后数据会丢失；只支持表级锁，适合临时数据或中间结果。
- **Archive**：支持高压缩比，适合大量写入、很少修改的归档数据，但查询和索引能力有限。

实际项目中我通常会优先选择 InnoDB，因为它在事务、并发控制和可靠性方面更完善。只有在临时表、归档等特殊场景下，才会考虑其他存储引擎。可以通过 `SHOW ENGINES;` 查看当前 MySQL 支持的存储引擎。

### 2. MySQL 为什么使用 InnoDB 作为默认存储引擎？

MySQL 将 InnoDB 作为默认存储引擎，主要是因为它在数据可靠性和并发性能之间取得了较好的平衡：

1. **支持事务**：InnoDB 支持 ACID，可以通过提交和回滚保证业务操作的一致性。
2. **并发性能较好**：它支持行级锁和 MVCC，读写之间的阻塞较少，适合高并发场景。
3. **支持崩溃恢复**：InnoDB 通过 redo log、undo log 等机制，在数据库异常宕机后恢复数据，保证持久性和一致性。
4. **支持外键约束**：可以在数据库层面维护表之间的引用完整性。
5. **索引与缓存机制完善**：InnoDB 使用 B+ 树索引和 Buffer Pool，能够减少磁盘 I/O，提高查询和写入效率。

相比之下，MyISAM 不支持事务和行级锁，发生异常后恢复能力也较弱。因此对于绝大多数需要事务、高并发和可靠性的业务，InnoDB 更适合作为默认存储引擎。

### 3. 说一下 MySQL 中 InnoDB 与 MyISAM 的区别？

InnoDB 和 MyISAM 的主要区别有以下几点：

1. **事务**：InnoDB 支持事务和 ACID，MyISAM 不支持事务。
2. **锁粒度**：InnoDB 支持行级锁和表级锁，并通过 MVCC 提高并发性能；MyISAM 主要使用表级锁，并发写能力较弱。
3. **外键**：InnoDB 支持外键约束，MyISAM 不支持。
4. **崩溃恢复**：InnoDB 通过 redo log、undo log 等机制支持崩溃恢复；MyISAM 的恢复能力较弱，异常宕机后表可能损坏。
5. **索引结构**：InnoDB 使用聚簇索引，主键索引的叶子节点保存完整行数据，二级索引保存主键值；MyISAM 使用非聚簇索引，索引与数据分开存储，索引叶子节点保存数据记录的地址。InnoDB 不要求用户必须显式创建主键：没有主键时，它会选择第一个非空唯一索引作为聚簇索引；如果也不存在，则自动生成隐藏的行 ID。
6. **行数统计**：MyISAM 会保存表的总行数，所以无条件的 `COUNT(*)` 可以直接读取；InnoDB 通常需要根据可见性统计记录，不能简单保存一个所有事务都适用的精确行数。

因此，要求事务、高并发和数据可靠性的业务一般选择 InnoDB。MyISAM 更适合以读取为主、对事务和并发写要求不高的旧有场景，但现在实际项目中通常优先使用 InnoDB。

## MySQL 数据文件

### 1. 数据管理中，MySQL 的数据文件大体分为哪些？

在 MySQL 5.7 及更早版本中，创建数据库后会在数据目录下生成同名目录，其中常见的文件主要有三类：

1. **`db.opt` 文件**：保存当前数据库默认使用的字符集和排序规则。
2. **`.frm` 文件**：保存表的元数据信息，主要是表结构定义，每张表通常对应一个 `.frm` 文件。
3. **`.ibd` 文件**：InnoDB 的独立表空间文件，用于保存表数据和索引。开启 `innodb_file_per_table` 后，每张表通常对应一个 `.ibd` 文件；如果未开启，数据也可以存放在 `ibdata1` 等共享表空间中。

MySQL 8.0 的文件结构发生了变化，主要包括：

1. **`mysql.ibd`**：MySQL 8.0 使用事务性数据字典，数据库、表、字段和索引等元数据主要保存在 `mysql.ibd` 中，不再使用 `db.opt` 和 `.frm` 文件。
2. **`表名.ibd`**：开启独立表空间时，每张 InnoDB 表对应一个 `.ibd` 文件，保存该表的数据、索引以及序列化字典信息（SDI）。
3. **`ibdata1`**：InnoDB 系统表空间文件，用于保存系统相关数据；如果未使用独立表空间，用户表数据也可能存放在其中。
4. **undo 和 redo 文件**：undo 表空间用于事务回滚和 MVCC，redo log 用于保证持久性和崩溃恢复。
5. **binlog 文件**：记录数据库的数据变更，主要用于主从复制和数据恢复；是否生成取决于二进制日志配置。

所以面试时可以概括为：旧版本常见的是 `db.opt`、`.frm` 和 `.ibd`；MySQL 8.0 将元数据统一放入事务性数据字典，用户表的数据和索引主要仍保存在 `.ibd` 表空间文件中，同时还有系统表空间、undo、redo 和 binlog 等文件。
