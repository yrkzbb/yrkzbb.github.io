## Redis 内存管理

### 1. 过期删除策略和内存淘汰策略有什么区别？

核心区别是：**过期删除处理的是 TTL 已到期的 Key，内存淘汰处理的是 Redis 达到 `maxmemory` 限制后的内存压力**。前者依据过期时间判断数据是否失效，后者依据配置的淘汰策略选择牺牲哪些 Key；被淘汰的 Key 不一定已经过期。

可以从以下方面对比：

| 对比项 | 过期删除 | 内存淘汰 |
| --- | --- | --- |
| 触发原因 | Key 的 TTL 已到期 | 内存达到或超过 `maxmemory`，且操作还需要使用内存 |
| 处理对象 | 已设置 TTL 并且已经过期的 Key | 根据 `maxmemory-policy`，可能是设置了 TTL 的 Key，也可能是所有 Key |
| 判断依据 | 过期时间 | LRU、LFU、随机、剩余 TTL 等策略 |
| 主要目的 | 清理已经失效的数据 | 在内存上限内继续提供服务 |
| 是否可能删除未过期数据 | 不会 | 会，取决于淘汰策略 |

Redis 通过惰性删除和周期性的主动删除共同清理过期 Key。Key 到达过期时间后在逻辑上已经失效，即使对应内存还没有被主动删除流程立即回收，客户端也不应再读到有效值。具体实现见第 3 题。

内存淘汰则是在内存达到 `maxmemory` 后，根据 `maxmemory-policy` 从候选 Key 中选择并删除数据。具体策略和选型见下一题。

举个例子：缓存 Key `user:1` 的 TTL 已经到期，它会被过期删除机制处理，与当前内存是否充足无关；而 `user:2` 还没有过期，但 Redis 已达到 `maxmemory`，如果配置的是 `allkeys-lru`，它仍可能因为近期很少访问而被淘汰。

### 2. 介绍一下 Redis 内存淘汰策略？

Redis 内存淘汰是指：当实例配置了 `maxmemory`，并且当前内存达到上限、操作还需要更多内存时，Redis 按照 `maxmemory-policy` 选择 Key 删除；如果策略不允许淘汰或没有候选 Key，则拒绝相关写请求。

淘汰过程可以概括为：

1. 处理需要使用内存的命令时，检查当前内存是否超过 `maxmemory`。
2. 根据淘汰策略确定候选范围，并通过抽样等方式选取候选 Key。
3. 删除候选 Key 并释放内存；如果仍超过上限，就继续淘汰。
4. 无法释放足够内存时，返回 OOM 错误。开启异步淘汰释放后，Key 可以先从键空间移除，再由后台线程释放较大的对象。

Redis 提供八种常见策略，可以分为三类：

| 策略 | 候选范围 | 选择方式 |
| --- | --- | --- |
| `noeviction` | 不选择 Key | 不淘汰，拒绝需要增加内存的写请求 |
| `allkeys-lru` | 所有 Key | 近似淘汰最近最少使用的 Key |
| `allkeys-lfu` | 所有 Key | 近似淘汰访问频率最低的 Key |
| `allkeys-random` | 所有 Key | 随机淘汰 |
| `volatile-lru` | 设置了 TTL 的 Key | 近似淘汰最近最少使用的 Key |
| `volatile-lfu` | 设置了 TTL 的 Key | 近似淘汰访问频率最低的 Key |
| `volatile-random` | 设置了 TTL 的 Key | 随机淘汰 |
| `volatile-ttl` | 设置了 TTL 的 Key | 优先淘汰剩余 TTL 较短的 Key |

其中，`allkeys-*` 可以从全部 Key 中淘汰；`volatile-*` 只处理设置了过期时间的 Key。如果使用 `volatile-*` 但实例中没有符合条件的 Key，Redis 无法靠淘汰释放内存，效果会接近 `noeviction`。

Redis 的 LRU 和 LFU 都是近似算法：它不会对全部 Key 维护一份严格排序，而是抽样一部分 Key，再从样本中选择更合适的淘汰对象。`maxmemory-samples` 越大，选择通常越接近理论结果，但采样本身的 CPU 开销也会增加。

- **LRU** 关注最近一次访问时间，适合热点随时间变化、最近访问的数据更可能再次被访问的场景。
- **LFU** 关注一段时间内的访问频率，并带有频率衰减，适合长期热点相对稳定的场景。
- **Random** 判断成本低，但命中率通常取决于数据分布，不保证保留热点数据。
- **TTL** 适合业务已经通过过期时间表达数据价值，希望先清理即将过期的数据。

选型时不能直接认为某一种策略一定最好：

- 纯缓存实例通常优先评估 `allkeys-lru` 或 `allkeys-lfu`，再根据真实命中率和访问分布选择。
- 数据不允许因为内存不足而被删除时使用 `noeviction`，同时做好容量监控和扩容，否则写请求会报错。
- 只有带 TTL 的数据允许被淘汰时可以考虑 `volatile-*`，但要确保有足够的候选 Key。
- 如果同一实例同时存放可淘汰缓存和不可丢失数据，更稳妥的方案通常是拆分实例，而不是仅依赖某个淘汰策略隔离风险。

实际排查时，我还会关注 `used_memory`、`maxmemory`、`evicted_keys`、缓存命中率、Big Key 和热点 Key。淘汰持续发生通常说明容量、TTL 或数据模型需要调整，而不只是简单更换淘汰算法。

### 3. 介绍一下 Redis 过期删除策略？

Redis 的过期删除采用**惰性删除 + 定期主动删除**，而不是只依赖其中一种。惰性删除保证访问过期 Key 时不会返回旧值，主动删除负责逐步清理那些到期后再也没有被访问的 Key，在 CPU 开销和内存回收速度之间做平衡。

当执行 `EXPIRE`、`PEXPIRE` 或 `SET ... EX/PX` 时，Redis 会为 Key 保存一个绝对的毫秒级过期时间。普通键空间保存实际数据，Redis 同时维护过期信息，以便判断 Key 是否到期。使用绝对时间意味着 Redis 停机期间时间仍会流逝，重启加载数据时已经到期的 Key 不会继续作为有效数据使用。

#### 惰性删除

客户端访问 Key 时，Redis 会检查它是否设置了过期时间以及是否已经到期：

- 没有过期，继续执行命令。
- 已经过期，先把 Key 从键空间删除，再按 Key 不存在处理。

这种方式只在访问时检查，CPU 开销比较有针对性；但如果大量过期 Key 再也没有被访问，它们可能在一段时间内仍占用内存，所以不能只使用惰性删除。

#### 定期主动删除

Redis 会在周期任务中运行主动过期循环，从带有过期时间的 Key 中抽取一部分进行检查，删除已经到期的 Key。它不会每次扫描全部 Key，而是设置时间预算，并根据抽样结果自适应地决定是否继续：如果发现过期 Key 较多，就增加清理工作；如果过期比例较低或达到时间上限，就结束本轮，把 CPU 让给正常请求。

主动过期循环通常还分为较完整的慢周期和耗时更短、调用更频繁的快周期。相关参数会受 Redis 的运行频率和 `active-expire-effort` 等配置影响，但核心原则是不让一次过期扫描长时间占用主线程。

网上常见的“每轮固定抽取 20 个 Key、过期比例超过 25% 就继续、最长执行 25ms”是对特定旧版本和默认配置的概括，不能作为所有 Redis 版本都不变的规则。当前实现仍然遵循“小批量抽样、根据过期比例决定是否继续、受时间预算约束”的思路，但抽样规模、可接受的过期比例和时间上限会受 Redis 版本、`hz` 以及 `active-expire-effort` 等因素影响。面试时应重点说明自适应抽样机制，而不是死记固定常量。

Redis 不采用“每个 Key 建一个定时器”，是因为海量定时器会带来较大的内存、调度和维护成本；也不采用固定的全量扫描，因为 Key 很多时会造成明显阻塞。抽样清理配合访问时检查，能以相对可控的成本保证过期数据最终被回收。

#### 删除后的处理

Key 过期后，不只是从主节点内存中移除。主节点还会把对应删除操作传播到 AOF 和副本，使持久化数据与主从节点保持一致。副本跟随主节点时通常依据主节点传播的删除操作处理过期 Key；当副本晋升为主节点后，才独立负责过期判断。

如果过期 Key 对应的是 Big Key，同步释放对象本身可能造成延迟。开启相应 Lazy Free 配置后，可以先从键空间解除关联，再让后台线程回收对象内存，但 Key 在逻辑上会立即失效。

所以过期时间并不承诺“到达这一毫秒时，内存一定立刻释放”，它承诺的是 Key 到期后不再作为有效数据返回，实际物理内存由惰性删除或主动删除随后回收。监控时可以结合 `expired_keys`、内存使用量以及延迟指标判断过期清理是否跟得上数据写入速度。

### 4. Redis 的缓存失效会不会立即删除？

不一定会立即从内存中删除，但 **Key 到期后会立即在逻辑上失效**。也就是说，TTL 到期和物理内存回收可能不在同一时刻发生，客户端正常访问时不会把已过期的值当作有效数据返回。

原因是 Redis 主要结合两种方式清理过期 Key：

- **惰性删除**：访问 Key 时检查 TTL，如果已过期就删除，并按 Key 不存在处理。
- **定期主动删除**：周期性地从设置了过期时间的 Key 中抽样检查并删除已过期数据，而不是在每个 Key 到期时扫描全部键空间。

因此，一个过期 Key 如果没有再被访问，可能要等到主动过期流程选中后才真正删除，在此之前仍可能占用内存。如果开启了过期异步释放，Key 可以先从键空间移除，其对象内存再由后台线程回收，这时物理内存的释放还会更晚一些。

### 5. Redis 为什么不在 Key 过期时立即删除？

核心原因是：**如果要在每个 Key 到期的瞬间精确删除，需要付出较高的计时、调度和删除成本，还可能影响正常请求的延迟**。Redis 选择惰性删除和定期主动删除，是在 CPU 消耗、内存占用和请求延迟之间做权衡。

如果要保证精确的即时删除，一般需要为每个设置 TTL 的 Key 维护定时任务，或持续精确检查最近到期的 Key。当 Key 数量很大、到期时间频繁变化时，维护这些结构和触发任务会消耗额外的 CPU 和内存。如果大量 Key 在同一时刻过期，集中删除还可能长时间占用主线程，造成延迟抖动。

而 Redis 只需要保证过期 Key 不再被当作有效数据返回，并不要求其占用的内存在 TTL 归零的同一毫秒释放。通过“访问时检查 + 后台分批抽样清理”，可以在不进行全量扫描的情况下回收过期数据，避免为了少量未及时释放的内存而持续消耗大量 CPU。
