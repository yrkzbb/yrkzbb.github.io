## Redis 主从复制

### 1. Redis 主从同步中的增量同步和全量同步怎么实现？

Redis 主从复制主要有两条路径：**全量同步用 RDB 快照建立数据基线，增量同步通过复制积压缓冲区补发从节点缺失的命令**。从节点建立复制连接后发送 `PSYNC`，主节点会根据复制 ID 和复制偏移量，判断能否继续增量复制。

#### 全量同步

当从节点第一次复制主节点，或者主节点无法从复制积压缓冲区中找到从节点缺失的数据时，会执行全量同步：

1. 主节点响应 `FULLRESYNC`，返回当前复制 ID 和复制偏移量。
2. 主节点生成 RDB 快照，并将快照传送给从节点。具体可以通过磁盘文件或无盘复制方式传输。
3. 在生成和传输 RDB 期间，主节点会把新的写命令保存在为此次同步维护的缓冲区中。
4. 从节点接收并加载 RDB，用快照数据替换自己当前的数据集。
5. 主节点再将 RDB 生成期间缓存的写命令发给从节点执行，之后进入持续的命令传播阶段。

全量同步的代价较高，会涉及生成快照、网络传输、从节点清空旧数据并加载 RDB 等工作。

#### 增量同步

主从连接短暂中断后，从节点会带着之前记录的复制 ID 和已复制到的偏移量发送 `PSYNC`。如果复制 ID 能够匹配，并且该偏移量之后的命令仍在主节点的 replication backlog 中，主节点就响应 `CONTINUE`，只把从节点断线期间缺失的命令补发给它，无需重新传输整份 RDB。

能否进行增量同步，关键看两点：

- **复制 ID 是否能够衔接**：用于确认主从节点是否处于可继续的复制历史中。
- **缺失的命令是否还在复制积压缓冲区中**：复制偏移量表示节点处理到的复制流位置。如果断线时间过长，所需命令已被环形积压缓冲区覆盖，则只能改为全量同步。

因此，主从复制并不是每次重连都做全量同步，而是优先尝试增量续传；只有无法补齐复制流时，才重新用 RDB 建立数据基线。同步完成后，主节点仍会将后续写命令持续发送给从节点；Redis 默认是异步复制，主节点通常不会等待从节点执行完再向客户端确认写入成功。

### 2. Redis 主从和集群可以保证数据一致性吗？

不能保证强一致性。**Redis 主从复制默认是异步的，Redis Cluster 中每个主节点与从节点之间也使用异步复制**，因此正常情况下会趋向最终一致，但在复制延迟、故障切换或网络分区时，可能出现短暂不一致，甚至丢失已向客户端确认的写入。

主要有以下几种情况：

- **复制延迟**：主节点写入成功后，命令可能还没有在从节点上执行。此时从从节点读取，可能读到旧数据。
- **故障切换**：如果主节点在某些写命令尚未复制到从节点时宕机，被提升的从节点不包含这部分写入，这些数据就可能丢失。
- **网络分区**：旧主节点与集群其他节点失联后，在它停止接受写入之前可能存在一个时间窗口。另一侧完成主从切换后，旧主节点上未复制的写入可能无法保留。

可以通过一些手段降低风险，但不能把 Redis 异步复制变成严格的强一致系统：

- 写入后使用 `WAIT` 等待指定数量的从节点确认已接收复制数据，可以缩小故障时的数据丢失窗口，但它不等价于强一致事务。
- 配置 `min-replicas-to-write` 和 `min-replicas-max-lag`，在健康从节点数量不足时拒绝写入，以可用性换取更小的丢数据风险。
- 对“写后立即读”敏感的业务优先读主节点，不要在无容忍窗口的场景直接读从节点。

所以我会根据业务容忍度做选择：缓存、会话等能容忍短暂不一致的数据适合使用 Redis 的高可用复制；如果数据要求严格不丢失或强一致，不能只依赖 Redis 主从或 Cluster，还需要使用适合该一致性要求的存储方案。

## Redis Sentinel

### 1. Redis 哨兵机制的原理是什么？

Redis Sentinel 的核心作用是：**在主从复制的基础上，对节点进行监控，并在主节点确认故障后自动完成主从切换**。它提供的是高可用管理，不负责数据分片，数据复制仍由 Redis 主从机制完成。

整个过程可以分为以下几步：

1. **监控与发现**：Sentinel 会定期向主节点、从节点和其他 Sentinel 发送 `PING`，并通过 `INFO` 等信息了解主从拓扑。多个 Sentinel 之间也会互相发现和交换监控信息。
2. **主观下线**：某个 Sentinel 在 `down-after-milliseconds` 时间内没有收到节点的有效响应，会单方面将其标记为主观下线，即 `SDOWN`。
3. **客观下线**：如果被判定主观下线的是主节点，Sentinel 会询问其他 Sentinel。当认为主节点下线的 Sentinel 数量达到配置的 `quorum`，主节点被判定为客观下线，即 `ODOWN`。
4. **选举故障转移领导者**：Sentinel 们会为本轮故障转移投票，选出一个 Sentinel 负责执行切换。达到 `quorum` 用于确认主节点客观下线，而真正授权故障转移还需要获得 Sentinel 的多数票，两者不能简单等同。
5. **选择新主节点**：领导者会从可用从节点中筛选候选者，综合考虑 `replica-priority`、复制进度等因素，选择更合适的从节点，并通过 `REPLICAOF NO ONE` 将它提升为新主节点。
6. **重建主从关系**：Sentinel 让其他从节点改为复制新主节点；旧主节点恢复后，也会被重新配置为新主节点的从节点。Sentinel 同时发布状态变化，客户端可以通过 Sentinel 查询当前主节点地址。

实际部署时通常使用至少 3 个彼此独立的 Sentinel，以便进行多数派判断和故障转移授权。但 Sentinel 不会把异步主从复制变成强一致复制；如果旧主节点宕机前存在尚未复制的写入，故障转移后仍然可能丢失这部分数据。

### 2. Redis Sentinel 选择新主节点的算法是什么？

Sentinel 不是从所有从节点中随机选一个，而是**先排除不合格的从节点，再依次比较复制优先级、复制偏移量和节点 ID**。核心目标是在可靠接管的前提下，尽量选择数据更新的从节点。

需要先区分两次“选举”：Sentinel 们先投票选出本轮故障转移的 Sentinel 领导者，然后由该领导者从 Redis 从节点中选出新主节点。这里的选主算法指第二个过程。

#### 第一步：排除不合格的从节点

Sentinel 会排除已下线、长时间无法联系、与原主节点断开过久，或者配置为不允许晋升的从节点。其中 `replica-priority` 为 `0` 表示该从节点永远不会被 Sentinel 提升为主节点。

#### 第二步：对候选从节点排序

对剩余的候选节点，Sentinel 按以下顺序比较：

1. **`replica-priority` 越小越优先**：管理员可以用它表达节点的人工优先级，例如让配置更高或网络位置更合适的从节点优先接管。
2. **复制偏移量越大越优先**：在优先级相同时，偏移量越大，通常表示从原主节点接收的复制数据越多，提升后丢失数据的风险相对更小。
3. **节点运行 ID 字典序较小者优先**：如果前两项都相同，使用 Redis 节点的 run ID 进行确定性的最终裁决。它主要是为了打破平局，并不代表该节点性能更好。

选出候选者后，Sentinel 向它发送 `REPLICAOF NO ONE`，使其成为新主节点；确认晋升成功后，再让其他从节点改为复制新主节点。因此，不能简单说 Sentinel “只选复制偏移量最大的从节点”，`replica-priority` 的排序在偏移量之前。

## Redis Cluster

### 1. Redis 有哪些集群模式，Redis Cluster 的优缺点是什么？

Redis 常见的部署形态有**主从复制、Sentinel 和 Redis Cluster**，它们解决的问题不同：主从复制用于数据副本和读扩展；Sentinel 在主从基础上增加故障检测和自动切换，但数据仍然主要受单个主节点容量限制；Redis Cluster 同时提供数据分片和高可用，适用于单机容量或写入吞吐已成为瓶颈的场景。

Redis Cluster 将键空间划分为 16384 个 Hash Slot。客户端根据 Key 计算所属 Slot，每个主节点负责一部分 Slot；主节点可以配置从节点，主节点故障后由从节点发起切换。节点之间通过 Cluster Bus 交换状态和故障信息；客户端访问错误节点时，会收到 `MOVED` 或迁移期间的 `ASK` 重定向。

#### 优点

- **可以水平扩容**：数据分散在多个主节点上，通过增加节点并迁移 Slot 扩大总容量和整体吞吐量。
- **具备自动故障转移能力**：分片主节点不可用时，其从节点可被选为新主节点。Redis Cluster 自身完成故障检测和切换，不需要再单独部署 Sentinel 来管理 Cluster。
- **去中心化**：没有单独的中心路由节点，客户端可以连接任意集群节点，并根据 Slot 拓扑定位数据。

#### 缺点

- **跨 Slot 操作受限**：多 Key 命令、事务和 Lua 脚本中涉及的 Key 通常需要位于同一 Slot。可以通过 Hash Tag，例如 `{user}:1` 和 `{user}:2`，让相关 Key 进入同一 Slot，但这会增加数据建模约束，不合理使用还可能造成 Slot 倾斜。
- **运维复杂度更高**：需要处理节点扩缩容、Slot 迁移、故障切换和客户端路由等问题，客户端也必须正确处理 `MOVED` 和 `ASK`。
- **仍然不保证强一致**：分片内部仍采用异步主从复制，在复制延迟、故障切换或网络分区时可能丢失少量已确认写入。
- **存在分布不均和热点风险**：性能不只取决于总节点数。如果数据量、Big Key 或高频 Key 集中在少数 Slot，对应主节点仍然会成为瓶颈。
- **功能存在集群约束**：Cluster 只使用第 `0` 号数据库，不支持通过 `SELECT` 切换到其他逻辑数据库；部分依赖全局键空间或跨 Slot 语义的操作也会受限。

因此，如果单个主节点已经能满足容量和性能需求，主从加 Sentinel 通常更简单；当数据量或写入压力需要跨多个主节点分担时，再选择 Redis Cluster。最终还要结合数据量、Key 分布、跨 Key 操作、一致性要求和运维能力判断。
