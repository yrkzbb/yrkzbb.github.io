## Redis 事务与原子性

### 1. 如何实现 Redis 原子性？

Redis 中单条命令本身通常具有原子性，因为命令对核心数据结构的操作主要由主线程串行执行，一条命令执行期间不会被另一条普通命令插入。如果一个业务操作包含多条命令，则可以根据场景使用 `MULTI/EXEC`、Lua 脚本或 `WATCH`。

常见方案如下：

1. **优先使用单条原子命令**：例如计数使用 `INCR`，不存在时写入使用 `SET key value NX`，只有 Key 存在时删除可以结合具体原子命令。能够用一条命令完成时，通常最简单可靠。
2. **使用 `MULTI/EXEC` 事务**：`MULTI` 之后的命令先进入队列，执行 `EXEC` 时由 Redis 连续执行，期间不会插入其他客户端的命令，适合不需要根据中间结果进行条件判断的一组操作。
3. **使用 Lua 脚本**：脚本中的多条 Redis 操作在服务端作为一个整体执行，其他普通命令不会在脚本中间插入。它适合“先读后判断再写”的逻辑，也能减少网络往返。
4. **使用 `WATCH` 实现乐观锁**：在 `MULTI` 前监视相关 Key；如果 Key 在 `EXEC` 前被其他客户端修改，事务不会执行，客户端需要重新读取并重试，适合存在并发条件判断的场景。

例如扣减库存时，需要保证“库存足够才扣减”，可以使用 Lua 脚本：

```lua
local stock = tonumber(redis.call('GET', KEYS[1]))
local count = tonumber(ARGV[1])

if stock and stock >= count then
    return redis.call('DECRBY', KEYS[1], count)
end

return -1
```

调用时把库存 Key 放在 `KEYS[1]`，扣减数量放在 `ARGV[1]`。判断和扣减在一次脚本执行中完成，不会出现两个客户端同时读到库存充足后都扣减的问题。在 Redis Cluster 中，脚本访问的多个 Key 还必须位于同一个哈希槽。

需要注意，Redis 事务与关系型数据库事务不同：`MULTI/EXEC` 能保证命令按顺序、不被其他客户端插入地执行，但遇到执行期错误时，已经成功执行的命令不会自动回滚。因此客户端应提前校验命令和参数；业务逻辑较复杂时，我更倾向于使用 Lua 脚本集中完成判断与修改。

另外，原子性只说明操作不会被中途干扰，不等于数据已经持久化或同步到副本。AOF 策略、主从复制和故障切换解决的是持久性与可用性问题，需要分别设计。如果业务同时修改 Redis 和数据库，单靠 Redis 事务也不能保证跨系统原子性。

## Redis 持久化

### 1. Redis 有哪两种持久化方式？分别有什么优缺点？

Redis 主要有两种持久化方式：**RDB 快照**和 **AOF 追加日志**。RDB 定期保存某个时间点的完整数据快照；AOF 记录导致数据变化的写命令，通过重放命令恢复数据。两者没有绝对优劣，需要根据可接受的数据丢失范围、恢复时间、磁盘和内存资源选择。

#### RDB

RDB 会把某个时间点的数据集生成紧凑的二进制快照文件。生产中通常使用 `BGSAVE`，由子进程生成快照，主进程继续处理请求。

优点：

- 文件紧凑，适合备份、归档和跨机房传输。
- 恢复时直接加载快照，通常比逐条重放 AOF 命令更快。
- 两次快照之间没有持续追加日志的磁盘写入，日常磁盘 I/O 开销相对较低。

缺点：

- 只能恢复到最近一次快照，发生故障时可能丢失两次快照之间的数据。
- `fork` 子进程本身可能造成延迟；生成快照期间如果写入很多数据，写时复制会增加内存占用。
- 保存大型数据集会消耗 CPU 和磁盘 I/O，配置不合理可能影响线上延迟。

#### AOF

AOF 会把写命令追加到日志中，重启时通过重放日志恢复数据。`appendfsync` 常见策略有 `always`、`everysec` 和 `no`，分别在持久性与性能之间做不同权衡。

优点：

- 数据安全性更可控。常用的 `everysec` 策略通常最多丢失约 1 秒的数据；`always` 持久性更强，但性能代价更高。
- 日志以追加方式写入，不需要频繁修改文件已有内容；尾部出现不完整命令时也有相应检查和修复手段。
- AOF 重写可以根据当前数据生成更精简的日志，避免文件无限增长。

缺点：

- AOF 文件通常比同一数据集的 RDB 文件更大，并持续产生磁盘写入。
- 恢复过程需要加载基础数据并重放增量命令，恢复速度取决于文件结构和数据规模，通常比加载单个 RDB 快照更慢。
- `fsync` 策略会直接影响性能和数据安全；AOF 重写也会带来 `fork`、写时复制以及额外磁盘 I/O。

可以简单对比如下：

| 对比项 | RDB | AOF |
| --- | --- | --- |
| 记录内容 | 某个时刻的数据快照 | 写命令日志 |
| 数据完整性 | 可能丢失最近一次快照之后的数据 | 取决于 `appendfsync` 策略 |
| 文件大小 | 通常较小 | 通常较大 |
| 恢复速度 | 通常较快 | 通常较慢，但会受 AOF 文件结构影响 |
| 运行成本 | 快照时集中消耗资源 | 持续写日志，并周期性重写 |

如果业务更关注恢复速度和定期备份，可以侧重 RDB；如果更关注尽量少丢数据，可以侧重 AOF。实际生产中也可以同时开启两者：RDB 用于快照备份，AOF 提供更细粒度的数据恢复。两者同时开启时，Redis 重启通常优先使用数据更完整的 AOF。现代 AOF 还可以使用 RDB 格式作为基础文件并配合增量 AOF，但这仍属于 AOF 持久化体系，不是第三种独立方式。

### 2. AOF 日志是如何实现的？

AOF 的核心思路是：**Redis 成功执行写命令后，把能够重建数据的命令追加到 AOF 缓冲区，再按照配置策略写入并同步到磁盘**。重启时按顺序加载基础文件和增量日志，就能恢复执行这些命令后的数据状态。

整体流程可以分为以下几步：

1. **执行写命令**：客户端发送 `SET`、`HSET`、`INCR` 等会修改数据的命令，Redis 先执行命令。只读命令不会写入 AOF，执行失败且没有产生修改的命令也不会作为有效变更记录。
2. **追加到 AOF 缓冲区**：Redis 将需要传播的写操作按照 RESP 格式编码，追加到内存中的 AOF 缓冲区。先写内存缓冲区可以减少大量零散的磁盘写操作。
3. **写入操作系统页缓存**：事件循环在合适时机调用 `write`，把 AOF 缓冲区内容写入文件。此时数据通常只是进入内核页缓存，并不一定已经落到物理存储设备。
4. **执行 `fsync`**：Redis 根据 `appendfsync` 策略决定何时要求操作系统把页缓存同步到磁盘。
5. **启动时恢复**：Redis 重启后加载 AOF 基础文件，再按顺序重放增量 AOF 中的命令，重建内存数据。

`appendfsync` 的三种常见策略是：

| 策略 | 实现方式 | 影响 |
| --- | --- | --- |
| `always` | 每批写命令都执行 `fsync` 后再确认 | 数据安全性最高，但磁盘同步会明显影响延迟和吞吐 |
| `everysec` | 通常每秒由后台线程执行一次 `fsync` | 性能和持久性较均衡，故障时一般可能丢失约 1 秒数据 |
| `no` | Redis 只执行 `write`，由操作系统决定何时刷盘 | 性能开销较低，但故障时可能丢失更多数据 |

这里要区分 `write` 和 `fsync`：`write` 通常只是把数据交给操作系统页缓存；`fsync` 才是请求内核把数据同步到持久化设备。因此“已经写入 AOF 文件”不一定等于发生故障后一定可以恢复，最终保证取决于刷盘策略和存储系统。

随着写命令不断增加，AOF 文件会越来越大，所以 Redis 还支持 **AOF 重写**。重写不是简单压缩旧日志，而是根据当前内存中的最终数据状态生成一份最小化的等价数据。例如同一个 Key 被连续修改很多次，重写后通常只需要保留能够还原最终值的命令。

Redis 7.0 起使用多部件 AOF，通常包括：

- **基础 AOF 文件**：保存重写时的数据基线，可以采用 RDB 二进制格式，也可以采用命令格式。
- **增量 AOF 文件**：记录基础文件生成期间及之后的新写命令。
- **清单文件**：记录恢复时需要加载哪些基础文件和增量文件。

执行 `BGREWRITEAOF` 时，子进程根据当时的数据快照生成新的基础文件，主进程继续处理请求，并把后续写操作记录到新的增量 AOF。基础文件生成完成后，Redis 原子地切换清单，再清理不再需要的旧文件。这样不用暂停服务来重写全部日志，但 `fork`、写时复制和集中磁盘 I/O 仍可能造成延迟或额外内存占用。

如果宕机导致 AOF 尾部只有半条命令，Redis 可以根据配置在启动时截掉不完整尾部，或者使用 `redis-check-aof` 检查修复。但这只能处理日志尾部损坏，不能替代正确的备份和刷盘策略。

### 3. RDB 快照是如何实现的？

RDB 的核心是：**在某个时间点得到内存数据的一致性视图，由子进程把这份视图序列化成二进制文件，主进程继续处理客户端请求**。生产环境通常使用 `BGSAVE`，它依赖操作系统的 `fork` 和写时复制机制。

完整流程大致如下：

1. **触发快照**：可以由 `BGSAVE` 命令、`save` 配置规则、主从全量同步等场景触发。`SAVE` 也能生成 RDB，但它由主进程同步执行，会阻塞其他请求，生产环境通常不直接使用。
2. **主进程执行 `fork`**：操作系统创建子进程。`fork` 完成后，父子进程拥有逻辑上相同的地址空间，此时的数据状态就是本次快照的时间点。
3. **利用写时复制**：刚 `fork` 时不会立即复制整个数据集，父子进程共享已有物理内存页。之后主进程如果修改某个内存页，操作系统才复制该页，让主进程修改副本；子进程继续看到修改前的数据，因此能获得一致的旧视图。
4. **子进程序列化数据**：子进程遍历各个数据库中的 Key，把数据类型、过期时间和实际内容按照 RDB 的紧凑二进制格式写入临时文件，并在文件中保存必要的版本、校验等信息。
5. **落盘并替换旧文件**：临时 RDB 生成成功后，Redis 将它替换为正式的 RDB 文件。使用临时文件再替换，可以避免生成到一半的文件直接覆盖上一份可用快照。
6. **子进程退出**：主进程收到子进程完成状态，更新最近保存时间等信息。下次启动时，如果选择使用 RDB 恢复，Redis 读取文件并反序列化到内存；已经过期的数据不会作为有效数据恢复。

写时复制保证了快照一致性。例如快照开始时 `count=10`，随后主进程把它改成 `11`：子进程仍从旧内存页读取 `10` 并写入本次 RDB，主进程则对外提供新值 `11`。因此 RDB 表示的是 `fork` 时刻附近的数据状态，而不是生成文件结束时的最新状态。

这种实现的主要代价有两个：第一，`fork` 本身需要复制页表，数据集很大时可能造成延迟；第二，快照期间写入越多，写时复制产生的新内存页越多，额外内存占用也越大。如果内存余量不足，可能导致快照失败甚至触发系统 OOM。另外，子进程序列化数据会消耗 CPU 和磁盘带宽，所以 RDB 虽然把主要工作移出了主进程，也不代表对线上性能完全没有影响。

RDB 只保存快照时刻的数据，不记录之后的每次修改。因此机器在下一次快照前故障时，最近一段数据可能丢失；快照周期应该根据可接受的数据丢失范围、数据规模和系统资源综合设置。
