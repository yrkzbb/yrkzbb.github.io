## Redis 事务与原子性

### 1. 如何实现 Redis 原子性？

Redis 中单条命令本身通常具有原子性，因为命令对核心数据结构的操作主要由主线程串行执行，一条命令执行期间不会被另一条普通命令插入。如果一个业务操作包含多条命令，则可以根据场景使用 `MULTI/EXEC`、Lua 脚本或 `WATCH`。

常见方案如下：

1. **优先使用单条原子命令。**
2. **使用 `MULTI/EXEC` 事务：**`MULTI` 之后的命令先进入队列，执行 `EXEC` 时由 Redis 连续执行，期间不会插入其他客户端的命令，适合不需要根据中间结果进行条件判断的一组操作。
3. **使用 Lua 脚本：**脚本中的多条 Redis 操作在服务端作为一个整体执行，其他普通命令不会在脚本中间插入。它适合“先读后判断再写”的逻辑，也能减少网络往返。
4. **使用 `WATCH` 实现乐观锁：**在 `MULTI` 前监视相关 Key；如果 Key 在 `EXEC` 前被其他客户端修改，事务不会执行，客户端需要重新读取并重试，适合存在并发条件判断的场景。

例如扣减库存时，需要保证“库存足够才扣减”，可以使用 Lua 脚本：

```lua
local stock = tonumber(redis.call('GET', KEYS[1]))
local count = tonumber(ARGV[1])

if stock and stock >= count then
    return redis.call('DECRBY', KEYS[1], count)
end

return -1
```

调用时把库存 Key 放在 `KEYS[1]`，扣减数量放在 `ARGV[1]`。判断和扣减在一次脚本执行中完成，不会出现两个客户端同时读到库存充足后都扣减的问题。

## Redis 持久化

### 1. Redis 有哪两种持久化方式？分别有什么优缺点？

Redis 主要有两种持久化方式：RDB 快照和 AOF 追加日志。RDB 定期保存某个时间点的完整数据快照；AOF 记录导致数据变化的写命令，通过重放命令恢复数据。

#### RDB

RDB 会把某个时间点的数据集生成紧凑的二进制快照文件。生产中通常使用 `BGSAVE`，由子进程生成快照，主进程继续处理请求。

优点：

- 文件紧凑，适合备份、归档和跨机房传输。
- 恢复时直接加载快照，通常比逐条重放 AOF 命令更快。
- 两次快照之间没有持续追加日志的磁盘写入，日常磁盘 I/O 开销相对较低。

缺点：

- 只能恢复到最近一次快照，发生故障时可能丢失两次快照之间的数据。
- `fork` 子进程本身可能造成延迟；生成快照期间如果写入很多数据，写时复制会增加内存占用。
- 保存大型数据集会消耗 CPU 和磁盘 I/O，配置不合理可能影响线上延迟。

#### AOF

AOF 会把写命令追加到日志中，重启时通过重放日志恢复数据。`appendfsync` 常见策略有 `always`、`everysec` 和 `no`，分别在持久性与性能之间做不同权衡。

优点：

- 数据安全性更可控。常用的 `everysec` 策略通常最多丢失约 1 秒的数据；`always` 持久性更强，但性能代价更高。
- 日志以追加方式写入，不需要频繁修改文件已有内容。
- AOF 重写可以根据当前数据生成更精简的日志，避免文件无限增长。

缺点：

- AOF 文件通常比同一数据集的 RDB 文件更大，并持续产生磁盘写入。
- 恢复过程需要加载基础数据并重放增量命令，恢复速度取决于文件结构和数据规模，通常比加载单个 RDB 快照更慢。
- `fsync` 策略会直接影响性能和数据安全；AOF 重写也会带来 `fork`、写时复制以及额外磁盘 I/O。

### 2. AOF 日志是如何实现的？

AOF 的核心思路是：Redis 成功执行写命令后，把能够重建数据的命令追加到 AOF 缓冲区，再按照配置策略写入并同步到磁盘。重启时按顺序加载基础文件和增量日志，就能恢复执行这些命令后的数据状态。

Redis 的 AOF 是通过记录写命令实现持久化的。Redis 执行完一条会修改数据的命令后，会把该命令按照 Redis 协议追加到 AOF 缓冲区，再根据 `appendfsync` 策略写入并同步到磁盘。

常见同步策略有三种：

1. **`always`：**每条写命令都执行 `fsync`，数据最安全，但性能最低。
2. **`everysec`：**每秒执行一次 `fsync`，默认且最常用，宕机最多可能丢失约 1 秒的数据。
3. **`no`：**只写入操作系统缓冲区，由操作系统决定何时刷盘，性能较高，但丢失数据可能更多。

Redis 重启时，会重新执行 AOF 中的写命令来恢复数据。

随着写命令增多，AOF 文件会越来越大，所以 Redis 会进行 AOF 重写。重写不是简单压缩旧日志，而是根据当前数据库状态生成一份更精简的新 AOF。例如，对一个键执行了 100 次自增，重写后可能只保留一条能恢复当前值的命令。重写期间产生的新命令还会被额外记录，重写完成后再合并，最后原子替换旧文件，避免丢失数据。

一句话总结：

AOF 就是先执行命令，再把写命令追加到日志；通过不同的刷盘策略平衡性能和可靠性，通过 AOF 重写控制文件大小，Redis 重启时重放日志恢复数据。

### 3. RDB 快照是如何实现的？

Redis 的 RDB 是把某一时刻内存中的数据生成一个二进制快照文件，默认叫 `dump.rdb`。Redis 重启时读取该文件，将数据恢复到内存。

生成 RDB 主要有两种方式：

1. **`SAVE`：**主线程直接执行快照，期间会阻塞客户端请求，一般不建议在线上使用。
2. **`BGSAVE`：**主进程调用 `fork` 创建子进程，由子进程把内存数据写入临时 RDB 文件，主进程继续处理请求。写完后再用临时文件原子替换旧的 RDB 文件。

`BGSAVE` 的关键是操作系统的 Copy-On-Write，写时复制。`fork` 后，父子进程最初共享相同的物理内存页：

- 子进程读取 `fork` 时刻的数据并生成快照。
- 如果主进程修改某个内存页，操作系统才会复制该页，让父进程修改副本。
- 子进程仍然读取原来的内存页，因此得到的是 `fork` 那一时刻的数据快照。

这样既能保证快照的一致性，又能让 Redis 主进程继续响应请求。

不过，`fork` 本身可能造成短暂阻塞；如果快照期间写操作很多，写时复制会增加内存占用。同时，RDB 只能保存最近一次快照的数据，宕机时可能丢失上次快照之后的所有修改。

一句话总结：

RDB 通过 `fork` 子进程生成内存快照，利用写时复制保证快照一致性，最后原子替换旧文件；它恢复快、文件紧凑，但实时性不如 AOF。

RDB 就是 Redis 在某个时刻把内存数据保存成二进制快照。通常通过 `BGSAVE` 执行：主进程 `fork` 一个子进程，子进程负责写 RDB 文件，主进程继续处理请求。父子进程借助写时复制共享内存；主进程修改数据时，系统才复制对应内存页，因此子进程可以保存 `fork` 时刻的一致性数据。写完后，用新文件原子替换旧文件。它的优点是文件紧凑、恢复快，缺点是可能丢失两次快照之间的数据。
