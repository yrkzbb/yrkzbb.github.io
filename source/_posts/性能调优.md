## 执行计划与索引分析

### 1. MySQL 的 `EXPLAIN` 有什么作用？

`EXPLAIN` 用来查看优化器选择的执行计划，帮助判断表的访问顺序、连接方式、是否使用索引、预计扫描行数，以及是否需要额外排序或临时表。它是定位慢 SQL 的重要工具，但执行计划只是分析依据，不能单凭某一个字段断定 SQL 一定快或慢。

常用写法如下：

```sql
-- 查看估算执行计划，不会真正执行这条 SELECT
EXPLAIN SELECT * FROM user WHERE status = 1;

-- 输出更详细、便于程序分析的 JSON 格式
EXPLAIN FORMAT=JSON
SELECT * FROM user WHERE status = 1;

-- MySQL 8.0.18 及以后：真实执行并显示实际耗时和行数
EXPLAIN ANALYZE
SELECT * FROM user WHERE status = 1;
```

执行计划中的重要字段有：

| 字段 | 含义 |
| --- | --- |
| `id` | 查询块编号；同一编号通常按从上到下执行，不同编号通常编号越大越先执行，但实际还要结合执行计划结构判断。 |
| `select_type` | 查询类型，例如 `SIMPLE`、`PRIMARY`、`SUBQUERY`、`DERIVED`。 |
| `table`、`partitions` | 当前访问的表或派生结果，以及实际扫描的分区。 |
| `type` | 访问方式，常见有 `ALL`、`index`、`range`、`ref`、`eq_ref`、`const`。访问范围通常依次缩小，但不能脱离扫描行数判断性能。 |
| `possible_keys`、`key` | 可能使用的索引和最终选择的索引；`key=NULL` 通常表示没有选择索引。 |
| `key_len` | 实际使用的索引键长度，可辅助判断联合索引利用了哪些列，不代表索引本身的总长度。 |
| `ref` | 哪些常量或列被用于和索引列比较。 |
| `rows`、`filtered` | 预计扫描行数和经过条件过滤后保留的百分比，两者可以粗略估算传给下一步的行数。 |
| `Extra` | 补充信息，重点关注 `Using index`、`Using index condition`、`Using filesort` 和 `Using temporary`。 |

面试或排查慢 SQL 时，我会优先看 `type`、`key`、`rows`、`filtered` 和 `Extra`，再结合数据量、数据分布及实际耗时判断，不能只凭“走了索引”就认为执行计划合理。

普通 `EXPLAIN` 主要给出估算计划。`EXPLAIN ANALYZE` 会真实执行语句，并对比预计行数和实际行数，因此在生产环境使用时要评估查询开销；如果用于可修改数据的语句，还要格外谨慎。

### 2. 怎么判断 SQL 有没有走索引？

最直接的方法是在 SQL 前加 `EXPLAIN`，重点看 `key` 和 `type`：`key` 显示实际使用的索引名，`NULL` 通常表示没有选择索引；`type=ALL` 表示全表扫描，`type=index` 则是全索引扫描，两者都可能扫描大量数据。

```sql
EXPLAIN SELECT * FROM user WHERE id = 100;
```

还要结合 `rows`、`filtered` 和 `Extra` 判断效果。`key` 不为 `NULL` 只能说明使用了索引，不代表一定高效；例如索引选择性很差或扫描范围很大，走索引也可能比全表扫描慢。`Extra` 中的 `Using index` 通常表示覆盖索引，不是“使用了索引”的唯一判断标志。

### 3. 怎么查看一张表有哪些索引？

可以使用 `SHOW INDEX`：

```sql
SHOW INDEX FROM user;
```

结果中重点看 `Key_name`、`Column_name`、`Seq_in_index`、`Non_unique`、`Index_type` 和 `Cardinality`，分别表示索引名、索引列、联合索引中的顺序、是否允许重复、索引类型和估算基数。

如果需要批量查询或按条件筛选，也可以查询 `information_schema.STATISTICS`。`SHOW CREATE TABLE user` 还能同时查看表结构中声明的主键、唯一索引和普通索引。

## 慢查询优化

### 1. MySQL 慢查询该如何优化？

慢查询优化的核心流程是先定位、再分析、然后优化并复测，不能看到 SQL 慢就直接加索引。

1. 通过慢查询日志、监控和实际参数确认慢 SQL、执行频率、返回行数以及是否存在锁等待。
2. 使用 `EXPLAIN`，必要时使用 `EXPLAIN ANALYZE`，检查扫描行数、索引、连接顺序、排序和临时表。
3. 根据 `WHERE`、`JOIN`、`ORDER BY` 和 `GROUP BY` 设计合适的单列或联合索引，同时避免重复、低收益索引。
4. 优化 SQL，例如减少无用列和返回行数、避免对索引列做不必要的函数或隐式类型转换、优化深分页和批量访问。
5. 如果执行计划没有明显问题，再检查数据分布、统计信息、锁竞争、Buffer Pool、CPU 和磁盘 I/O。缓存、读写分离或分库分表应在单机优化不足且业务确实需要时再考虑。

最终要用相同数据量和参数复测，并关注吞吐、延迟以及写入成本，不能只看一次查询变快。

### 2. 如果 `EXPLAIN` 选择的索引不符合预期，有什么办法干预？

先确认优化器是否真的选错。优化器可能因为数据量小、索引选择性差、回表成本高或查询范围过大，合理地选择另一个索引甚至全表扫描。

可以按下面的顺序处理：

1. 使用 `EXPLAIN ANALYZE` 对比估算与实际行数，并执行 `ANALYZE TABLE` 更新统计信息；数据分布倾斜时可以评估直方图。
2. 调整 SQL 写法和参数类型，避免函数、隐式转换等导致索引难以利用。
3. 根据过滤、连接和排序条件建立或调整联合索引，并清理明显重复或低价值索引。
4. 确认优化器仍选错且经过真实数据验证后，再考虑 `USE INDEX`、`FORCE INDEX` 或优化器 Hint 临时干预。

强制索引应作为最后手段，因为数据分布变化后，原来被强制的索引可能变差。使用后要记录原因并持续验证执行计划，而不是把 Hint 当作长期替代索引设计的方案。

### 3. 什么是 MySQL 慢查询日志？

慢查询日志用于记录执行时间超过阈值的 SQL，是定位慢 SQL 的重要入口。它只说明语句执行得慢，不直接说明慢的原因，后续还需要结合执行计划、锁等待和系统资源分析。

常用配置可以这样查看和设置：

```sql
-- 查看是否开启、日志位置和时间阈值
SHOW VARIABLES LIKE 'slow_query_log%';
SHOW VARIABLES LIKE 'long_query_time';

-- 动态开启并设置阈值为 1 秒
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 1;
```

`slow_query_log` 控制是否开启，`slow_query_log_file` 指定日志文件，`long_query_time` 控制时间阈值，`min_examined_row_limit` 可以限制最少扫描行数。`log_queries_not_using_indexes` 可以辅助发现未使用索引的查询，但可能产生大量低价值日志，不能长期盲目开启。

分析时可以先按执行次数、总耗时和平均耗时聚合 SQL，再优先处理高频且总成本高的语句；常用工具有 `mysqldumpslow` 和 `pt-query-digest`。动态设置在重启后可能失效，生产环境还应写入配置文件，并注意日志占用的磁盘空间。
