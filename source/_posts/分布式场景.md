## 分布式理论

### 1. 什么是分布式系统？

分布式系统是由多台通过网络连接的计算机共同完成任务，但对外尽量表现为一个整体的系统。

它的核心不是简单地“部署了多台机器”，而是不同节点之间需要通过网络通信、协作和共享状态。这样做可以提升系统的扩展性、可用性和处理能力，但也会引入网络延迟、部分节点故障、数据一致性以及故障定位困难等问题。由于网络和节点都可能出错，分布式系统通常要重点考虑容错、幂等、重试和一致性。

### 2. 分布式和微服务有什么区别？

分布式强调的是系统的运行和协作方式，微服务强调的是应用的架构拆分方式，两者不是同一个维度。

分布式系统把计算或存储分散到多个节点上，节点可能运行同一个应用的多个副本，也可能承担不同职责。微服务则按业务能力把一个应用拆成多个可以独立开发、部署和扩缩容的服务。微服务通常以分布式方式运行，因此会遇到远程调用、服务发现和分布式事务等问题；但分布式系统不一定采用微服务，例如一个由多个节点组成的分布式数据库。

### 3. 介绍一下 CAP 理论。

CAP 理论指出：当分布式系统发生网络分区时，一致性和可用性不能同时得到完全保证，只能在二者之间取舍。

- `C`（Consistency）表示每次读取都能获得最新写入的数据，或者明确失败。
- `A`（Availability）表示每个发送到正常节点的请求都能在有限时间内得到非错误响应，但响应不保证是最新数据。
- `P`（Partition Tolerance）表示节点之间发生网络分区时，系统仍能继续运行。

实际的分布式系统必须面对网络分区，所以通常讨论的是分区发生时选择 `CP` 还是 `AP`，而不是简单地从三个属性中任选两个。很多系统还会根据业务和操作类型动态取舍，例如关键写操作偏向一致性，部分读操作允许返回旧数据来保证可用性。

### 4. 怎么理解 BASE 理论？

BASE 是在很多分布式场景中对强一致性的一种工程化放宽：允许系统短时间不一致，以换取更高的可用性和扩展性，但最终要收敛到一致状态。

它包括三个含义：`Basically Available`，发生故障时允许降级，但核心功能基本可用；`Soft State`，允许中间状态在一段时间内存在；`Eventually Consistent`，如果后续没有新的更新，数据最终会达到一致。

最终一致并不等于不保证一致，也不意味着没有时间边界。实际设计中仍要通过消息重试、幂等、补偿和对账等机制推动状态收敛，并根据业务定义可接受的不一致窗口。

## 分布式锁

### 1. 用 Redis 怎么实现分布式锁？

常见实现是使用带过期时间的原子命令加锁，并用唯一标识配合 Lua 脚本安全解锁：

```text
SET lock:order:123 request-id NX PX 30000
```

`NX` 保证键不存在时才写入，`PX` 设置租约，避免客户端宕机后锁永久不释放；`request-id` 应由每个加锁请求唯一生成。解锁时不能直接执行 `DEL`，而要原子地比较锁值，只删除自己持有的锁：

```lua
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
end
return 0
```

如果业务执行时间可能超过租约，还需要可靠的续期机制。即便如此，Redis 锁也不能单独解决进程长时间暂停、主从切换时数据尚未同步等所有问题。对正确性要求很高的场景，我还会在资源侧增加 `fencing token`、版本号或唯一约束，防止过期的锁持有者继续写入。

### 2. 还有没有其他方法实现分布式锁？

有，常见方案包括数据库、ZooKeeper 或 etcd，选择时要结合一致性要求、性能和运维成本。

- 数据库可以使用唯一索引抢占锁记录，或使用 `SELECT ... FOR UPDATE` 做事务内互斥。它实现简单，但吞吐量和故障处理能力受数据库限制，还要处理事务超时与死锁。
- ZooKeeper 可以创建临时顺序节点，序号最小的客户端获得锁，其他客户端监听前一个节点；会话失效后临时节点自动删除，适合强调一致性的协调场景。
- etcd 可以基于租约、事务比较和 watch 实现锁，并利用线性一致读写和租约回收处理故障。

如果竞争只发生在单进程内，就不需要分布式锁；如果能用数据库唯一约束、幂等设计或任务分片消除竞争，通常也比引入锁更稳妥。

## 分布式 ID

### 1. 什么情况需要用分布式 ID？

当多个服务实例、数据库分片或不同机房需要并发生成全局唯一标识，而且无法依赖单库自增主键时，就需要分布式 ID。

例如订单库进行了分库分表，如果各分片独立使用自增主键，ID 可能冲突，也不方便跨库聚合。除了唯一性，实际还可能要求高吞吐、趋势递增、低延迟、可用性以及不暴露业务量。是否使用分布式 ID 要看这些约束；单库系统直接使用自增主键通常更简单。

### 2. 分布式 ID 有什么方案？

常见方案主要有以下几类：

- `UUID`：本地生成、无中心依赖，但字符串较长且通常无序，直接作为聚簇索引主键可能增加页分裂和存储开销。部分有序 UUID 可以缓解这一问题。
- 数据库号段：服务一次申请一段 ID 并在内存中递增，性能较高，也容易做到趋势递增；需要处理号段服务的高可用和切换。
- Snowflake 类算法：通常把时间戳、节点编号和序列号编码进 64 位整数，本地生成、吞吐量高；要解决节点编号分配、时钟回拨和同毫秒序列耗尽问题。
- Redis 自增：利用 `INCR` 获得递增 ID，实现直接，但 Redis 的可用性、持久化和故障切换会进入关键链路。

没有一种方案在所有场景都最优。我会根据是否要求有序、峰值并发、容灾范围、可接受的依赖和安全性来选择。

## 分布式事务

### 1. 什么情况下需要使用分布式事务？

当一个业务操作跨越多个不能共享本地事务的资源，而且这些资源之间存在必须共同成功或按业务规则保持一致的约束时，才需要考虑分布式事务。

例如创建订单同时扣减库存、使用优惠券和记录支付状态，这些数据由不同服务或数据库管理，本地事务无法一次覆盖。设计时我会先考虑能否调整服务边界、合并强一致数据，或者通过幂等和状态机降低原子性要求；只有确实存在跨资源一致性需求时，才引入分布式事务，因为它会增加延迟、耦合度和异常处理复杂度。

### 2. 分布式事务的解决方案你知道哪些？

常见方案可以按一致性和业务侵入程度分为几类：

- `XA/2PC`：协调者驱动各参与者先准备、再提交，能提供较强一致性，但会占用资源，协调者或网络异常时还可能阻塞，适合参与资源支持 XA 且并发压力可控的场景。
- `TCC`：业务实现 `Try`、`Confirm`、`Cancel` 三个阶段，控制能力强，但侵入性高，需要处理幂等、空回滚和悬挂。
- Saga：把长事务拆成多个本地事务，每一步配套补偿操作，适合流程较长、允许最终一致的业务；补偿通常是业务语义上的撤销，不一定能完全恢复物理状态。
- 可靠消息最终一致性：本地事务与消息发送通过事务消息或本地消息表衔接，消费者以幂等和重试完成后续操作，适合异步、允许短暂不一致的场景。

选择方案时要看业务能否补偿、允许多长的不一致窗口、吞吐量和资源是否支持相应协议，而不能只看实现是否方便。

### 3. 阿里的 Seata 框架了解过吗？

了解。Seata 是一套分布式事务解决方案，常见模式包括 `AT`、`TCC`、`Saga` 和 `XA`，核心角色是事务协调器 `TC`、事务管理器 `TM` 和资源管理器 `RM`。

以常用的 `AT` 模式为例，一阶段在本地事务中提交业务数据，同时记录回滚所需的 `undo_log`；二阶段如果全局提交，主要清理日志，如果全局回滚，则根据前后镜像生成补偿 SQL。Seata 还通过全局锁检测写冲突。

`AT` 对业务代码侵入较小，但不是无条件适用：它主要面向支持本地事务的关系型数据库，业务 SQL 和表结构也要满足相应限制；长事务还可能带来锁竞争和回滚成本。对业务补偿要求明确的场景，可以选择 `TCC` 或 `Saga`。

## 分布式组件

### 1. RPC 的概念是什么？

RPC，也就是远程过程调用，是让程序像调用本地方法一样调用另一个进程或机器上的服务，但底层实际经历了网络通信。

一次典型 RPC 会经过服务发现、序列化、网络传输、服务端执行和结果反序列化。框架通常还会提供超时、负载均衡、重试、连接管理和链路追踪等能力。所谓“像本地调用”只是编程体验，不能忽略网络调用可能超时、失败、重复执行或返回不确定结果，因此接口需要合理设置超时，并结合操作语义决定是否重试和如何保证幂等。

### 2. ZooKeeper 拿来做什么？核心的原理是什么？

ZooKeeper 是面向分布式系统的协调服务，常用于配置管理、服务注册与发现、主节点选举、分布式锁和命名等场景，不适合当作通用的大数据量数据库。

它提供类似文件系统的 `znode` 数据模型、临时节点、顺序节点和 watch 通知。服务端通过 ZAB 协议由 Leader 对写请求排序并复制到多数节点，提交后再对外生效，从而维护一致的更新顺序；读请求默认可以由当前连接的节点直接处理，所以不应笼统地把所有读取都描述为线性一致。客户端利用会话和临时节点感知故障，利用 watch 获得一次性的变更通知，并在需要时重新注册监听。

## 分布式场景

### 1. 常见的限流算法你知道哪些？

常见的限流算法有固定窗口、滑动窗口、漏桶和令牌桶，它们对突发流量的处理方式不同。

- 固定窗口在每个时间窗口内计数，实现简单，但窗口边界可能出现瞬时双倍流量。
- 滑动窗口按更细粒度的时间片或请求时间计算近期流量，边界更平滑，但存储和计算成本更高。
- 漏桶以固定速率处理请求，能够把流量整形成稳定速率，但突发请求可能排队或被拒绝。
- 令牌桶按固定速率生成令牌，请求取得令牌后才能通过，在桶容量范围内允许一定突发流量。

单机限流可以使用进程内计数器；多实例需要共享计数状态或在网关统一限流，例如用 Redis 配合 Lua 脚本保证判断和扣减的原子性。具体阈值还应结合接口容量、下游依赖和压测结果确定。

## 分布式一致性算法

### 1. 说下 Raft 算法？

Raft 是一种基于多数派复制日志的共识算法，目标是让多个节点即使发生部分故障，也能对相同的操作顺序达成一致。它把问题拆成 Leader 选举、日志复制和安全性约束三部分。

节点分为 Leader、Follower 和 Candidate。Follower 在选举超时后转为 Candidate，提高任期并发起投票；获得多数票的节点成为 Leader。正常情况下，客户端写请求由 Leader 追加到日志并复制给 Follower，当该任期的日志被多数节点确认后，Leader 才能推进提交位置并应用到状态机。

Raft 使用任期和日志匹配规则处理旧 Leader、重复消息和日志冲突，并通过投票限制保证新 Leader 的日志足够新。它能容忍少于半数节点故障，例如 5 个节点通常可容忍 2 个节点故障，但少数分区无法继续提交新日志。

### 2. 说一下 Paxos 协议？

Paxos 是在异步网络中让多个节点对某个值达成共识的一类协议。在节点可能宕机、消息可能延迟、丢失或重复，但不会被恶意篡改的前提下，只要多数节点可以通信，就能够保证已经选定的值不会被另一个值推翻。

以 Basic Paxos 为例，角色包括 Proposer、Acceptor 和 Learner。提议者先用递增且唯一的提案编号发起 `Prepare`；接受者承诺不再接受编号更小的提案，并返回自己已接受的最高编号提案。提议者获得多数响应后，必须优先采用这些响应中编号最高的已接受值；如果没有已接受值，才可以使用自己的值，再发起 `Accept`。该值获得多数接受后即被选定。

Basic Paxos 主要解决一次共识，实际系统通常需要 Multi-Paxos 连续复制日志，并通过稳定 Leader 减少重复的准备阶段。Paxos 重点保证安全性；在持续竞争或网络长期异常时，活性还依赖超时、选主等工程机制。

### 3. Raft 协议和 Paxos 协议的原理？

两者都通过多数派的交集性质保证共识安全：任意两个多数派至少有一个共同节点，因此已经确认的信息不会在下一轮决策中完全丢失。它们通常也都要求超过半数节点可用才能继续形成新的共识。

区别主要在组织方式上：Paxos 从提案编号和多数派接受规则出发，Basic Paxos 先描述单值共识，工程上通常扩展为 Multi-Paxos；Raft 从复制日志出发，明确规定 Leader 选举、日志复制和成员变更等机制，并使用任期以及“日志足够新”的投票条件保证新 Leader 包含已提交日志。

因此，两者解决的是同类问题，不能简单说谁的一致性更强。Raft 的状态和流程通常更容易理解及实现，而具体系统的性能和可靠性还取决于实现、网络、持久化策略和成员配置。

### 4. 有什么框架或技术用了 Raft 协议？

典型例子包括 etcd、Consul，以及 Kubernetes 依赖的 etcd；一些数据库和基础设施也使用 Raft 或其变体进行元数据管理、日志复制或选主。

需要注意的是，“使用 Raft”不代表系统所有数据路径都直接由 Raft 处理。例如 Kubernetes API Server 把状态保存到 etcd，真正执行 Raft 共识的是 etcd 集群；有些数据库也只在特定复制组或元数据模块使用 Raft。判断时应看具体组件和版本的架构，而不是只看产品名称。

### 5. 描述一下 ZAB 协议？

ZAB 是 ZooKeeper 使用的原子广播协议，核心目标是让各服务器以相同顺序提交事务，并在 Leader 故障切换后保持已提交状态不丢失。

正常广播阶段，Leader 为写事务分配全局有序的事务标识 `zxid`，把提议发送给 Follower；收到法定数量的确认后提交事务，并通知其他节点提交。Leader 故障后进入恢复流程，集群选出新的 Leader，同步各节点日志，确保新 Leader 包含应保留的事务，再恢复广播。

ZAB 和 Raft 都采用 Leader 与多数派复制，但协议目标和具体机制不同：ZAB 围绕 ZooKeeper 的崩溃恢复和有序事务广播设计，Raft 则以更通用、易理解的复制状态机共识为目标，因此不能把 ZAB 简单等同于 Raft。
