## 日志基础

### 1\. MySQL 的日志文件分为哪几种？

MySQL 的日志可以先分为 Server 层日志和存储引擎层日志。常见的 Server 层日志包括错误日志、慢查询日志、通用查询日志和 binlog；InnoDB 还维护 redo log 和 undo log。

1.  **错误日志（Error Log）**：记录 MySQL 启停、运行异常、崩溃恢复等重要信息，主要用于故障排查。
2.  **慢查询日志（Slow Query Log）**：记录执行时间超过阈值等符合条件的 SQL，用于性能分析。
3.  **通用查询日志（General Query Log）**：记录客户端连接和收到的语句，信息量很大，通常只在临时诊断时开启。
4.  **binlog**：Server 层的逻辑变更日志，主要用于复制和基于时间点恢复。
5.  **redo log**：InnoDB 的物理变更日志，主要保证事务持久性，并用于崩溃恢复。
6.  **undo log**：保存撤销修改所需的信息，用于事务回滚和 MVCC 构造历史版本。

2\. 讲一下 binlog。

binlog 是 MySQL Server 层记录数据库变更的逻辑日志，不属于某个特定存储引擎。它会记录 DML 产生的数据变化以及 DDL 等变更事件，通常不记录普通 `SELECT`。它主要有两个用途：把主库的变更传递给从库进行复制，以及配合全量备份做基于时间点恢复。

binlog 常见格式有：

1.  **`STATEMENT`**：记录产生变更的 SQL，日志量可能较小，但部分非确定性语句可能导致主从结果不一致。
2.  **`ROW`**：记录行发生了什么变化，复制结果更确定，但批量修改时日志量可能较大。
3.  **`MIXED`**：通常使用 `STATEMENT`，在有风险的场景切换为 `ROW`。

binlog 以事件形式追加写入文件，并按文件大小或管理操作轮换。事务提交时，线程先把该事务的 binlog 内容写入 binlog cache，再在提交阶段写入 binlog 文件。`sync_binlog` 控制 binlog 多久执行一次持久化同步；例如 `sync_binlog=1` 通常表示每次事务提交都同步一次，持久性更强，但写盘开销也更高。

binlog 是逻辑日志，不能替代 InnoDB 的 redo log。它也不是默认永久保留，实际可恢复范围取决于备份、保留策略以及日志是否完整。

### 3\. undo log 的作用是什么？

undo log 主要有两个作用：支持事务回滚，以及为 MVCC 提供历史版本。

1.  **事务回滚**：InnoDB 修改数据前会记录能够撤销该操作的信息。如果语句失败、事务执行 `ROLLBACK` 或被选为死锁牺牲者，可以利用 undo log 将修改恢复到之前的状态。
2.  **MVCC**：记录中的回滚指针可以关联到 undo log 中的旧版本。快照读根据 Read View 判断当前版本不可见时，会沿版本链查找对当前事务可见的历史版本。

事务提交后，undo 也不一定马上删除：只要仍有 Read View 可能访问其中的历史版本，就需要等待 purge 线程后续清理。

### 4\. 有了 undo log，为什么还需要 redo log？

因为两者解决的问题不同：undo log 主要保证原子性，负责“修改失败后怎么撤销”；redo log 主要保证持久性，负责“已经提交的修改在崩溃后怎么重做”。

例如事务修改了 Buffer Pool 中的数据页，但数据页尚未刷回表空间：

-   如果事务回滚，需要根据 undo log 恢复旧值。
-   如果事务已经提交后 MySQL 崩溃，需要根据已持久化的 redo log 恢复新值。

因此只有 undo log，无法保证已提交但尚未写回数据文件的修改在崩溃后仍然存在；只有 redo log，也无法方便地撤销未提交事务或为 MVCC 提供旧版本。两者不能互相替代。

## 事务提交与崩溃恢复

### 1\. redo log 怎么保证事务持久性？

redo log 通过 WAL（Write-Ahead Logging，预写日志）保证持久性：修改数据页时，InnoDB 不要求立即把随机分布的数据页全部刷盘，而是先生成 redo 记录；事务提交时，按配置确保相关 redo 已经持久化，然后才向客户端返回提交成功。

数据页可以留在 Buffer Pool 中成为脏页，稍后再刷回表空间。如果提交后、数据页刷盘前发生崩溃，InnoDB 启动时会从检查点之后扫描 redo log，重做已经提交或需要恢复的页修改，并结合 undo 等信息处理未完成事务。redo 记录通过 LSN 标识顺序；检查点表示此前相关脏页已经推进到可安全复用日志空间的位置，使容量有限的 redo 文件能够循环使用，也缩小崩溃恢复需要扫描的范围。

持久性强度受 `innodb_flush_log_at_trx_commit` 影响。在常见的 `1` 配置下，每次事务提交都会将 redo 从日志缓冲区写入日志文件并执行持久化同步；设置为 `0` 或 `2` 可以减少同步开销，但操作系统或主机崩溃时可能丢失最近一段事务。因此不能脱离配置说 redo 在任何故障下都绝对不丢数据。

### 2\. 能不能只用 binlog，不用 redo log？

对 InnoDB 的正常事务恢复来说不能。binlog 和 redo log 位于不同层次，记录内容和用途也不同，不能直接互相替代。

binlog 是 Server 层的逻辑变更日志，适合复制和基于备份重放；redo log 是 InnoDB 面向数据页恢复的物理日志，包含页修改所需的信息和日志序列位置，可以高效地把崩溃前尚未刷盘的脏页恢复到一致状态。

如果没有 redo log，事务提交时就可能需要把涉及的所有数据页同步写回各自的随机位置，性能会显著下降；而且 InnoDB 现有的检查点和崩溃恢复机制也无法只依靠 binlog 工作。反过来，只有 redo log 也不能替代 binlog 的跨存储引擎复制和基于时间点恢复能力。

### 3\. binlog 两阶段提交过程是怎样的？

两阶段提交用于让 InnoDB redo log 和 Server 层 binlog 对同一事务保持一致。概念上的过程是：

1.  **Prepare 阶段**：InnoDB 写入 redo log，并把事务标记为 `PREPARE` 状态。
2.  **写 binlog**：Server 层把事务的 binlog 写入文件，并按配置持久化。
3.  **Commit 阶段**：InnoDB 在 redo log 中记录事务提交，事务完成。

如果没有这个协议，可能出现 redo 已提交但 binlog 没写，或者 binlog 已写但 redo 未提交，导致崩溃恢复后的主库数据与复制、时间点恢复结果不一致。

恢复时，如果 redo 中的事务已经提交，直接按已提交处理；如果只到 `PREPARE`，MySQL 会检查 binlog 中是否存在该事务的完整提交记录：存在则提交，否则回滚。实际实现还会使用组提交等机制优化刷盘次数，但面试回答两阶段提交时，核心是说明它解决 redo log 与 binlog 的一致性问题。

### 4\. 一条 `UPDATE` 语句的具体执行过程是怎样的？

一条 InnoDB `UPDATE` 大致经历 Server 层解析和优化、存储引擎读写记录、生成事务日志以及提交几个阶段。

1.  客户端发送 SQL，Server 层进行权限检查、解析和预处理，优化器选择执行计划。
2.  执行器调用 InnoDB，根据执行计划通过索引查找目标记录；所需数据页不在 Buffer Pool 时，需要先从磁盘读入。
3.  InnoDB 对目标索引记录加锁，检查条件，并生成用于回滚和 MVCC 的 undo 信息。
4.  InnoDB 在 Buffer Pool 中修改数据页，使其成为脏页，同时生成 redo 记录并写入 redo log buffer；如果索引列发生变化，还要维护相关索引。
5.  Server 层把逻辑变更写入该事务的 binlog cache。
6.  提交时通过两阶段提交协调 redo log 和 binlog；提交成功后释放事务持有的锁。脏页不必在提交时立即写回表空间，之后由后台线程按策略刷盘。

具体锁范围、读取行数和日志量取决于索引、执行计划、隔离级别、更新列以及命中的数据量，不能把 `UPDATE` 简化成“直接在磁盘 B+ 树上改一个值”。

### 5\. MySQL 如何保障数据不丢失？

MySQL 不能在所有硬件损坏、人为误删和多副本同时故障下无条件保证数据绝不丢失。更准确地说，它通过事务日志、刷盘策略、页保护、备份和复制降低不同故障下的数据丢失风险。

1.  **redo log 与 WAL**：保证已提交但尚未刷入数据文件的 InnoDB 修改可以在崩溃后重做。
2.  **undo log**：回滚未完成事务，使数据库恢复到事务一致状态。
3.  **binlog 与两阶段提交**：保证 binlog 和 InnoDB 提交状态一致，并支持复制和基于时间点恢复。
4.  **刷盘配置**：要求较强持久性时，通常使用 `innodb_flush_log_at_trx_commit=1` 和 `sync_binlog=1`。如果降低刷盘频率换取吞吐，主机崩溃时可能损失最近的事务。
5.  **Doublewrite**：降低数据页写入过程中发生部分页写、导致页面损坏的风险。
6.  **备份和复制**：定期全量或增量备份、校验恢复流程，并根据业务使用异步、半同步或更强的一致性复制方案，应对磁盘损坏、误操作和实例级故障。

因此要先明确要防的是进程崩溃、操作系统崩溃、断电、磁盘损坏还是误删除，再设计相应的恢复点目标和恢复时间目标，不能只凭一个日志参数承诺“零丢失”。

## 数据页写入与可靠性

### 1\. redo log 是在内存里吗？

redo log 既涉及内存缓冲区，也涉及磁盘上的日志文件。

事务执行过程中，redo 记录通常先写入内存中的 redo log buffer，随后由 InnoDB 写入 redo 日志文件，并根据 `innodb_flush_log_at_trx_commit` 等配置决定何时执行持久化同步。写入操作系统页缓存不等于已经稳定落盘，只有完成相应的持久化同步，才能在主机断电等故障后依赖它恢复。

所以，redo log buffer 用于减少频繁的小写入并支持批量刷盘，磁盘上的 redo 日志文件才是崩溃恢复所依赖的持久化介质。

### 2\. 为什么要写 redo log，而不是直接写到 B+ 树里？

因为直接把每次修改同步写回 B+ 树数据页，会产生大量随机 I/O，而且一次很小的行修改也可能要求写入整个数据页。redo log 采用 WAL，把离散的数据页修改先转换为体积更小、接近顺序追加的日志写入，事务可以更快完成持久化。

修改后的数据页仍然会写回 B+ 树所在的表空间，只是不要求在每次提交时立即完成。后台线程可以合并多次修改、按检查点和脏页比例批量刷盘，从而减少随机写和重复写。发生崩溃时，则从检查点位置开始使用 redo log 恢复尚未刷盘的修改。

因此 redo log 不是不写 B+ 树，而是把“事务提交时必须完成的持久化工作”和“数据页最终写回”解耦，以顺序日志写换取更好的吞吐和可恢复性。

### 3\. 了解 MySQL 的 Doublewrite Buffer 吗？

Doublewrite 是 InnoDB 防止部分页写（torn page）的机制。InnoDB 数据页通常比底层存储的一次原子写单位大，如果写数据页过程中断电或系统崩溃，表空间中的页面可能一部分是新数据、一部分是旧数据，形成损坏页。

刷脏页时，InnoDB 会先把页面写入 doublewrite 区域并持久化，再把页面写到各自表空间的最终位置。如果崩溃恢复时发现最终位置的页面损坏，可以从 doublewrite 中找到完整页面副本进行修复，然后再应用 redo log。

需要 Doublewrite 是因为 redo log 通常记录的是基于原页面的物理变化；如果作为恢复基础的数据页本身已经撕裂，就不能可靠地只靠 redo 修好。Doublewrite 会增加一定写放大，但其第一阶段可以批量、较顺序地写入，并且现代 MySQL 使用专门的 doublewrite 文件等方式优化开销。它和 binlog 写两份、主从复制都不是同一个概念。
