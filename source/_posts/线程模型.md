## Redis 线程模型

### 1. Redis 为什么快？

Redis 快不是单一原因造成的，核心是**以内存访问为主、高效的数据结构、事件驱动的网络模型，以及尽量短的命令执行路径**共同作用。

主要原因有以下几点：

1.  **数据主要在内存中操作**：多数读写不需要等待磁盘随机 I/O，内存访问延迟远低于磁盘。RDB、AOF 主要负责持久化，不是普通读请求的数据来源。
2.  **数据结构和编码经过优化**：Redis 针对不同场景使用 SDS、哈希表、跳表、`listpack`、`quicklist` 等结构，并会根据数据规模选择紧凑编码。
3.  **使用 I/O 多路复用和非阻塞网络 I/O**：一个事件循环可以监听大量客户端连接，只处理已经就绪的事件，避免为每个连接创建一个线程以及大量线程切换。
4.  **命令执行大多串行完成**：Redis 的核心命令执行路径通常由主线程处理，减少了锁竞争、线程同步和上下文切换开销，也让单条命令天然具有原子执行的特性。不过这不代表 Redis 所有工作都只有一个线程。
5.  **使用多线程和后台任务处理辅助工作**：使用 I/O 线程处理部分网络读写；持久化、异步释放内存等工作也可以由子进程或后台线程完成，从而减少主线程承担的耗时工作。命令本身仍主要在主线程执行。
6.  **协议和批量交互开销较低**：RESP 协议解析相对简单，客户端还可以通过 `pipeline` 合并多条请求，减少网络往返次数，提高吞吐量。

不过，“Redis 在内存中，所以一定快”并不准确。执行 `KEYS`、超大范围查询、处理 Big Key，或者运行复杂度较高的命令，仍可能长时间占用主线程；网络带宽、持久化配置、内存压力和热点 Key 也会影响实际性能。因此排查性能问题时，我会结合慢日志、命令复杂度、Key 大小、请求量和系统资源一起分析。

### 2. Redis 哪些地方使用了多线程？

Redis 并不是完全单线程。准确地说，**普通命令的核心执行仍主要由主线程串行完成**，但网络 I/O、磁盘同步和异步释放等辅助工作会使用线程。

主要包括以下几个方面：

1.  **网络 I/O 线程**：Redis 6.0 起可以配置 I/O 线程，并行处理部分客户端 Socket 的读取、协议解析和响应写回，降低网络读写成为瓶颈时主线程的压力。命令真正访问和修改数据的过程仍主要交给主线程执行，所以不是多线程并行执行普通命令。
2.  **AOF 的后台 `fsync`**：当 `appendfsync` 使用 `everysec` 策略时，Redis 可以把 `fsync` 交给后台 I/O 线程，避免主线程每秒直接等待磁盘同步完成。若使用 `always`，持久化语义更强，但延迟和吞吐会受到更明显影响。
3.  **异步释放内存**：执行 `UNLINK`，或者对 `FLUSHDB`、`FLUSHALL` 使用 `ASYNC` 时，主线程先从键空间解除关联，再由后台线程释放对象占用的内存。配置了 Lazy Free 后，部分过期、淘汰或覆盖操作也可以采用类似方式，减少释放 Big Key 对主线程的阻塞。
4.  **其他后台 I/O 工作**：Redis 的后台 I/O 线程还可以处理部分文件关闭等可能阻塞的系统调用，让主线程尽快继续处理客户端请求。

这里要特别区分线程和进程：`BGSAVE` 生成 RDB，以及后台重写 AOF，传统实现主要通过 `fork` 创建**子进程**完成，不属于多线程。子进程利用写时复制读取数据快照，父进程继续处理请求，但 `fork` 和写时复制本身仍可能带来延迟和额外内存开销。

所以面试中如果说“Redis 是单线程的”，通常指的是命令执行和核心数据结构操作主要由主线程串行完成；如果说 Redis 整个进程只有一个线程，就是不准确的。

### 3. Redis 的网络模型是怎样的？

Redis 的网络模型可以概括为 **Reactor 模式 + 非阻塞 Socket + I/O 多路复用 + 事件循环**。主线程不需要阻塞等待某一个连接，而是让内核同时监听大量文件描述符，只把已经可读或可写的连接交给 Redis 处理；命令对核心数据结构的操作仍主要由主线程串行完成。

Redis 内部有一层事件库 `ae`，它对不同操作系统的多路复用接口做了封装。`ae` 事件循环主要处理两类事件：**文件事件**负责监听 Socket 的连接、可读和可写状态；**时间事件**负责执行周期性任务，例如推进部分后台维护工作。网络请求主要走文件事件。

处理流程大致是：

1.  Redis 把监听 Socket 注册为可读事件。当有新连接到达时，内核通知 Redis，Redis 调用 `accept` 建立客户端连接，并把客户端 Socket 设置为非阻塞。
2.  客户端 Socket 被注册为可读事件。事件循环调用 `epoll_wait` 等接口等待，内核一次返回一批已经就绪的文件描述符。
3.  Redis 调用对应的读事件处理器读取请求，解析 RESP 协议，然后把命令交给主线程执行。
4.  命令结果先写入客户端输出缓冲区。如果不能立即全部发送，就为该 Socket 注册可写事件。
5.  Socket 可写时，事件循环调用写事件处理器继续发送；响应全部发送后，取消不再需要的可写事件，避免无意义地反复唤醒。

整个过程是 Reactor 风格：多路复用器负责发现就绪事件，事件循环负责分发，具体处理器负责连接、读取和写回。它的优势不是让一个线程同时执行多条命令，而是一个线程可以管理大量连接，并且只处理当前已经就绪的连接，避免“一连接一线程”带来的线程数量、锁竞争和上下文切换开销。
