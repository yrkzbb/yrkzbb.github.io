## 网络分层模型

### 1. 分别介绍一下 OSI 模型和 TCP/IP 模型？

核心区别是：**OSI 是一个七层的理论参考模型，TCP/IP 是基于实际互联网协议族形成的分层模型，工程实践中更常用 TCP/IP 模型**。分层的目的是让每一层只关注自己的职责，通过标准接口与相邻层协作。

#### OSI 七层模型

OSI 从上到下分为七层：

| 层次 | 主要职责 | 常见协议或例子 |
| --- | --- | --- |
| 应用层 | 直接为应用程序提供网络服务 | HTTP、DNS、SMTP、FTP |
| 表示层 | 处理数据格式转换、编码、压缩和加密 | JSON 编码、字符集转换、TLS 的相关表示功能 |
| 会话层 | 建立、管理和终止应用之间的会话 | 会话控制、同步点 |
| 传输层 | 提供端到端传输，处理可靠性、流量控制和端口复用 | TCP、UDP |
| 网络层 | 负责跨网络寻址和路由选择 | IP、ICMP，路由器 |
| 数据链路层 | 在直接相连的节点之间传输帧，处理 MAC 寻址和差错检测 | Ethernet、Wi-Fi、VLAN，交换机 |
| 物理层 | 通过传输介质发送比特流 | 网线、光纤、无线信号，中继器 |

OSI 的优势是边界清晰，适合学习、协议设计和故障定位。实际网络协议并不总是严格对应其中某一层，所以不能把七层边界理解为完全不可跨越的实现规则。

#### TCP/IP 四层模型

TCP/IP 模型通常分为四层：

| 层次 | 主要职责 | 常见协议或例子 |
| --- | --- | --- |
| 应用层 | 包含应用数据格式、会话和具体网络服务 | HTTP、HTTPS、DNS、SSH、SMTP |
| 传输层 | 负责进程到进程的通信 | TCP、UDP |
| 网际层 | 负责 IP 寻址、分组和路由 | IPv4、IPv6、ICMP |
| 网络接口层 | 负责本地链路上的帧传输和物理信号 | Ethernet、Wi-Fi、ARP |

有些教材会把 TCP/IP 的网络接口层拆成数据链路层和物理层，形成常说的五层模型。这是分层口径的差异，不代表底层协议发生了变化。

#### 两种模型的对应关系

| OSI 模型 | TCP/IP 模型 |
| --- | --- |
| 应用层、表示层、会话层 | 应用层 |
| 传输层 | 传输层 |
| 网络层 | 网际层 |
| 数据链路层、物理层 | 网络接口层 |

数据发送时会自上而下逐层封装：应用数据经过传输层后变成 TCP Segment 或 UDP Datagram，到网际层加上 IP 头部形成 Packet，到链路层封装成 Frame，最后转换为比特传输。接收端再按相反顺序解封装，把数据交给对应应用。

## HTTP

### 1. HTTP 报文由哪些部分组成？

从语义上看，HTTP 报文由**起始信息、头字段和可选的消息体**组成。在 HTTP/1.x 的文本报文中，具体表现为起始行、请求头或响应头、空行和消息体四部分。

#### 请求报文

```http
POST /users HTTP/1.1
Host: example.com
Content-Type: application/json
Content-Length: 16

{"name":"Alice"}
```

- **请求行**：包含请求方法、请求目标和 HTTP 版本，例如 `POST /users HTTP/1.1`。
- **请求头**：描述主机、内容类型、认证、缓存等元数据，例如 `Host`、`Content-Type`、`Authorization`。
- **空行**：在 HTTP/1.x 中用来分隔头部和消息体。
- **请求体**：可选，承载 JSON、表单或文件等数据。`GET` 通常不使用请求体。

#### 响应报文

```http
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 11

{"ok":true}
```

- **状态行**：包含 HTTP 版本、状态码和原因短语，例如 `HTTP/1.1 200 OK`。
- **响应头**：描述响应内容、缓存、Cookie 等信息，例如 `Content-Type`、`Cache-Control`、`Set-Cookie`。
- **空行**：分隔头部和响应体。
- **响应体**：可选，承载 HTML、JSON、图片或文件等内容。例如 `204` 响应就不包含消息体。

HTTP/2 和 HTTP/3 在传输时使用二进制帧，不再使用 HTTP/1.x 这种文本起始行和空行格式；例如方法、路径和状态会表示为 `:method`、`:path`、`:status` 等伪头字段。但从应用层语义看，仍然可以理解为控制信息、头字段和可选内容。

### 2. HTTP 常用状态码有哪些？

HTTP 状态码的第一位表示大类：`1xx` 是信息响应，`2xx` 表示成功，`3xx` 表示重定向或缓存协商，`4xx` 表示客户端错误，`5xx` 表示服务端错误。

| 状态码 | 含义 | 常见场景 |
| --- | --- | --- |
| `100 Continue` | 可以继续发送请求体 | 客户端使用 `Expect: 100-continue` |
| `200 OK` | 请求成功 | 成功查询或处理请求 |
| `201 Created` | 成功创建资源 | `POST` 新建资源 |
| `204 No Content` | 请求成功，但无响应体 | 成功删除或无需返回数据的更新 |
| `301 Moved Permanently` | 资源永久迁移 | 域名或 URL 永久更换 |
| `302 Found` | 资源临时位于另一地址 | 临时跳转 |
| `304 Not Modified` | 缓存协商命中，资源未变更 | 配合 `If-None-Match` 或 `If-Modified-Since` |
| `400 Bad Request` | 请求语法或参数有误 | JSON 格式错误、缺少必需参数 |
| `401 Unauthorized` | 缺少有效身份认证 | 未登录、Token 无效或过期 |
| `403 Forbidden` | 服务器理解请求，但拒绝执行 | 身份已识别但没有资源权限 |
| `404 Not Found` | 找不到目标资源 | URL 或业务资源不存在 |
| `405 Method Not Allowed` | 资源不允许该请求方法 | 对只读接口发送 `POST` |
| `409 Conflict` | 请求与资源当前状态冲突 | 重复创建、版本冲突 |
| `429 Too Many Requests` | 请求过多 | 触发限流 |
| `500 Internal Server Error` | 服务器内部异常 | 未处理异常或程序错误 |
| `502 Bad Gateway` | 网关从上游收到无效响应 | 上游服务异常或连接失败 |
| `503 Service Unavailable` | 服务当前不可用 | 过载、维护或临时降级 |
| `504 Gateway Timeout` | 网关等待上游响应超时 | 上游服务处理过慢 |

需要注意，`401` 的名称虽然是 Unauthorized，实际语义主要是“缺少有效认证凭据”；已经完成身份识别但没有权限时，通常使用 `403`。

### 3. HTTP `301` 和 `302` 分别表示什么？

`301` 和 `302` 都是重定向状态码，服务器通常通过 `Location` 响应头告诉客户端新地址。核心区别是：**`301` 表示资源已永久迁移，`302` 表示本次或暂时使用另一地址**。

- **`301 Moved Permanently`**：以后应该优先使用新 URL。浏览器、搜索引擎和中间缓存可能长期记住这个跳转，适合域名更换、URL 永久改版等场景。
- **`302 Found`**：当前资源只是临时从另一 URL 提供，客户端后续请求原则上仍应使用原 URL，适合临时活动页、登录跳转等场景。

在历史实现中，许多客户端遇到 `301` 或 `302` 时，会把原来的 `POST` 重定向为 `GET`。现行 HTTP 语义也允许客户端为了兼容这样处理。如果必须明确保留原请求方法和消息体，临时重定向应使用 `307 Temporary Redirect`，永久重定向应使用 `308 Permanent Redirect`。

### 4. HTTP `502` 和 `504` 有什么区别？

`502` 和 `504` 通常都是网关或反向代理返回的错误。核心区别是：**`502` 表示已经从上游收到了无效响应，或者无法正常建立上游连接；`504` 表示等待上游响应超时**。

- **`502 Bad Gateway`**：上游进程崩溃、端口未监听、连接被拒绝或重置，或上游返回了代理无法解析的响应，都可能导致 `502`。
- **`504 Gateway Timeout`**：网关通常已经尝试访问上游，但上游处理过慢、下游依赖阻塞或网络延迟过高，在规定时间内没有得到响应。

排查时，`502` 优先检查上游实例状态、端口、连接和协议是否正常；`504` 优先检查上游耗时、慢 SQL、连接池、下游依赖和代理超时配置。不过不同网关的错误映射可能有差异，最终要结合代理和上游日志判断。

### 5. HTTP 常用的请求方法有哪些？

HTTP 请求方法用来表达客户端希望对资源执行什么操作。常见方法有：

| 方法 | 常见语义 | 安全性与幂等性 |
| --- | --- | --- |
| `GET` | 获取资源 | 安全、幂等 |
| `HEAD` | 只获取与 `GET` 相同的响应头，不返回响应体 | 安全、幂等 |
| `POST` | 提交数据进行处理，常用于新建子资源或执行动作 | 通常不幂等 |
| `PUT` | 用请求内容创建或整体替换目标资源 | 幂等 |
| `PATCH` | 部分更新资源 | 不默认保证幂等，取决于补丁语义 |
| `DELETE` | 删除目标资源 | 幂等 |
| `OPTIONS` | 查询服务器或资源支持的通信选项 | 安全、幂等，常见于 CORS 预检 |
| `CONNECT` | 让代理建立到目标的隧道 | 常用于经 HTTP 代理建立 HTTPS 连接 |
| `TRACE` | 请求服务器回显收到的请求，用于诊断 | 实际服务中常因安全考虑禁用 |

这里的“安全”是 HTTP 语义上不应改变服务器资源状态，不代表信息传输更安全；“幂等”是多次执行与执行一次对资源的预期效果相同，不代表每次响应内容必须完全一样。

### 6. `GET` 和 `POST` 分别适合什么场景，有哪些区别？

核心区别是语义：**`GET` 用于获取资源，原则上不应产生业务副作用；`POST` 用于向服务器提交数据进行处理，常用于创建资源或执行动作**。

| 对比项 | `GET` | `POST` |
| --- | --- | --- |
| 典型场景 | 查询详情、列表、搜索 | 创建订单、提交表单、上传文件、执行有副作用的动作 |
| 参数位置 | 通常放在 URL 路径或查询字符串中 | 通常放在请求体中 |
| 安全性 | 语义上是安全方法，不应改变资源 | 通常会改变服务器状态 |
| 幂等性 | 语义上幂等 | 默认不保证幂等，重试可能重复创建或执行 |
| 缓存 | 浏览器和中间代理通常更容易缓存 | 只有满足明确缓存条件时才可被缓存，实践中较少 |
| 收藏与分享 | URL 中的查询条件便于复制、收藏和分享 | 请求体不会随 URL 一起保存 |
| 数据大小 | 受浏览器、服务器和代理的 URL 长度限制 | 可承载较大请求体，但仍受客户端和服务器配置限制 |

不能说 `POST` 天然比 `GET` 安全。两者在不使用 HTTPS 时都可能被窃听；敏感信息不应放在 URL 中，但放在请求体也仍需要 HTTPS、认证和授权保护。HTTP 并未统一禁止 `GET` 携带内容，但其请求体没有通用语义，一些服务器和中间件会忽略或拒绝，因此不应依赖它传递常规查询条件。

### 7. HTTP 长连接是什么？

HTTP 长连接，也叫持久连接，是指**一次 HTTP 请求响应结束后不立即关闭底层连接，后续请求继续复用它**。这样可以避免每次请求都重新建立 TCP 连接，HTTPS 还能减少重复 TLS 握手，从而降低延迟和 CPU 开销。

在 HTTP/1.0 中，持久连接通常需要显式协商 `Connection: keep-alive`；HTTP/1.1 默认使用持久连接，如果要关闭可以使用 `Connection: close`。服务器仍然可以根据空闲超时、最大请求数或资源压力主动断开连接，所以“长连接”不代表永不断开。

HTTP/1.1 在一条连接上通常要按顺序处理请求响应，实际客户端经常建立多条连接提高并发。HTTP/2 可以在一条连接上多路复用多个流，减少连接数；HTTP/3 基于 QUIC，复用的是 QUIC 连接，而不是 TCP 连接。

需要区分 HTTP 长连接、长轮询和 WebSocket：长连接强调底层连接复用；长轮询是服务器暂时不返回某个 HTTP 请求，等有数据或超时再响应；WebSocket 则是建立双向持久通信通道。

### 8. HTTP 的默认端口是什么？

**HTTP 的默认端口是 `80`，HTTPS 的默认端口是 `443`**。所谓默认端口，是指 URL 没有显式指定端口时，客户端根据 URI Scheme 选择的端口。

```text
http://example.com       -> example.com:80
https://example.com      -> example.com:443
http://example.com:8080  -> 显式使用 8080
```

端口只是约定的默认值，并不限制 HTTP 服务只能监听 `80`。HTTP/1.1 和 HTTP/2 的 HTTPS 通常在 TCP `443` 上运行；HTTP/3 基于 QUIC，通常使用 UDP `443`。

### 9. HTTP/1.1 如何判断请求边界？

TCP 只提供连续字节流，没有“一次读取就对应一个 HTTP 请求”的消息边界。因此 HTTP/1.1 解析器需要**先以 `CRLF CRLF`，即 `\r\n\r\n`，找到请求头结束位置，再根据头字段确定消息体长度**。

服务端一般按以下流程解析：

1. 从 socket 持续读取字节到缓冲区，先解析请求行。
2. 继续读取直到出现 `\r\n\r\n`，解析完整请求头。
3. 根据消息分帧规则读取请求体：
   - 有有效的 `Transfer-Encoding: chunked` 时，按分块编码解析；每块先是十六进制长度，再是对应数据，长度为 `0` 的块表示结束，之后还可以跟 Trailer。
   - 没有分块编码但有合法的 `Content-Length` 时，继续读取指定字节数。
   - 请求中两者都没有时，通常按没有请求体处理，而不能在持久连接上靠“等待连接关闭”确定请求体结束。
4. 报文完整后交给业务处理；缓冲区如果还有剩余字节，继续将其解析为持久连接上的下一个请求。

因此，TCP 的粘包或拆包对 HTTP 解析器来说是字节流分段问题：一个 HTTP 报文可能分多次到达，多个报文也可能一次被读到。程序不应依赖单次 `read()` 的边界，而应维护缓冲区和解析状态。对 `Content-Length` 与 `Transfer-Encoding` 冲突、重复长度字段等异常报文，前后端必须严格一致地拒绝或解析，否则可能产生 HTTP Request Smuggling 风险。

### 10. HTTP 断点续传是什么？

HTTP 断点续传是指文件传输中断后，不必从头开始，而是从指定的字节位置继续传输。对下载来说，它主要基于 HTTP 的 **Range Request** 机制。

例如，客户端已下载前 1000 字节，可以请求从第 1000 字节继续：

```http
GET /video.mp4 HTTP/1.1
Host: example.com
Range: bytes=1000-
```

服务器支持该范围时，返回 `206 Partial Content`：

```http
HTTP/1.1 206 Partial Content
Accept-Ranges: bytes
Content-Range: bytes 1000-9999/10000
Content-Length: 9000
```

`Content-Range` 表示本次返回的字节区间和完整资源大小。如果请求范围不可满足，服务器可以返回 `416 Range Not Satisfiable`。

为了防止中断期间文件已经变更，客户端可以保存 `ETag` 或 `Last-Modified`，续传时通过 `If-Range` 让服务器校验资源版本。版本不匹配时应重新下载完整文件，避免拼接出错误内容。

断点上传与下载不完全相同：HTTP 通用范围请求主要定义的是分段获取响应内容，断点上传通常需要业务 API 或专用协议支持，例如先创建上传任务，再按分片编号上传，最后校验并合并分片。

### 11. HTTP 为什么不安全？

这里通常说的是**明文 HTTP 不提供加密、完整性保护和服务器身份认证**，而不是说 HTTP 这个应用层语义本身必然导致安全漏洞。

- **不保密**：请求和响应以明文传输，路径上的网络节点可能窃听 Cookie、Token、请求参数和响应内容。
- **不保证完整性**：攻击者可能篡改传输内容，例如替换页面脚本、修改下载文件或注入广告，通信双方无法仅靠 HTTP 发现。
- **不验证通信对方身份**：客户端无法仅靠明文 HTTP 确认连接的是真实服务器，容易受到 DNS 欺骗、中间人攻击或恶意代理的影响。

HTTPS 在 HTTP 与传输层之间使用 TLS，通过加密、消息认证和数字证书解决传输途中的保密性、完整性和服务器身份认证问题。但 HTTPS 不会自动解决 SQL 注入、XSS、CSRF、越权和业务逻辑漏洞，这些仍需要应用层安全措施。
