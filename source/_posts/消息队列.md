## 消息队列场景

### 1. 什么是消息队列？

消息队列是一种异步通信中间件：生产者把消息发送到 Broker，Broker 负责存储和投递，消费者再按自己的处理能力消费。

它把消息的生产和处理解耦，双方不必同时在线，也不需要直接依赖彼此地址。常见模型有点对点和发布订阅，具体产品通常还提供持久化、确认、重试、顺序消费和消息回溯等能力。

### 2. 为什么需要消息队列？

主要是为了解耦、异步和削峰填谷。

- 解耦：订单系统只发布“订单已创建”事件，不需要逐一调用库存、积分和通知系统。
- 异步：把非核心链路放到后台处理，缩短主请求响应时间。
- 削峰：Broker 暂存突发流量，消费者按稳定速率处理，保护数据库等下游系统。

此外，它也适合事件驱动、日志采集和数据同步。但引入消息队列会增加一致性和运维复杂度，不能为了“架构高级”而使用。

### 3. 消息队列有什么缺点？

主要代价是系统复杂度和故障面增加：

- 异步链路只能做到最终一致时，需要处理重复、丢失、乱序和积压。
- Broker 故障、网络分区和客户端配置错误都可能影响业务。
- 排查从同步调用栈变成跨生产者、Broker、消费者的链路追踪。
- 消息序列化、网络传输和排队会带来额外延迟。
- 集群部署、容量规划、监控告警和升级都需要运维成本。

因此核心同步结果若必须立即返回，或业务量很小、调用关系简单，直接调用可能更合适。

### 4. 消息队列怎么选型？

我会先根据业务约束做压测和验证，而不是只比较单项吞吐量：

- 消息模型：是否需要事务消息、延迟消息、路由、过滤、回溯或流处理。
- 性能目标：吞吐量、端到端延迟、消息大小和峰值流量。
- 可靠性：副本机制、持久化、确认语义、故障切换和容灾要求。
- 顺序要求：全局顺序还是业务键范围内顺序。
- 运维生态：团队经验、监控工具、客户端语言和云服务支持。

一般来说，Kafka 擅长高吞吐事件流和日志场景；RocketMQ 对事务、延迟、顺序等业务消息支持较完整；RabbitMQ 的 AMQP 路由灵活、低延迟，适合中小规模业务消息。最终还要结合数据规模和实测结果选择。

### 5. 消息队列使用场景有哪些？

常见场景包括：

- 用户注册后异步发送邮件、短信和初始化数据。
- 秒杀、支付回调等峰值流量缓冲。
- 订单事件驱动库存、物流、积分等系统。
- 订单超时关闭、定时提醒等延迟任务。
- 数据库变更、日志和埋点进入数据平台。
- 跨系统最终一致性和失败重试。

前提是业务能接受异步处理，并设计好幂等、重试、监控和补偿机制。

### 6. 消息重复消费怎么解决？

消息队列通常采用“至少一次”投递，重试和确认丢失都可能造成重复，所以最终要由消费者保证幂等。

常见做法是为消息设置稳定的业务唯一键，例如 `orderId + eventType`。消费者在同一本地事务中写入去重记录并更新业务数据；也可以利用数据库唯一索引、条件更新或状态机阻止重复执行。Redis `SETNX` 可用于去重，但要处理过期时间、持久化以及 Redis 与业务数据库的一致性，不能仅靠短期缓存完成关键业务幂等。

### 7. 消息丢失怎么解决的？

要分生产、Broker 和消费三个阶段治理：

- 生产端：等待 Broker 确认，失败时有限重试；对关键消息可配合本地消息表或事务消息。
- Broker：开启持久化和多副本，选择满足可靠性要求的同步策略，并监控副本状态和磁盘。
- 消费端：业务处理成功后再确认；失败则重试，超过阈值进入死信队列或人工补偿。

同时要有消息轨迹、对账和补偿任务。任何方案都不能只靠一个配置宣称“绝不丢失”，还要明确故障模型、确认时点和可接受的数据损失窗口。

### 8. 使用消息队列还应该注意哪些问题？

除了重复、丢失和顺序，我还会关注：

- 消息体只放必要数据，控制大小，并设计可兼容的消息版本。
- 设置重试上限、退避和死信处理，避免毒消息无限重试。
- 做生产与消费限流，防止积压恢复时冲垮下游。
- 监控发送失败、消费延迟、积压量、死信量、磁盘和副本状态。
- 规划 Topic、分区或队列数量，避免热点键。
- 做好权限、传输加密和敏感数据治理。

还需要提前设计消息保留周期、回溯方式和故障演练流程。

### 9. 消息队列的可靠性、顺序性怎么保证？

可靠性依赖端到端协作：生产端确认和重试、Broker 持久化及多副本、消费成功后确认，再配合幂等、死信和对账补偿。

顺序性通常只能在一个分区或队列内保证。生产者应按 `orderId` 等业务键路由到同一分区，消费者对该分区串行处理，并避免异步线程导致完成顺序变化。若要求全局有序，可以只使用一个分区和单消费通道，但吞吐和可用性会受到明显限制。

### 10. 如何保证幂等写？

核心是让同一个业务操作执行多次与执行一次的最终结果相同。

数据库场景可以使用唯一索引配合 `INSERT`、带版本号或状态条件的 `UPDATE`，也可以在同一事务中写业务表和消费记录。例如：

```sql
UPDATE orders
SET status = 'PAID'
WHERE order_id = ? AND status = 'UNPAID';
```

受影响行数为 1 才执行后续逻辑。涉及外部支付、发券等副作用时，还要把幂等键传递给下游，并通过状态机、查询确认和补偿处理未知结果。

### 11. 如何处理消息队列的消息积压问题？

我会先止损并判断瓶颈在哪，而不是直接扩容消费者：

1. 观察生产速率、消费速率、消费延迟和失败率，检查是否有慢 SQL、下游故障、热点分区或毒消息。
2. 修复故障后，在分区或队列有余量且下游能承受的前提下增加消费者和消费线程。
3. 优化批量拉取、批量写入、I/O 和业务逻辑，对失败消息隔离处理。
4. 积压极大时可临时转发到更多分区或临时 Topic，由扩容后的消费者并行处理。

恢复期间必须限流并监控下游，处理完还要重新评估容量和告警阈值。消费者数量超过可并行分区数通常不会继续提升吞吐。

### 12. 如何保证数据一致性，事务消息如何实现？

消息队列场景一般追求最终一致性，而不是把所有服务放进一个强一致事务。

常见方案有事务消息和本地消息表。事务消息通常先发送不可消费的预备消息，再执行本地事务，最后提交或回滚消息；若提交结果未知，Broker 回查生产者的本地事务状态。消费者仍需幂等、重试和补偿，因为事务消息主要解决“本地事务与消息发送”的一致性，不会自动保证所有下游业务成功。

本地消息表则把业务数据和待发送记录写进同一本地数据库事务，再由后台任务投递并重试，流程更通用，但需要处理扫描、去重和状态维护。

### 13. 消息队列是参考哪种设计模式？

核心思想主要对应生产者—消费者模式和发布—订阅模式。

生产者—消费者模式通过缓冲队列协调两端速度；发布—订阅模式让一条事件被多个相互独立的订阅者接收。它还体现了观察者模式的思想，但消息中间件通常通过 Broker 异步传递并持久化消息，生产者和消费者不直接持有彼此引用，因此不能简单等同于进程内观察者模式。

### 14. 让你写一个消息队列，该如何进行架构设计？

我会先明确吞吐、延迟、消息大小、保留时间、投递语义和顺序范围，再设计核心链路：

- Producer SDK：路由、批量发送、超时重试和幂等标识。
- Broker：按 Topic 和分区追加写日志，维护索引、消费位点和副本。
- Consumer Group：分区分配、拉取、确认、重试和再均衡。
- 元数据与控制面：节点发现、分区 Leader、权限和配置管理。
- 高可用：多副本复制、Leader 选举、故障恢复和数据校验。
- 运维：积压、延迟、磁盘、副本状态监控，以及限流和死信处理。

第一版可以采用单机追加日志和拉取模型，再逐步加入分区、多副本和再均衡。设计取舍要围绕目标场景，不必一开始实现所有高级功能。

## RocketMQ

### 1. 消息队列为什么选择 RocketMQ 的？

如果业务以订单、交易为主，需要事务消息、延迟消息、顺序消息、重试和死信等能力，我会优先考虑 RocketMQ。它对这类业务消息提供了比较完整的原生支持，也支持按 Tag 或 SQL 属性过滤和消息轨迹。

但选型还要看团队经验、吞吐和延迟目标、云服务可用性及运维成本。若主要是超高吞吐日志和流处理，Kafka 生态可能更合适；若路由规则复杂且规模不大，RabbitMQ 也可能更简单。

### 2. RocketMQ 和 Kafka 的区别是什么？如何做技术选型？

两者都支持分区、多副本、消费组和高吞吐，但侧重点不同：

- Kafka 更偏事件流平台，分区日志、长期保留、回放以及流处理生态成熟，适合日志、埋点、CDC 和实时计算。
- RocketMQ 更偏业务消息，原生提供事务、延迟、顺序、重试、死信和消息过滤等能力。
- Kafka 的并行度主要由分区数决定；RocketMQ 也通过队列并行消费，但业务消息控制能力更直接。

不能只看官方吞吐数字。我会用真实消息大小、分区数、副本、确认级别、磁盘和消费逻辑压测，再结合功能需求和运维能力选择。

### 3. RocketMQ 延时消息的底层原理

核心是消息先由 Broker 持久化并标记为到期前不可投递，到达指定时间后再进入可消费状态，消费者不会在客户端本地等待。

版本差异会影响实现：RocketMQ 4.x 主要使用预设延迟级别，把消息转入内部定时 Topic，由定时任务到期后恢复原 Topic 和队列；RocketMQ 5.x 支持指定投递时间，Broker 使用定时存储与时间轮等机制调度。延迟消息适合订单超时等场景，但它不是严格实时定时器，实际投递会受 Broker 负载、存储和消费积压影响。

### 4. RocketMQ 怎么处理分布式事务？

RocketMQ 使用事务消息保证本地事务与消息发送最终一致：

1. Producer 先发送对消费者不可见的 half message。
2. Broker 保存成功后，Producer 执行本地事务。
3. Producer 根据结果向 Broker 提交 `Commit` 或 `Rollback`。
4. 若二次确认丢失或状态为 `Unknown`，Broker 回查 Producer 的本地事务状态。
5. 提交后消息才对消费者可见；回滚则不投递。

它不是跨所有下游服务的强一致两阶段提交。消费端仍要保证幂等，并通过重试、死信和补偿实现最终一致。

### 5. RocketMQ 消息顺序怎么保证？

RocketMQ 通常保证消息组或单个 MessageQueue 范围内有序，而不是整个 Topic 全局有序。

生产端应按 `orderId` 等业务键选择固定队列，使同一业务实体的消息进入同一队列；消费端使用顺序消费，让该队列的消息串行处理。失败重试时也要避免越过失败消息继续处理。全局有序可以只用一个队列，但会牺牲并行度，因此一般采用业务键局部有序。

### 6. RocketMQ 怎么保证消息不被重复消费？

RocketMQ 无法在所有故障场景下保证业务层“绝不重复”。例如消费者处理成功后 ACK 丢失，Broker 会重投；生产端超时重试也可能形成重复消息。

因此应采用至少一次投递加消费端幂等：使用业务唯一键，配合数据库唯一索引、状态机或同事务去重表。不能只依赖 `messageId`，因为同一业务操作重新发送时可能生成不同的消息 ID。

### 7. RocketMQ 消息积压了，怎么办？

先通过控制台和监控定位是所有队列积压还是个别热点队列，并检查消费失败、线程阻塞、下游慢调用和 Broker 负载。

修复根因后，可以在队列数允许且下游有容量时增加消费者实例或消费线程，优化批量消费，并把毒消息隔离到重试或死信流程。若原 Topic 队列数不足且积压非常大，可临时把消息转发到更多队列的新 Topic 并行消费。恢复过程中要限流，防止扩容后的流量压垮数据库。

## Kafka

### 1. 对 Kafka 有什么了解吗？

Kafka 是分布式事件流平台。消息按 Topic 组织，Topic 划分为多个 Partition，每个分区是只追加的有序日志，并可配置多副本实现容错。

Producer 负责选择分区并写入记录；Consumer 以消费组方式读取，同一分区在同一时刻只分配给组内一个消费者；消费进度用 offset 表示。Kafka 适合高吞吐日志、埋点、CDC、事件驱动和流处理，也支持幂等生产和事务，但顺序保证的边界是单个分区。

### 2. Kafka 为什么这么快？

Kafka 的高吞吐来自多种设计共同作用，而不是单个“零拷贝”：

- 分区日志以追加写为主，适合顺序磁盘 I/O，并依赖操作系统页缓存。
- 生产和消费支持批量、压缩，减少系统调用和网络开销。
- 分区可以分布到多个 Broker，并由多个消费者并行处理。
- 传输路径可利用 `sendfile` 等零拷贝能力，减少数据在内核态和用户态之间复制。
- 消费者按 offset 顺序拉取，Broker 不必为每个消费者维护复杂消息状态。

实际性能仍受消息大小、批量参数、副本确认、磁盘、网络、分区数和消费逻辑影响。

### 3. Kafka 的模型介绍一下，Kafka 是推送还是拉取？

Kafka 的核心模型是 Producer 把记录写入 Topic 的某个 Partition，Broker 按分区日志保存，Consumer Group 中的消费者负责读取分配给自己的分区并提交 offset。

从消费端看，Kafka 是拉取模型：消费者主动调用 poll 获取数据，可以控制速率、批量大小和消费位置。它支持长轮询，所以没有数据时不需要高频空转。拉取便于消费者按自身能力形成背压，但应用必须正确设置轮询、处理和 offset 提交策略。

### 4. Kafka 如何保证顺序读取消息？

Kafka 只保证单个 Partition 内的记录顺序，不保证多个 Partition 之间的全局顺序。

要保证同一订单的事件有序，Producer 应使用相同 key，让它们稳定进入同一分区；同一消费组内该分区只交给一个消费者读取。消费者内部若并发处理，还要按 key 串行化，或确保 offset 提交不会跳过尚未完成的消息。要求全局顺序只能使用单分区等串行方案，会限制吞吐和扩展性。

### 5. Kafka 消息积压怎么办？

先看 consumer lag、生产/消费速率和各分区分布，区分消费者故障、处理变慢、频繁再均衡和热点分区。

如果分区数大于消费者数且下游有余量，可以增加消费者；如果消费者已达到分区数，再加实例不会增加该组并行度，需要优化批处理、数据库写入和业务逻辑，或合理增加分区。积压严重时也可以让临时消费组把数据写入分区更多的临时 Topic 再并行处理。增加分区会影响 key 到分区的映射，不能在依赖顺序时随意操作。

### 6. Kafka 为什么一个分区只能由消费者组的一个消费者消费？这样设计的意义是什么？

准确说，是同一时刻一个 Partition 在同一个 Consumer Group 内只分配给一个 Consumer；不同消费组可以各自读取同一分区。

这样可以保留分区内顺序，避免多个消费者竞争同一 offset，并让消费进度管理和故障转移更简单。代价是单个消费组的最大直接并行度受分区数限制。一个消费者可以负责多个分区，但一个分区不会同时分配给组内多个消费者。

### 7. 如果有一个消费主题 topic，有一个消费组 group，topic 有 10 个分区，消费线程数和分区数的关系是怎么样的？

如果这里的“消费线程”指 10 个独立 Kafka Consumer，那么最多 10 个能同时获得分区：

- 5 个 Consumer 时，每个平均负责 2 个分区。
- 10 个 Consumer 时，通常每个负责 1 个分区。
- 超过 10 个时，多出的 Consumer 会空闲。

Kafka Consumer 通常不是线程安全的，一个 Consumer 应由一个线程调用 `poll`。应用可以把拉取后的记录交给工作线程池处理，但这会引入分区内乱序、背压和 offset 提交难题，需要额外协调。

### 8. 消息中间件如何做到高可用？

核心是避免单点，并让故障后能继续服务且数据满足预期的一致性级别：

- Broker 集群化，分区或队列配置多个副本。
- Leader 负责读写，Follower 同步数据，故障时重新选主。
- 元数据节点使用共识协议或高可用部署，客户端能刷新路由。
- Producer 使用确认和有限重试，Consumer 支持重新分配和断线恢复。
- 跨机架、可用区部署，并监控副本落后、磁盘和网络状态。

副本数不等于一定不丢数据，还要结合写入确认、同步副本条件、刷盘策略和故障范围配置。

### 9. Kafka 和 RocketMQ 消息确认机制有什么不同？

生产端两者都支持等待 Broker 确认和失败重试，但配置语义不同。Kafka 通过 `acks=0/1/all` 控制确认范围，配合 `min.insync.replicas`、幂等 Producer 和事务影响可靠性；RocketMQ 常见发送方式有同步、异步和单向发送，并根据 Broker 存储及副本策略返回结果。

消费端 Kafka 主要提交 offset，可以自动或手动提交；提交表示该消费组的进度已推进。RocketMQ Consumer 则向 Broker 返回消费成功或失败，失败消息按策略重试，超过次数可进入死信队列。两者在 ACK 或提交结果不确定时都可能重复，因此消费端仍需幂等。

### 10. Kafka 和 RocketMQ 的 broker 架构有什么区别？

Kafka 以 Topic Partition 为核心，每个分区有 Leader 和 Follower 副本，客户端直接与分区 Leader 通信。现代 Kafka 使用 KRaft 控制器集群维护元数据和选主；早期版本依赖 ZooKeeper。

RocketMQ 的路由由 NameServer 提供，Broker 向 NameServer 注册；经典部署中 Broker 按 BrokerName 组成主从组，消息物理写入 CommitLog，再通过 ConsumeQueue 提供按 Topic/Queue 的逻辑索引。较新的部署模式也支持基于 Raft/DLedger 或 Controller 的自动切换能力。两者都能横向扩展，但元数据管理、存储组织和故障切换方式不同。

## RabbitMQ

### 1. RabbitMQ 和 AMQP 是什么关系？

AMQP 是消息通信协议规范，RabbitMQ 是实现了 AMQP 的消息 Broker。

RabbitMQ 最常用的是 AMQP 0-9-1，同时也可通过插件等方式支持 AMQP 1.0、MQTT 和 STOMP。可以把 AMQP 理解为通信规则，把 RabbitMQ 理解为遵循这些规则并提供交换机、队列、路由和确认能力的具体产品，两者不是同一个概念。

### 2. RabbitMQ 核心组件有哪些？

主要组件包括：

- Producer：发布消息。
- Exchange：接收消息并根据类型、routing key 和 binding 路由。
- Queue：存储等待消费的消息。
- Binding：定义 Exchange 到 Queue 的路由关系。
- Consumer：订阅队列并处理消息。
- Connection 和 Channel：TCP 连接及其上的轻量逻辑通道。
- Virtual Host：隔离交换机、队列、权限等资源的逻辑空间。

消息通常由 Producer 发给 Exchange，再路由到 Queue，而不是直接发送给某个 Consumer。

### 3. RabbitMQ 有哪几种交换机类型？

常见有四种：

- `direct`：routing key 与 binding key 精确匹配。
- `fanout`：忽略 routing key，广播到所有绑定队列。
- `topic`：按点分隔的 routing key 做通配匹配，`*` 匹配一个单词，`#` 匹配零个或多个单词。
- `headers`：根据消息头属性匹配，通常不依赖 routing key。

RabbitMQ 还有默认交换机及插件提供的其他类型。选型取决于是一对一路由、广播还是规则订阅。

### 4. RabbitMQ 的特性你知道哪些？

RabbitMQ 的特点是 AMQP 路由模型灵活、客户端语言丰富，并支持持久化、Publisher Confirm、消费者 ACK、优先级、TTL、死信、流控和管理界面。

集群环境可以使用 quorum queue 提供复制和故障选主，也支持 Streams 处理可回放的大规模数据流。它适合业务消息和复杂路由，但最终吞吐、延迟和可靠性仍取决于队列类型、消息持久化、确认策略、磁盘和集群配置。

### 5. RabbitMQ 的底层架构是什么？

客户端通常先建立 TCP Connection，再复用多个轻量 Channel。Producer 将消息发到 Exchange，Exchange 根据 Binding 路由到一个或多个 Queue，Consumer 从 Queue 获取消息并 ACK。

单个队列由一个节点上的 Leader 负责处理。经典队列默认不复制；quorum queue 基于 Raft 在多个节点保存副本并进行 Leader 选举。RabbitMQ 集群会同步交换机、绑定和用户等定义，但“加入集群”本身不代表所有队列消息都自动拥有副本，需要选择正确的队列类型和副本配置。

### 6. 消息中间件 RabbitMQ 的可靠性保障怎么做？

需要覆盖完整链路：

- Producer 开启 Publisher Confirm，处理 nack、超时和连接中断；不可路由消息可使用 mandatory return 或备用交换机发现。
- Exchange、Queue 设置 durable，消息标记为持久化；但持久化仍应结合 Confirm 判断是否被 Broker 接受。
- 关键队列使用 quorum queue 和合理副本数，跨故障域部署。
- Consumer 关闭不合适的自动 ACK，业务成功后手动 ACK；失败时重试或进入死信队列。
- 消费端保证幂等，并配合心跳、自动恢复、监控、对账和补偿。

网络故障可能导致“Broker 已处理但确认未到达”，所以可靠投递往往伴随重复消息。

### 7. 讲一下 RabbitMQ 的延迟队列和死信机制。

死信是消息因被拒绝且不重新入队、TTL 到期、队列超长，或 quorum queue 超过投递次数限制后，被重新发布到配置的 Dead Letter Exchange，再按路由规则进入死信队列。

延迟队列常用“TTL + DLX”实现：消息先进入设置 TTL 的等待队列，到期成为死信后路由到实际消费队列。要注意普通队列中单条消息过期的检查可能受队头消息影响，不适合大量任意时间精度的定时任务。也可以使用延迟消息交换机插件；选择时要结合插件运维、可靠性、消息规模和版本能力。死信转发也不是天然零丢失，关键场景应使用合适的队列类型并做好监控和补偿。
