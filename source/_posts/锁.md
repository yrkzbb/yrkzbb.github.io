## 锁基础

### 1. MySQL 有哪些锁？应该如何理解？

MySQL 的锁可以从三个维度理解：锁多大范围、允许什么操作，以及具体锁住索引的哪一部分。

1. **按锁定范围**：包括全局锁、表级锁和行级锁。全局锁影响整个实例；表级锁包括显式表锁、协调 DDL 与 DML 的元数据锁（MDL），以及 InnoDB 的意向锁；行级锁粒度最小，适合高并发访问。
2. **按兼容模式**：分为共享锁（S 锁）和排他锁（X 锁）。S 锁之间兼容，S 锁与 X 锁、两个 X 锁通常冲突。`SELECT ... FOR SHARE` 使用共享锁定读，`UPDATE`、`DELETE` 和 `SELECT ... FOR UPDATE` 通常需要排他锁。
3. **按 InnoDB 行锁范围**：包括只锁索引记录的 Record Lock、只锁索引间隙的 Gap Lock，以及两者组合的 Next-Key Lock。后两者主要用于阻止范围内插入新记录。

还存在 AUTO-INC 锁等特殊锁。理解锁的关键是：InnoDB 的行锁实际加在索引记录或索引间隙上，所以锁住多少数据取决于隔离级别、查询条件、索引和执行计划，而不只是 SQL 最终返回了多少行。

### 2. 数据库的表锁和行锁有什么作用？

表锁和行锁都用于协调并发访问、避免冲突操作破坏数据一致性，主要区别是锁定粒度和并发成本。

1. **表锁**：一次锁住整张表，实现和管理相对简单，获取锁的开销较小，适合全表操作或并发要求不高的场景。但锁粒度大，即使两个事务访问不同记录，也可能互相阻塞，并发能力较低。
2. **行锁**：只锁住相关的索引记录或范围，不同事务修改不同记录时通常可以并发执行，适合高并发 OLTP 场景。但行锁的管理成本更高，事务锁定大量记录时会占用更多锁资源，也更容易形成复杂的锁等待和死锁。

InnoDB 的“行锁”本质上是索引记录锁，不是直接按数据页中的物理行号加锁。因此 SQL 是否使用合适索引，会直接影响扫描范围和实际锁定范围。表锁不一定总比行锁差，批量处理大量数据时，要根据访问范围、并发量、索引和执行计划判断。

## 锁与并发更新

### 1. MySQL 两个线程的 `UPDATE` 同时处理同一条数据，会不会阻塞？

会不会阻塞取决于事务是否重叠，但对 InnoDB 来说，如果两个事务确实同时更新同一条记录，通常会发生阻塞。`UPDATE` 需要对目标索引记录加排他锁，同一记录上的两个排他锁不兼容。

例如事务 A 先执行：

```sql
START TRANSACTION;
UPDATE account SET balance = balance + 100 WHERE id = 1;
```

在 A 提交或回滚前，事务 B 执行下面的语句通常要等待：

```sql
UPDATE account SET balance = balance - 50 WHERE id = 1;
```

A 释放锁后，B 才能继续，并基于届时可用的最新记录执行更新。如果等待超过锁等待超时时间，B 会报错；如果多个事务形成循环等待，还可能发生死锁，InnoDB 会回滚其中一个事务。

如果第一条语句在 `autocommit=1` 下已经执行并提交，第二条语句再开始，就不存在同时持锁，也不会因此等待。使用 MyISAM 等其他存储引擎时，锁行为也不能按 InnoDB 行锁理解。

### 2. 如果两个更新范围的条件不是主键或索引，还会阻塞吗？

有可能，而且阻塞范围往往会比预期更大。InnoDB 的行锁是加在扫描到的索引记录上的；如果过滤条件没有可用索引，执行计划通常需要扫描聚簇索引的大量记录甚至全表。

例如 `status` 没有索引：

```sql
UPDATE orders SET flag = 1 WHERE status = 'NEW';
UPDATE orders SET flag = 2 WHERE status = 'DONE';
```

虽然两个条件在业务上互斥，但两条语句都可能从聚簇索引头部开始扫描，并对扫描涉及的记录加锁，因此仍可能发生锁等待，不能仅根据最终匹配的数据范围判断它们一定互不阻塞。

具体锁定范围还受隔离级别、执行计划和版本行为影响。在 `REPEATABLE READ` 下，范围扫描还可能涉及间隙锁或 Next-Key Lock；在 `READ COMMITTED` 下，InnoDB 通常可以较早释放不匹配记录上的锁，并减少间隙锁，但目标记录上的排他锁仍会保留到事务结束。因此应先查看 `EXPLAIN`，并根据查询模式建立合适索引，而不是把“条件不同”当作不会阻塞的依据。

### 3. 两条 `UPDATE` 处理同一张表中不同的主键范围，一个 `id < 10`，另一个 `id > 15`，会不会阻塞？底层为什么？

在题设只有这两个简单主键条件的情况下，通常不会互相阻塞。因为一条语句处理 `id < 10`，另一条处理 `id > 15`，目标记录和需要保护的逻辑范围互不重叠。

```sql
UPDATE account SET status = 1 WHERE id < 10;
UPDATE account SET status = 2 WHERE id > 15;
```

底层原因是 InnoDB 的行锁建立在索引上。两条语句都可以使用主键索引直接做范围扫描，对各自命中的主键记录加排他锁；在 `REPEATABLE READ` 下，还会根据实际索引记录对相应边界使用 Gap Lock 或 Next-Key Lock。两边不会锁住同一条目标记录；即使稀疏数据使边界落在同一个物理索引间隙，纯间隙锁之间也是兼容的，它们的作用是阻止插入，不是互相排斥。两个事务在表级持有的意向排他锁（IX）之间也兼容，所以不会仅因操作同一张表而阻塞。

这个结论有明确前提：执行计划确实使用主键范围，并且 SQL 没有通过其他条件、触发器或外键操作访问共同资源。如果实际扫描了相同记录，或者事务此前已经持有其他冲突锁，仍可能等待甚至死锁。因此面试时应先回答“在题设条件下通常不阻塞”，再说明最终锁范围要结合执行计划和事务上下文确认。
